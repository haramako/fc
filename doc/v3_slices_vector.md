## 1. 設計方針と検討状況

### ユーザーから示された方針

- 基本的には Zig の slice を参考にする。
- array → vector は**コピー**。元メモの変換表の共有参照という表記は誤りで、ユーザー側で訂正済み。
- コピーに伴う不要な一時領域を避け、代入先での直接構築・in-place 初期化も考える。
- 8 ビットの添字を使いつつ、256 要素を扱いたい用途がある。
- 参照先の寿命、ROM、特にバンク切替に関わる管理は基本的に利用者の責任とする。
  ただし、単純な機能で管理負担を減らせるものは検討する。
- 容量不足は基本的に STP 相当の停止。必要な場面には成功・失敗を返す操作も用意する。
- 言語を複雑にしない。利用者向けのジェネリクスは導入せず、型に応じた共通処理が必要なものは言語組み込みにする。

### 実装済みの初版（2026-09-25）

- `[]T` / `[]const T` は slice、長さ推論の配列は `[?]T`（`fcc migrate` の規則 infer-arrays が `[]T` → `[?]T`）。
- 長さは **`u8`**（slice は 3 バイト、要素は 255 個まで）。ゲームの配列は大半が小さく、ループと添字が 8 ビットで済む
  （`lda (p),y` / `iny` / `cpy len`）。大きいものは後で別の型（`[]u16 T` のような広い slice、または vector）として足す。
- 長さの分かる配列 → slice は暗黙。文字列リテラルの長さは終端の 0 を含めない（メモリには 0 が残る）。
- `s[i]` は検査なし。`a[lo..hi]`（lo / hi は省略可）は定数の範囲だけ検査。
- `@len(x)`（配列は定数、enum はメンバー数）、`@slice(p, n)`、`@ptr(s)`、`@copy(dst, src)`（短いほうの長さ、要素数を返す。mem.copy）。
- const の配列を `[]T` に入れると警告（`*const` と同じ）。slice の const 宣言（ジャグ配列の表など）はまだ無い。
- 長さ `u16` の広い slice `[:u16]T`（4 バイト）。`[]T` → `[:u16]T` は暗黙（長さを広げて作り直す）、逆は長さが収まらない
  ことがあるので `@slice(@ptr(s), n)`。256 要素以上の配列の範囲、長さが `u16` の `@slice` は広い slice。
- vector は後回し。構文は **`[<N]T`**（容量 N、長さは実行時に変わる、領域を値自身が持つ）、容量によらない参照は `*[<]T`
  （2026-09-25 決定）。`[:N]T` も検討したが、`[:u16]u8`（参照）と `[:16]u8`（実体）が 1 文字違いになるのでやめた。

### 当初の提案・未決事項（記録）

- slice を「ポインタ＋長さ」の非所有ビュー、vector を「固定容量の領域＋現在の長さ」を持つ値とする。
- `[]T` を slice 専用にし、従来の初期値から長さを推論する配列を `[?]T` と書く案。
- 長さは `uint16`、slice はポインタ 2 バイト＋長さ 2 バイトの計 4 バイトにする案を推奨。
  **長さの幅はまだ確定していない。**
- vector の表記、変換の暗黙性、文字列の終端と長さ、組み込み API、動的境界検査の方針は未決。

本書への記録は、これらの提案の採用や実装開始を意味しない。

## 2. 型の役割

| 種類 | 表記案 | データ領域 | 長さ | 容量 |
|---|---|---|---|---|
| pointer | `*T` | 参照先を借りる | 持たない | 持たない |
| array | `[N]T` | 値自身が持つ | 型に固定 | N |
| 長さ推論 array | `[?]T` | 値自身が持つ | 初期値から N を推論 | 確定後は普通の `[N]T` |
| vector | `[N?]T` など（未決） | 値自身が持つ | 実行時に変わる | 型に固定した N |
| slice | `[]T` | 参照先を借りる | 値として持つ | 持たない |

ここでの「所有」はデータ領域を値自身が持つという意味で、所有権の移動・借用検査・自動解放を導入する意味ではない。
要素が pointer や slice なら、それらの参照先まで再帰的に所有・コピーするわけではない。

slice の容量フィールドは不要とする案。vector を slice にするときは使用中の要素だけを公開し、
容量を超えて伸長する操作は持たせない。vector を更新する関数には vector のポインタを渡す方法が考えられる。

`blob` はバイト slice（`[]uint8`）と同じ構造を想定した元メモの案。
別名を設けるか独立した型にするか、そもそも追加するかは未決。

## 3. slice と部分 slice

slice は、配列などの領域を「ポインタ＋要素数」で参照する値。
部分 slice は独立した型ではなく、既存の範囲の一部を参照する slice を作る操作を指す。

```fc
// 構文案。関数内の宣言を想定
var a:[8]uint8;
var all:[]uint8 = a[..];
var part:[]uint8 = all[2..5];
```

- 範囲は開始を含み、終端を含まない。上の `part` は添字 2・3・4 の 3 要素。
- 概念的には `{ ptr: &a[2], len: 3 }`。データのコピーもメモリ確保も行わない。
- `part[0] = 10` は `a[2]` を変更する。
- slice の値を代入するとポインタと長さがコピーされ、参照先のデータは共有される。
- 長さはバイト数ではなく要素数。部分 slice の先頭アドレスは `start * sizeof(T)` だけ進める。
- 空の slice や `s[len..len]` のような空の部分範囲も自然に扱いたい。

用途は、文字列の一部分を描画へ渡す、使用済み領域を除いた残りのバッファへ書く、など。
長さの取得を `s.len` とするか `@len(s)` とするかは未決。

Zig の基本モデルを参考にするが、定数の範囲指定を常に配列ポインタ型へ変えるなど、
Zig の細かな型推論規則までそのまま導入するとは決めていない。

## 4. array・vector のコピーと直接構築

```fc
// 構文案。[8?] は vector の仮表記
var a:[4]uint8 = [1, 2, 3, 4];
var v:[8?]uint8 = a;
```

意味は、`v` 自身の領域へ 4 要素をコピーし、現在の長さを 4 にすること。
`v` を変更しても元の `a` は変わらない。ここを共有参照にはしない。

実装は最初から `v` の要素領域へコピーして長さを設定すればよく、
一時 vector を作ってから全体を再コピーする必要はない。
リテラルや関数の戻り値も、代入先へ直接構築する方式を検討する。
これは余分なコピーを省く話で、元配列の領域を vector として再解釈する話ではない。

```fc
var b = a;                 // 提案: [4]uint8 を推論して配列をコピー
var v:[8?]uint8 = a;        // 型指定で vector へコピー
```

型指定なしの `var v = a;` だけから vector へ変換する規則は設けず、
元の array 型を推論するのが一貫している、という提案。

コピーの意味と、一時領域を省く最適化の条件は区別する。
既存領域への代入でコピー元と先が重なる場合や、初期化式が代入先の古い内容を読む場合には、
評価順序と重なりの扱いを別途定める必要がある。

### 変換の整理案

| 操作 | 意味・検討方針 |
|---|---|
| array → vector | 要素をコピーし、長さを設定する。共有参照にしない |
| array / vector → slice | 元の要素領域へのビューを作る。vector は現在の長さを使う |
| slice → slice | ポインタと長さのコピー。要素データは共有 |
| slice → array / vector | 要素のコピーが必要。長さ・容量の条件を検査する |
| array / vector の値のコピー | 自身の要素領域をコピーする。要素が slice なら、その参照先は共有 |
| pointer → slice | `@slice(ptr, len)` などで長さを明示する。参照先の有効性は利用者が保証 |
| slice / vector → pointer | 長さ情報を落とす操作。表記・暗黙変換の可否は未決 |

どれを暗黙の代入変換にし、どれを明示的な組み込みにするかは未決。
slice → array の長さ一致条件、vector の未使用領域の初期化・コピー範囲も決める必要がある。
外部バッファを所有型 vector として扱う元メモの `@vector(ptr, len)` / `@vec` 案は、
領域を自身で持つモデルとの整合性が必要なため、初版の提案範囲には含めない。

## 5. 8 ビット添字と 256 要素

256 要素の添字は 0〜255 のため 8 ビットに収まる。
しかし空を含む長さは 0〜256 の **257 通り**なので、独立した 8 ビット値だけでは表現できない。
添字の幅と長さの幅を分けて考える。

| 表現 | 利点 | 制約 |
|---|---|---|
| `len:uint16` | 空も 256 も通常の整数として扱える | メタデータが 1 バイト増える |
| `len:uint8`、0 を 256 と解釈 | 小さい。256 回のループに利用できる | 空のために別の状態・規則が必要 |
| `len:uint8`、最大 255 | 単純な 8 ビット表現 | 256 要素を扱う要求を満たさない |

通常の slice はポインタ 2 バイト＋長さ 2 バイトの計 4 バイトとする案を推奨する。
空の文字列や部分範囲もあるため、0 を 256 と解釈する方式を公開表現には持ち込まない。
vector も初版は長さ 16 ビットに統一する案。フィールド順・実際の ABI は未決。
小容量 vector の長さだけを 8 ビットに縮めるのは、メモリ使用量を見てから検討できる。
8 / 16 ビットの型を併設する場合の複雑さと現行 ABI による比較実験は
[長さ・ABI の試算](v3_slice_tradeoffs.md#1-長さを-8--16-ビットに分ける場合) を参照。

長さが 16 ビットでも、長さの範囲が分かるループを必ず 16 ビット添字で実行する必要はない。
例えば 256 要素を処理する専用ループは、8 ビットの添字が一周したことを終了条件にできる。
0〜256 要素の処理では空を先に判定し、残りを 8 ビットカウンタで処理する実装を選べる。
`@copy` / `@append` などの組み込みにこの実装を集約する案がある。
ただし要素サイズが 2 バイト以上なら、添字の幅とアドレス計算の幅も区別する。

```fc
// 問題になる形。s.len が 256 なら i は 255 の次に 0 へ戻り、終了しない
for (var i:uint8 = 0; i < s.len; i++) {
    // ...
}
```

このソースの意味を特別に変更して 256 回ループとすることは提案しない。
ソースでは 16 ビットのカウンタで正しく書き、条件を証明できる場合にコンパイラが縮めるか、
組み込み処理が専用ループを出す。これらは今後の実装・最適化案であり、現状の保証ではない。

## 6. 長さ推論配列の記法と文字列

現状の `[]T` は長さ省略の array であり、slice ではない。
`[]T` を slice 専用にするなら、初期値から長さを推論する配列には `[?]T` という別表記を使う案。

```fc
// 構文案
var a:[4]uint8;
var b:[?]uint8 = [1, 2, 3];  // [3]uint8 に確定
var s:[]uint8 = b[..];       // slice
```

`[?]T` は宣言時の推論用で、確定後は普通の `[N]T`。実行時の長さフィールドは持たない。
初期値のない外部データ参照など、現在 `[]T` が使われている別のケースは、
単純な `[?]T` への置換では済まないため移行規則を別途検討する。

```fc
var text:[?]uint8 = "hoge";
```

現在の「文字列は末尾に 0 を付ける」仕様を維持するなら、これは `[5]uint8` になる。
文字列を直接 slice へ変換するときの長さを 4 にするか、終端を含めるかは未決。
普通の `[5]uint8` の全体を `text[..]` で切り出す場合と、文字列リテラルからの変換は区別して決める必要がある。
`textmap` の文字列も終端 0 を持つため、同じ整理が必要。
castle の既存 API を調べた結果、通常の slice に加えて終端 0 を保証する読み取り専用 slice を
候補に残す価値がある。[sentinel の調査](v3_slice_tradeoffs.md#3-sentinel-終端の調査) に詳細を記録した。
採用もリテラルの長さ規則も未確定であり、現行配列の要素数を黙って変更しない。

`[?]T` と vector 候補の `[N?]T` は、意味が異なるのに見た目が近い。
長さ推論配列の記法を採用するなら、vector の表記も合わせて整理する。

## 7. 単純な仕組みで減らせる管理負担

### 読み取り専用性

- `[]const T` のような読み取り専用 slice を検討する。
- ROM 配列や文字列から作ったビューの読み取り専用性を引き継ぎ、書き込み可能な slice への暗黙変換を禁止する。
- 「この参照から書き込めない」という保証に留め、バンク切替や他の参照で内容が変わらないとは保証しない。
- 読み取り専用ポインタの提案と合わせて設計する。

### 長さ・容量の検査

- 容量 8 の vector に 9 要素を初期化するなど、定数で分かる不正操作はコンパイル時に拒否する。
- 部分 slice の範囲条件は `0 <= start <= end <= len` とする案。
- 動的な添字・範囲の検査はデバッグ時だけ有効にする案があるが、モードや失敗時の扱いは未決。
- 検査できるのは渡された長さに対する範囲。利用者が生ポインタから不正な slice を作った場合の有効性までは保証しない。

### 組み込み操作

```fc
// API 案。名前・引数・戻り値は未確定
@copy(dst, src);
var ok = @try_append(&v, src);
var s:[]uint8 = @slice(ptr, len);
```

- `@copy` は両方の長さを受け取り、ポインタと別にサイズを渡す手間を減らす。
  長さ一致を要求するか、コピー元の長さ以上の宛先を許すか、vector の長さを更新するかは未決。
- `@try_append` は固定容量 vector へ追加し、容量不足なら**変更せず false**を返す案。
  コピー前に容量を検査し、必要長の計算の整数オーバーフローも避ける必要がある。
- 通常の `@append` は容量不足で STP 相当の停止、`@try_append` は失敗を返す、という二本立てを基本案とする。
  ここでの STP は停止方針を表す。対象 CPU ごとの命令・停止ルーチンは未決。
- 元と先が重なるコピーや、vector 自身の部分 slice を追加する場合の意味は仕様化が必要。
- slice の記述子のコピーと、参照先の要素データのコピーは明確に区別する。

### `try!` の短いアイデアメモ

`try! concat(...)` または `concat(...)!` のように、失敗し得る呼び出しの結果を受け、
失敗時には停止することを呼び出し側で指定する構文も候補にする。
成功値の取り出し、失敗の伝播との区別、通常版 / try 版との関係は未決。
現時点ではこのメモだけに留め、エラー型・例外・ジェネリクスや構文の実装には進まない。

## 8. 自己管理とする範囲・初版の候補

参照先の寿命、バンク切替で参照先の内容が変わること、リングアロケータによる上書きは自己管理とする。
借用検査や自動のバンク切替は本案に含めない。
文字列 slice を vector に保存しても、元文字列の寿命が延びるわけではない。

初版の候補は **slice・部分 slice・固定容量 vector・`@copy`・`@append` / `@try_append`**。
これらは利用者向けジェネリクスや暗黙のメモリ確保なしで提供できる。

元メモにある、アロケータを明示的に渡す `@concat` / `@clone` は次の段階の候補。
戻り値の参照先の寿命、失敗時の戻り値、停止する版との関係を決めてから追加する。
リングアロケータ、独立した文字列型、オプショナル引数も初版の必須事項にはしない。

容量も持つ slice を言語の基本型として追加することは、現時点では推奨しない。
容量が必要な書き込み処理には、領域全体の slice と使用長を組み合わせた小さな構造体を使う案がある。
これは allocator から取得した領域でも、固定配列から借りた領域でも使える。

```fc
// 構文案。自動拡張・自動解放はしない
struct ByteBuffer {
    storage:[]uint8;  // 領域全体。storage の長さが容量
    used:uint16;     // 使用中の長さ
}

// 読む側には使用中の範囲だけを渡す
// buf.storage[..buf.used]
```

長さ 16 ビット案なら記述子は 6 バイト。通常の slice は 4 バイトのままにできる。
要素領域を内蔵する vector と異なり、この構造体は領域を参照する。
値をコピーしても領域は共有されるため、書き込み位置を更新する関数へはポインタで渡す案。
allocator 自体や所有権を値に持たせず、解放・リセットは呼び出し側で管理する。

部分 slice に容量を引き継ぐ仕様を追加せず、「参照できる範囲」と「追加できる領域」を分けて表せる。
動的な再確保による拡張は初版に含めない。再確保で既存の slice が無効になる規則が別途必要になるため。

## 9. castle の実コードからの検討（2026-09-20 追記）

### 調査範囲と判断

ユーザー指定により、最大の既存コードベースである `C:\Work\castle` の実ソースを主要な判断材料とした。
以下のファイル名は同プロジェクトの `src/` 相対。FC リポジトリの `examples/castle` とは内容が異なるため、
参照箇所を同一視しない。castle のソースの変更や実行・性能計測はしていない。

**通常の slice を基本とし、外部領域へ書き足す小さな ByteBuffer を早期に試す**案が実例に合う。
メモリ確保は既に複数箇所で使われている。ただし、確認した FC ソースの主な用途は
固定サイズ領域の切り出しと、必要量を一度確保して後で解放する文字列コピーであり、
容量不足のたびに再確保する動的コンテナではない。

### 利用例

| 箇所 | 現在の処理 | slice / vector 案への示唆 |
|---|---|---|
| `ppu.fc` の `alloc` | 256 バイトの `gr_buf` をカーソルで切り出し、末尾側に収まらなくなると先頭へ戻す | 要求した範囲の slice を返せる。領域の再利用で古い参照が上書きされる管理は残る |
| `ppu.fc` の `put` と `ppu.asm` の `ppu_put3` | ポインタとサイズをキューへ保存し、割り込み側で後から読む | API のポインタ＋長さを slice にまとめられるが、呼び出し終了までの寿命だけでは足りない |
| `event.fc` の `run_get_item` | `ppu.alloc(32)` の領域へ、文字列とファイル内容を末尾ポインタを進めながら連結 | 内蔵領域を持つ vector への置換より、借りた領域＋使用長の ByteBuffer に直接的な用途がある |
| `common.fc` の `heap_strcpy`、`heap.fc`、`event2.fc` | 文字列長を調べて一度確保・コピーし、イベント終了時に解放 | 長さ付きの clone に用途がある。容量を増やす機能はこの用途には不要 |
| `fs.fc` の `copy` | ROM バンクを切り替えてデータを RAM へコピーし、元のバンクへ戻す | 呼び出し後も有効な結果には、RAM へのコピーが必要。ROM の slice を返すだけには置き換えられない |
| `subtext.fc` の `process_subtext` | 64 バイトを確保し、ファイルのコピーが返す実サイズで PPU 転送 | 宛先の容量を持つ slice と、実際に書いた範囲の slice を使い分ける好例 |
| `text.fc`・`menu.fc` の文字描画 | 終端 0 まで読み、改行や濁点・半濁点のコードを処理してタイル領域へ書く | 文字列長は符号化済みのバイト数として扱う。表示幅や文字数とは別で、出力領域の長さも独立して必要 |
| `irqcmd.fc` の `begin` / `commit` / `add_*` | 128 バイトを 64 バイトずつの二面に分け、IRQ が読まない側へコマンドを追記 | 書き込み側の部分 slice＋使用長で容量管理できる。面の切替と IRQ への公開は従来どおり明示的に行う |
| `savedata.fc` の `data`、`bg.fc` の `data_buf` | 512 バイトの保存領域、2048 バイトの作業領域 | 言語全体の slice 長を 256 以下には制限しない方がよい。256 を超える実データもある |
| `en.fc` の `type` / `cur_max` / `new` | 固定スロットから空きを探し、使用範囲の上限まで処理する | 穴のある固定プールであり、全ての「配列＋カウンタ」を末尾追加の vector とみなさない |

### 先ほどの容量管理案への具体的な修正

「allocator をあまり使わないから容量付き構造は後でよい」とだけ判断せず、
**固定容量の外部領域に追記する処理は既にある**ことを設計へ反映する。

- §8 の ByteBuffer は将来の抽象的な候補に留めず、`run_get_item` の文字列組み立てで最初に試す候補とする。
- 初版ではバイト専用の struct と通常の関数でよい。複数の要素型で必要になったら共通処理を組み込みにする。
- 領域不足なら変更せず失敗を返す方針にできる。自動拡張や言語の基本型としての容量付き slice は必要ない。
- `fs.copy` の移行案は、宛先 slice の長さで容量を確認し、成功したら書いた範囲か書いた長さを返すもの。
  返却形式・失敗時の契約・ファイルサイズに終端 0 が含まれるかは、データ生成側も確認して決める。
- `heap_strcpy` は既に clone 相当の用途。汎用 allocator インターフェースを待たず、
  castle 固有の通常の関数として slice を返す形を試せる。
- PPU 用のリングバッファは明示的な寿命管理を維持する。現在の `alloc` はカーソルが周回する実装であり、
  単純な「フレームごとにリセットされる領域」と仮定してはいけない。

### 8 ビット ABI と長さ 16 ビットの接続

castle の `ppu.put` のサイズとキューの `gr_size_buf` は 1 バイト。
`ppu.asm` の通常転送ループは Y を 0 から増やしてサイズと比較するため、
この経路ではサイズ 0 のビット列が 256 回の転送になる形を持つ。
一方、言語の slice の長さ 0 は空を意味させたい。

従って、16 ビットの `slice.len` をそのまま下位 8 ビットへ切り詰めて既存 API へ渡してはいけない。
slice を受け取るラッパ側で空・1〜255・256・それ以上を明示的に扱い、
256 を特殊値で渡せるか、分割するか、拒否するかを転送モードごとに決める。
カスタム転送経路にも同じ規約があるとは仮定しない。
これは「公開する長さは普通の整数、専用ルーチン内部では 8 ビットの表現を使う」という §5 の具体例。

### 設計案を試す順序と検証項目

1. `subtext` のファイル読み込みから PPU 転送までを、容量付きの宛先範囲と使用中範囲で表す。
2. `event.run_get_item` の文字列組み立てを ByteBuffer で表し、不要な一時 vector や追加コピーが要らないことを確認する。
3. `heap_strcpy` 相当を長さ付きにし、イベント終了時の解放と文字列終端の契約を維持する。
4. `irqcmd` の書き込み側で容量検査を試し、割り込み側の配置・命令形式・公開手順を保つ。

実装時は空・255・256 要素、256 を超えるコピー、容量ちょうど・不足、文字列終端、
バンク復帰後の利用、キューに渡したバッファの消費時点を確認する。
生成コードのサイクル数、RAM / ROM 使用量、引数の受け渡しも既存コードと比較する。
現時点では読み取りに基づく設計上の判断であり、移行や検証を完了したという意味ではない。

## 10. ライブラリ API の利用イメージ

具体的な宣言・呼び出し例と契約案は [v3_slices_api_examples.md](v3_slices_api_examples.md) にまとめた。
以下も未実装の提案であり、現行の API や確定した仕様ではない。

| 用途 | API 案・データの流れ |
|---|---|
| 標準の文字列処理 | `str.equal` / `starts_with`、終端 0 との境界の `from_z` / `to_z`。基本は長さ付きバイト列 |
| 確保なしの連結・数値化 | 呼び出し側の領域 → `buffer.ByteBuffer` → `try_append` / `str.try_append_uint` → 使用中の slice |
| 自身で領域を持つ文字列・一覧 | 固定容量 vector ＋ `@try_append`。文字列 slice の一覧では参照先までコピーしない |
| 組み込み readonly ファイルシステム | 生成された数値 ID → `fs.read_into(id, dst)` / `read_at(id, offset, dst)` → RAM 上の使用中 slice。ファイル名検索・書き込み API は持たない |
| castle のメッセージ組み立て | ByteBuffer の残りへファイルを直接読み、実際の文字列長を反映して後続テキストを追加 |
| ゲーム特有の描画 | ゲーム文字コードの slice → `game_text.render_into` → タイル列の slice → `ppu.put_slice` で転送予約 |
| イベント間の文字列保持 | 明示的な `heap.clone` → 読み取り専用ビューとして利用 → 元の領域を `release` |

標準ライブラリはバイト列と容量管理、ユーザーライブラリはゲーム文字コード・ROM 配置・描画・割り込みを担当する。
容量不足は通常版で停止し、回復したい呼び出しには bool または `{ok, data}` を返す版を使う。
例中の回復用 API はジェネリクス・例外・optional 型を前提にしない。
バンク付き ROM のビューを返してすぐバンクを戻す API は避け、通常の読み出しは呼び出し側の RAM へコピーする。

## 11. 次に決めること

1. `#fc 3` の文法として `[]T` を slice、`[?]T` を長さ推論 array にするか。vector の最終表記と将来の v2 → v3 migrate。
2. 長さを 16 ビットにするか。容量の上限、レイアウト、引数・戻り値の ABI。
3. 暗黙変換の範囲、値コピー・重なり・直接構築の意味、vector の未使用領域の扱い。
4. 文字列の終端 0 と slice 長、`textmap`、既存の文字列 API との接続。
5. 読み取り専用型、長さ取得・部分範囲・生ポインタからの構築の表記。
6. 組み込みの失敗時の契約、動的境界検査、256 要素を処理する生成コード。
7. castle の実例での試行範囲、ByteBuffer の最小 API、既存の 8 ビットサイズを使う asm との接続。

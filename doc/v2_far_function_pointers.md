# farcall 対応の関数ポインタ

2026-09-21。V2 に `farfn(...):T` を追加。既存の `fn(...):T` の表現・呼び出しは維持する。
castle を調査した設計の経緯と、実装した仕様・制約を記録する。castle 自体の移行は行わない。

## 1. 背景（追加前）

- `fn(...):T` は 2 バイトの CPU アドレス。間接呼び出しは `reg` にアドレスを入れて `jsr_reg` を呼ぶ。
- 直接呼び出しの farcall は既存の `FC_FARCALL` 3 バイト（アドレス下位・上位・バンク）を使う。
  MMC3 トランポリンは呼び先アドレスからスロットを判定し、必要ならバンクを切り替え、戻る前に元へ戻す。
- 実行時の 2 バイトの関数ポインタから所属バンクは復元できない。同じ CPU アドレスに異なるバンクの関数が配置され得る。
- 小さい const 関数表は最適化で直接呼び出しに変換され、farcall になる場合がある。
  現在の対象は最大 16 要素などの条件付きで、可変コールバックも含めた言語機能の保証には使えない。

確認箇所: `internal/types/types.go`、`internal/sema/hlc.go` の `isFarCall`、
`internal/codegen/call.go` / `llc.go`、`internal/opt/devirt.go`、`fclib/nes/farcall_mmc3.asm`。

## 2. 採用仕様: fn と 3 バイトの farfn を分ける

| 型の表記 | サイズ | 呼び出し |
|---|---:|---|
| `fn(uint8):void` | 2 バイト | 現在のマッピングを使って呼ぶ。マッピングは呼ぶ側が管理 |
| `farfn(uint8):void` | 3 バイト | 所属バンクへ切り替えて呼び、元のバンクへ戻す |

`farfn` を型の予約語として追加した。表現はアドレス下位・上位・バンクの順に 3 バイト、パディングなし。
引数・戻り値の型を持つ通常の関数ポインタとして扱い、generic や別の呼び出し構文を要求しない。

```fc
options(farcall: true);
use event2;

public struct EventRunner {
    func:farfn():void;
    param:[8]uint8;
}
public var runner:EventRunner;

function setup():void {
    runner.func = event2.run_confirm_dialog;
}
function run():void {
    if (runner.func != null) {
        runner.func();
        runner.func = null;
    }
}
```

関数シンボルを farfn の文脈へ入れるときに、コンパイラがアドレスとバンクを組にする。
別バンクの関数を保持したコールバックをコピーしても、バンク情報が付いて回る。
farfn の const 配列、struct / SoA フィールド、引数・戻り値も同じ 3 バイト表現。
配列の 3 倍添字は 16 ビットで計算し、85 → 86 要素で 256 バイトを越える表も扱う。

### 変換・比較

- **関数シンボル → farfn**: 許可。実際の配置先シンボルからリンク時にバンクを取得する。
- **既存の fn 変数 → farfn**: 暗黙には変換しない。2 バイトの値だけではバンクが分からない。
  明示的にバンクを添える低水準の構築 API は、必要性を確認してから追加する。
- **farfn → fn**: 暗黙には変換しない。明示的なアドレス抽出を用意するかは保留。
- 型推論だけの `var f = target;` / `const TABLE = [f, g];` は既存の fn を維持する。
  farfn を作る場所は型注釈で明示する。代入・引数・戻り値・リテラルの文脈からも生成できる。
- `null` は 3 バイトすべて 0。比較・代入に対応する。通常の fn と同様に null 呼び出しの検査は挿入しない。
  使用前に呼び出し側で検査する。算術・順序比較は不可。
- farfn 同士の等価比較はアドレスとバンクを比較する。固定領域の関数についても生成時の表現を統一する。
- `uint16` / `*void` は 2 バイトなので farfn の代わりにはならない。既存の同サイズ `bitcast` 規則を崩さない。
- `options(farcall: true)` は **farfn を呼び出す場合**に必要。型・変数・定数の宣言やコピーだけなら不要。
- cc65 ABI / legacy fastcall の関数を farfn にすることは不可。通常の stack / Entry ABI の関数を使う。
- 手動バンク指定のコンストラクタは追加しない。整数からの farfn の `bitcast` も不可。
  同サイズの値どうしの `bitcast` は既存規則どおりの低水準操作であり、バンクやシグネチャの検証は行わない。
- 明示的な farfn 化は `options(near: true)` によらず実際の入口のバンクを保持する。

### バンク番号

実際に呼ぶ入口の `.bank(symbol)` を使う。関数に `options(segment: ...)` があっても、配置先をリンカに解決させる。
`.bank` は ld65 の実行メモリ領域の `bank` 属性であり、アドレスの bits 16–23 を取る `.bankbyte` とは別物。
ca65 の公式説明にも `.addr function` と `.byte <.bank(function)` を並べる表の例がある。
既存の独自 `ld65.cfg` をそのまま利用できる。[ca65: .BANK](https://cc65.github.io/doc/ca65.html#ss10.2)

初期 ABI は現在のトランポリンに合わせてバンク 0..255。範囲外の切り捨てを許さずリンク時に検査する。
MMC3 では CPU アドレスが呼び出しスロットも表すので、別のスロットフィールドは不要。
一般のマッパーへの対応はターゲット側のトランポリン契約として定義する。

## 3. 他案との比較

| 案 | 利点 | コスト・制約 |
|---|---|---|
| **fn と farfn を分ける** | 必要な場所だけバンク管理を任せられる。既存 ABI・手動切替を維持 | 型が 1 種増え、3 バイト値への対応が必要 |
| fn を全部 3 バイトにする | 型の使い分けが不要 | 既存の表・struct・引数・キャストの ABI が変わる。バンク管理不要の箇所にも増分 |
| 固定バンクに関数ごとの中継コードを生成し、fn は 2 バイトのまま | 表と変数のサイズを維持できる | 固定 ROM を消費。ポインタ値が本体のアドレスと異なる。アドレス取得・比較と最適化にも規約が要る |
| 固定領域の 3 バイト記述子を指す 2 バイトの値 | 変数のサイズを維持できる | 呼び出しに記述子の読み出しが加わる。既存 fn と同じ幅でも表現の互換性はない |

素朴な中継コードは、即値 `lda` + 絶対 `sta` を 3 組と `jmp farcall` で 18 バイト / 関数。
castle の PROCESS / NEW_FUNC に含まれる全 164 種の関数へ作るなら 2,952 バイトになる試算。
固定領域の関数などに中継を作らなければ減るが、固定 ROM の空きが必要な点は変わらない。

V2 は明示的な farfn を採用した。全 fn の表現変更は行わない。

## 4. castle での使い分けと容量

2026-09-21 に読んだ `C:/Work/castle/src` を基準とする（別作業で更新されるためスナップショットの数値）。

- `menu.fc` の SCENE_* 表: 同モジュールの関数なので通常の fn で足りる。
- `event.fc` の `EventRunner.func`、`common.fc` の `game_event_callback`、`my.fc` のタッチイベント:
  バンクをまたいで保存・遅延実行する用途なので farfn の候補。
  現在はコールバックを `options(segment: common)` / `options(segment: my)` に配置する例がある。
  farfn にすれば呼ぶための配置制約を緩められるが、関数の引数やデータ参照のマッピング条件は別に確認する。
- `en_vtbl.fc` の PROCESS / NEW_FUNC: 各 84 要素、各 82 種、合計 164 種の関数。
  アドレス表 2 本の 336 バイト + EN_BANKS 84 バイト = 420 バイト。
  2 本を 3 バイトの farfn 表にして EN_BANKS が不要になれば 504 バイト、差分は **+84 バイト**。
  EN_BANKS を別用途・高速な手動経路用に残すなら **+168 バイト**。

容量以上に大事なのが `en.process()` の切替方法。現状はループ中に呼び先のバンクへ切り替え、
**ループ終了時に一度だけ元のバンクへ戻す**。通常の farfn 呼び出しは毎回元へ戻すので、
これを置換するとバンク復帰の回数が増える。敵更新ループは手動切替 + fn を残す候補。
`en.setup()` は既に 1 回の呼び出しごとに復帰しているので、farfn に移行しやすい。

1 個のポインタの保存・コピーは 2 → 3 バイト。全体の呼び出しコストには、3 倍添字の計算、
表・変数からの読み出し、トランポリン判定、バンク退避・切替・復帰、Entry ABI が関係する。
3 バイト表は 85 要素で 255 バイト、86 要素で 258 バイトになる。
uint8 の添字でも、要素幅との乗算や各バイトの読み出しには必要に応じてアドレスの桁上がりを扱う。
既存メモの farcall サイクル概算は関数ポインタ経由の実測値ではない。
今回の実行検証は呼び先・結果・バンク復帰を対象とし、castle のホットループの性能測定・移行は別作業とする。

## 5. 実装と検証

- `fcc build -d` の far call 一覧にも載せる。実行時の呼び先は `indirect farfn(...):T` と表示する。
- 型のシグネチャとポインタの near/far 表現を分け、通常の関数入口のシンボルから生成する。
  呼び先には stack / Entry ABI で入り、`__direct` / `__frame` は使わない。
- 呼び先の値を一度評価・保持し、引数の評価が完了してから `FC_FARCALL` へ転送する。
  引数の式がコールバック変数を書き換えたり、別の farcall を行ったりしても、先に保持した呼び先へ入る。
- 呼び出しグラフでは near/far 表現を除いたシグネチャを照合し、Entry 保持・再帰検出・フレーム割付へ伝える。
  struct / SoA 内の関数シンボルもアドレス取得として扱う。
- 既存の関数表直接化・インライン化は farfn の呼び出しには適用しない。
  定数伝播で関数が確定しても、farfn の ABI とバンク切替・復帰は維持する。
- 配列・struct は 3 バイトのリンク時定数、SoA は各バイトの列として出力する。
  定数別名・表・SoA を含め `.bank(symbol)` が 0..255 に収まるかリンク時に検査する。

`internal/driver/farfn_test.go` は最適化なし / O2 の両方で以下を検証する。

- 値のコピー、引数・戻り値、null、struct / SoA、ポインタ経由、90 要素の表、再帰。
- 引数評価中の呼び先変数の変更と入れ子の farcall。
- MMC3 の実マッピングで、異なるバンクの同一 CPU アドレスにある関数の呼び分けと比較。
  固定バンク・同一バンク・2 スロット・入れ子からのバンク復帰。これは内部 NES ランナーでの検証であり実機テストではない。
- 無効な型変換や farcall オプション不足の診断。バンク 255 の成功と 256 のリンクエラー。

関数ポインタ表そのものが ROM にある場合、**表を読む時点でそのデータがマップされている必要がある**。
呼び出し時にコードのバンクを管理しても、表・引数・戻り値のデータポインタのバンク管理までは行わない。

既存の FC_FARCALL は共有領域なので、通常の入れ子と割り込みからの再入は別問題。
ISR からの farfn 呼び出しはサポート対象外。コンパイラによる経路全体の禁止・安全性検証は行わず、
既存 interrupt 問題や MMC3 参考実装の割り込みマスク処理は今回変更しない。

## 6. 参考と今後の検討

GBDK もバンク情報付きの far pointer と FAR_CALL を提供している。
公開の FAR_PTR は uint32_t なので、FC の 3 バイト案とは表現サイズが異なる。
参考にするのは「アドレスと所属バンクを組にして呼ぶ」という仕組み。
[GBDK far_ptr.h](https://gbdk.org/docs/api/far__ptr_8h.html)

GBDK の説明でも、far pointer 経由の呼び出しは共有変数を使うため ISR から使用しないとしている。
[GBDK ROM Banking / Far Pointers](https://gbdk.org/docs/api/docs_rombanking_mbcs.html#far_pointers)

今後の検討:

- 必要な場合の手動バンク指定・near アドレス抽出 API。
- farfn のバンク条件を保った直接化・インライン化の最適化。
- イベント・コールバックの実利用への移行。敵更新の一括切替は既存の fn を使い、個別に性能判断する。

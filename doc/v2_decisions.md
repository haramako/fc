## 1. 相互 `use` の可視性

### 事実

- **castle の 41 モジュールのうち 26 が 1 つの強連結成分（相互 use の塊）に入っている**:
  bg, bg_mmc, boxelev, common, debug_menu, en, en1〜en8, en_vtbl, ending, event, event2, fs, game,
  menu, my, my_process, savedata, sound, subtext。miku（7 モジュール）と fclib には循環なし。
  test には `test_cycle <-> cycle_use` の意図的な循環テストがある
- 現行の解決順序（`hlc.go:201 compileModule` / `hlc.go:55 Compile`）:
  1. `use X` に出会うと**その場で** X のトップレベル文（var/const/function 宣言、options、include）を処理する。
     X が登録済み（処理途中でも）ならそのオブジェクトをそのまま返す
  2. 全モジュールのトップレベル処理が終わってから、**関数本体**を全部コンパイルする
- つまり順序依存が効くのは**トップレベル評価**（const の初期値、配列長、options に他モジュールの
  シンボルを使う場合）だけ。関数本体からは全モジュールの全シンボルが見える
- `Scope.Find` の `finding` フラグは `use * from` の相互参照で無限再帰しないための防御で、
  可視性の仕様ではない

### 選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| A. DAG 強制 | 循環 `use` をコンパイルエラーにする | **castle の 26 モジュール塊をほどく大工事**（インターフェースモジュール分離・前方宣言の導入）が利用者側に発生する。v2 移行を「機械的」に保つ方針と矛盾。**不採用推奨** |
| B. 宣言フェーズ分離（順序非依存） | (1) 到達可能な全モジュールをパース（グラフ構築）→ (2) 全モジュールの宣言を登録。トップレベルの定数式は**シンボル単位で遅延評価**し、値レベルの循環（`const a = b.x; const b.x = a`）だけをエラーにする（Go のパッケージ初期化依存解析と同じ考え方）→ (3) 関数本体 | モジュール循環は許容したまま順序依存が消える。castle は現行で解決できている参照の上位互換なので結果は変わらない（副作用順の変化による asm 差分は F-mod の `-update` 範囲）。**採用推奨** |
| C. 現状維持を仕様化 | 到達順依存を文書化する | 分割コンパイル時に「順序」を再現する必要があり、キャッシュの正当性が担保しづらい |

### F-mod（分割コンパイル）への含意（案 B の場合）

- モジュールインターフェース（公開宣言 + const 値）は SCC 単位で一緒に計算する（宣言フェーズは
  コード生成を含まないので安価）。高価な関数本体コンパイルは**凍結済みインターフェースだけを入力**に
  モジュール単位で行えるので、キャッシュ単位はモジュールのまま
- キャッシュキーは「自モジュールのソース + 依存モジュールの**インターフェース**のハッシュ」。
  依存の本体が変わってもインターフェースが同じなら再コンパイル不要

### 推奨

**B**。R3-b では構造だけ B の形（`sema.CompileModule` + `ModuleInterface`）にして解決順序は現行のまま、
F-mod で遅延評価に切り替える。

### B の採用条件（2026-09-12 追加検討: 「B で問題ないか」の再確認）

方向として問題ない。ただし「上位互換」は**参照解決**についてであり、以下の 4 点は切替時に
明示的に扱わないと asm/ROM や挙動が変わる。いずれも F-mod の作業項目に入れる。

| # | 論点 | 事実 | 対処 |
|---|---|---|---|
| B-1 | **モジュールの登録順がリンク順** | `driver.go:133` が `hlc.Modules` の順（`use` 到達の深さ優先順）で `.o` を並べて ld65 に渡す。`fcc build`（miku）はこの順で ROM レイアウトが決まる。`base.asm` 生成（`driver.go:229`）も同じ順で走査 | **決定 2026-09-12: 発見順に依存しない**。リンク順は `use` の到達順ではなく**決定的で順序非依存な規則**（モジュール名のソート順を推奨。castle の Rakefile が `*.o` を glob するのと同じ結果になる）で定める。ROM レイアウトが変わって問題が出た場合は、**fc を使うプログラム側を書き換える**（例: 配置を固定したいコードは `options(bank:/org:/segment:)` で明示する）。切替コミットでは miku の ROM golden を意図的差分として `-update` |

それ以外の要素（`include asm/chr` のリスト、モジュール内の `Vars`/`Defs` 順 = BSS/コード配置順）は

### 1.1 B-2 の詳細: 名前衝突の解決規則（提案）

「衝突したらエラーにするか」への答えは **曖昧な衝突だけエラー、優先順位が明確な衝突はエラーにしない**。

#### コーパスの事実（2026-09-12 に静的解析）

- 現行 `Scope.Find` の順: 自モジュールの宣言 → `use * from` した順 → 親。すべて**無警告で先勝ち**
- `use X;` が作るモジュール束縛（`X` という名前）は `Public` なので **`use * from` で再輸出される**。
  castle はこれに全面的に依存している: `common.fc` が `use nes; use ppu; use fs; use bg; ...` を宣言し、
  全モジュールが `use * from common` でそれらを受け取る。**24 モジュール**が自前の `use X` なしに
  `X.y` を参照している（bg, en1〜en8, event, game, main, my, …）
- 「自宣言 vs glob 輸入の同名」: castle 23 件、miku 2 件、test 1 件。**うち関数/変数の実衝突は
  `my_process.fc` の `process`（`my.process` を自前定義で隠す）の 1 件のみ**。残りはすべてモジュール束縛
  （`use my;` を en と en1 の両方が持つ、等）で、指す先は同一オブジェクト
- 「glob vs glob の同名」: castle 84 件（全部 `en_vtbl` が `en1`〜`en8` を一括 glob するため）。
  内訳は同一オブジェクトのモジュール束縛が大半、実体が異なるのは `STEAM_DIR_FLIP` / `STEAM_DIR_SPR`
  （en5 と en7 が別々に定義）の 2 件で、**どちらも en_vtbl 内で非修飾参照されていない**

#### 提案する規則（v2 仕様）

| # | 衝突の種類 | 規則 | 根拠 |
|---|---|---|---|
| S1 | 自モジュールの宣言 vs glob 輸入（`use * from`） | **自宣言が勝つ。エラーにしない**（glob は弱い束縛）。`fcc check` で lint 警告は可 | Rust の glob import と同じ。castle の `my_process.process` が依存。B-2 の「部分状態で common.x を掴む」現象は、この規則を順序非依存に適用することで**常に自宣言**に統一される |
| S2 | 自モジュールの宣言 vs 選択的輸入（`use a from mod;`、§2 で導入） | **エラー**（再宣言） | 明示的輸入は強い束縛。Go/Rust と同じ |
| S3 | 選択的輸入 vs glob 輸入 | 選択的輸入が勝つ | Rust と同じ |
| S4 | glob vs glob で同名が**異なる実体**を指し、その名前が**非修飾で使われる** | **エラー**（曖昧） | 現行は先勝ちで無警告 = 潜在バグ源。castle は現状 0 件なので移行コストなし。使われていなければエラーにしない（Rust と同じ、en_vtbl の一括 glob を許容するため） |
| S5 | glob vs glob で同名が**同一実体**（複数経路で同じモジュール束縛が届く） | エラーにしない | castle の `my` 等 80 件超がこれ |
| S6 | モジュール束縛（`use X;`）の glob 再輸出 | **維持**（castle 24 モジュールが依存） | v2 文法では `public use X;` で再輸出を明示し、無印 `use X;` は再輸出しない、という整理が候補。マイグレータが `common.fc` の `use` 行に `public` を付与すれば互換。文法 v2 設計で決める |

**B-2 との関係**: S1 を順序非依存に適用するのが B 案そのもの。現行と結果が変わるのは
「部分状態の A を第三者が観測していた」ケースだけで、コーパスの静的解析では該当候補が
`my_process.process` の 1 件に絞られる。切替時の asm golden 差分で最終確認する。

## 2. `use * from` の継続可否

### 事実

- 使用数（castle + fclib + test）: `common` 19、`unittest` 13、`en` 9、`nes` 4、`math`/`resource`/`graphics` 各 3、
  `en1`〜`en8`/`bg`/`bg_mmc`/`boxelev_data`/`en_vtbl`/`fs_config`/`graphics_tbl`/`my`/`stdio` 各 1
- 用途は 2 種類に分かれる:
  1. **プレリュード**: `common`, `nes`, `unittest`, `math` — 全ファイルで暗黙に使いたい共通定義
  2. **1 つの論理モジュールをファイル分割**: `en` ← `en1`〜`en8`, `en_vtbl`; `graphics` ← `graphics_tbl`;
     `bg` ← `bg_mmc`。これは「同じモジュールの続き」を表現する手段が無いための代用で、
     **§1 の相互 use 塊の主因**でもある（en1〜en8 が全部 SCC に入っている）
- 言語リファレンスに書かれている選択的インポート `use print from stdio;` は**現行では構文的に到達不能**
  （`parser.y:85` の `id_list: tID` で、`tID` はレキサが決して返さないトークン）。実在する形は
  `use mod;` / `use mod as x;` / `use * from mod;` の 3 つだけ

### 選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| A. 廃止 | v2 で `use * from` を削除、全部 `mod.sym` 参照に | castle の書き換え量が大きい（`common` の定数参照が全ファイルに散っている）。マイグレータが自動で `mod.` 前置するのは、識別子の出所解決（= sema）が必要で、フォーマッタの範囲を超える |
| B. 維持 + 選択的インポートを実装 | `use * from mod;` を残し、`use {a, b} from mod;`（または `use a, b from mod;`）を**本当に**実装する。リファレンスの記述に実装を合わせる | 移行コストゼロ。名前空間汚染は利用者の選択に委ねる |
| C. B + 「複数ファイル = 1 モジュール」 | 用途 2 を言語機能にする（例: `module en;` 宣言を持つファイル群が 1 モジュールになる、または `en/` ディレクトリ = モジュール） | `use * from en1` 系の循環が構造的に消える。F-mod のキャッシュ単位も自然になる。ただし文法 v2 の設計項目が 1 つ増える |

### 推奨

**B を v2 の必須、C を v2 の検討項目**（文法 v2 設計の時点で決める）。`use * from` の廃止は C が
入って castle 側の移行が済んだ後に改めて判断する。

### 決定

- [x] **2026-09-12: 推奨どおり採用。** `use * from` は維持。選択的インポートを v2 文法で実装する
      （F-fmt の文法 v2 設計項目）。「複数ファイル = 1 モジュール」は v2 文法設計の検討項目。
      `use * from` の廃止可否は C 導入と castle 移行の後に再判断。
      付随: `parser.y` の到達不能規則 `id_list: tID` は v2 文法で削除、`language_reference.md` の
      `use print from stdio;` の記述は実装に合わせて改訂する（§5）

## 3. `include("xxx.rb")` マクロ機構の一般化

### 事実 — 現存するマクロは 5 ファイル 7 個で、性質が 4 種類に分かれる

| マクロ | 定義元 | 呼び出し数 | 何をしているか | 必要な能力 |
|---|---|---|---|---|
| `_T(str)` / `_M(str)` | castle `macro.rb` | 63 / 8 | 文字列リテラルをフォント表（`tmp/font/*.chr.txt`）で**バイト列に変換**し `[..., 0]` の配列にする | ビルド時のテキスト変換。外部表ファイルの読み込み |
| `VERSION_STR()` | castle `macro.rb` | 1 | `../VERSION` の中身を上と同じ変換で埋め込む | ビルド時定数の注入 |
| `printf(args...)` | fclib `stdio.rb` | 6 | 引数の**型**（`uint8*` なら `print`、int なら `print_int16`）で呼び分けるブロックに展開 | 引数型の参照（sema 情報） |
| `cos(x)` | fclib `math.rb` | — | `sin(x + 64)` への純粋な書き換え | 構文的置換のみ |
| `unittest_run_tests()` | fclib `unittest.rb` | test 全部 | スコープ内の `test_*` 関数を**列挙**して順に呼ぶブロックを生成 | スコープの列挙（リフレクション） |
| `times(n){...}` | fclib `stdmacro.rb` | 0 | ループ展開（現行では展開結果が不正で**使われていない**） | — |

- 現行 Go 版は `include("x.rb")` の**ファイル名**をキーに Go 実装へ固定（`macros.go`）。castle の
  `macro.rb` は castle のディレクトリ構造（`../tmp/font/`, `../VERSION`）に依存している
- 汎用マクロ機構が本当に要るのは表のうち「テキスト変換」だけで、他は言語機能か組み込みで足りる

### 選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| A. 汎用マクロ言語を作る | fc 言語内の宣言的マクロ / 外部コマンド（JSON で AST 授受）/ 埋め込みスクリプト（Starlark 等） | 実需要（上表）に対して過大。AST を利用者に公開すると文法 v2 以降の AST 変更が互換性問題になる |
| B. **用途別の小さな言語機能に置き換える** | (i) **文字列エンコーディング表**: `options(text_table: "tmp/font/text.chr.txt")` 等で表を登録し、`_T("...")` 相当をプレフィックス付きリテラル（例 `t"..."`, `m"..."`）か組み込み関数にする → `_T/_M` を代替。(ii) **ビルド時定数**: `fcc build -D VERSION_STR="..."` またはファイル参照 `options(define: {VERSION_STR: file("../VERSION")})` → `VERSION_STR` を代替。(iii) `printf` と `unittest_run_tests` は**組み込みのまま**（`include("stdio.rb")` を書かなくても使える標準機能に昇格）。(iv) `cos` は F2 のインライン関数で書ける。`times` は削除 | 利用者から見た変更は castle の `macro.rb` 1 ファイルと `include` 行だけ。マイグレータで機械的に置換可能 |
| C. 現状維持 | ファイル名キーの固定実装を v2 でも続ける | castle 専用コードがコンパイラに残り続ける |

### 推奨

**B**。文法 v2 の設計項目として (i)(ii) の表記を決める。移行期間中は `include("x.rb")` を
v1 互換の別名として受理し、警告を出す。

### 決定

- [x] **2026-09-12: 推奨どおり採用。** 汎用マクロ機構は作らない。用途別に置換する:
      (i) 文字列エンコーディング表（`_T`/`_M` の代替）、(ii) ビルド時定数（`VERSION_STR` の代替）、
      (iii) `printf` / `unittest_run_tests` は組み込み標準機能に昇格、(iv) `cos` はインライン関数（F2）、
      `times` は削除。(i)(ii) の表記は文法 v2 設計で決める。移行期間中 `include("x.rb")` は

## 4. 文法バージョン宣言の表記

### 事実

- 現行レキサで `#` は**いかなるトークンでもない**（`lexer.go` の記号表に無い）→ ファイル先頭の
  `#fc 2` は v1 では字句エラー。v1 処理系が v2 ファイルを黙って誤読することがない
- `options(...)` 文は既にあるが、パーサは**パースを始める前**にバージョンを知る必要があるので、
  文としてのバージョン宣言は先読みが要り、フォーマッタ/エディタ連携で扱いにくい
- 対象ファイルは castle 36 + miku 7 + fclib 11 + test 22。マイグレータが宣言行を機械的に付けられる

### 選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| A. 先頭行プラグマ `#fc 2` | ファイル 1 行目（空行・コメントは前置可）に `#fc <version>`。無ければ v1 | 単純。レキサの先頭で 1 行読むだけ。`fcc migrate` が付与する。**推奨** |
| B. `options(syntax: 2);` | 既存文法の再利用 | 先読みが必要。`options` は現在モジュール属性（bank 等）の入れ物で意味が混ざる |
| C. ファイル拡張子 `.fc2` | 拡張子で判別 | `use mod;` の解決規則が二重になる。エディタ設定も分裂 |
| D. プロジェクト設定 | `fcc build --syntax 2` / 設定ファイルで一括指定 | ファイル単体で自己記述できないので、`fclib` のように複数プロジェクトから使われるファイルで破綻 |

### 「宣言なし = v1」の期限

- 移行期間: 宣言なし = v1（現行ファイルが一切壊れない）
- 既知プロジェクト（castle / miku / fclib / test）の移行完了後: 宣言なしは**警告**付きで v1
- v1 パーサ削除時（時期未定）: 宣言なしは v2、`#fc 1` はエラー

D は A の補助として `--syntax` を用意してもよい（宣言なしファイルの既定を CLI で切り替える）。

### 推奨

**A**（+ 補助として D の CLI フラグ）。表記の細部（`#fc 2` / `#!fc 2` / `#version 2`）は好みで決めてよいが、
`#` 始まりであることが v1 との非互換性を保証する点は共通。

### 決定

- [x] **2026-09-12: A（先頭行プラグマ `#fc 2`）を採用。** 宣言なし = v1。補助として CLI の `--syntax` を
      用意してよい（宣言なしファイルの既定の切替用）。
      検討過程: 既存の `options(version:2);` 文を活かす案（B）も挙がったが、**レキサレベルの文法
      （字句規則・コメント・リテラル表記）はパース開始前に決まっている必要がある**ため、文としての
      宣言ではなくファイル冒頭のプラグマとして別扱いにする、という理由で A に確定。
      なお `options(...)` 文自体は将来 `@...` のような表記に変える構想があるが、それは文法 v2 設計
      （F-fmt）に委ね、本決定とは独立。

## 6. ドット参照の可視性・デフォルト可視性・マイグレーションの前提

### 事実（2026-09-12 に計測: `mod.name` で private に届いている参照を sema に一時フックを入れて数えた）

- 現行仕様: 宣言のデフォルトは **public**（`Module.CurrentPublic` の初期値 `true`、歴史的理由）。
  `private:` / `public:` ラベルで以降のデフォルトを切り替える（sema のコメントに「そのうち消す」とある暫定機能）。
  `private` の効果は「`use * from` の取り込み対象から外す」だけで、**`mod.name` のドット参照は private にも届く**
- ドット参照で private に届いている箇所: **castle 38 箇所・28 シンボル・7 モジュール**
  （menu 2 / game 6 / bg 2 / event 14 / sound 2 / my 1 / event2 1。参照側は event.fc 10、en7 5、debug_menu 4、en2 4、…）。
  **miku 0、fclib 0、test 0**。すべて参照先モジュールが直接宣言したもので、glob 再輸出経由（S6）は 0 件
- `stdio.init` はコンパイラ内部のマクロ `unittest_run_tests` が `ModuleInterface.Lookup` で直接参照しているだけで、
  利用者コードからのドット参照はない（v2 では `public` にするか、組み込み化（§3）の際に解消）

### 決定（2026-09-12）

1. **ドット参照は public のみ**（規則 S1〜S6 に S7 として追加: `mod.name` は `mod` の public 宣言だけを見る）
2. **宣言のデフォルトは private**。`public:` / `private:` ラベルは v2 文法から削除し、宣言ごとの `public` キーワードに統一する
3. **マイグレーションの元は「現時点の v1 ソース」**。public/private の付け直しも含めて `fcc migrate` が行い、
   移行のために v1 ソースを手で直すことは前提にしない。したがって:
   - v1 モードの sema は移行期間中ずっと「デフォルト public・ラベル有効・ドットは private に届く」を保つ
   - 可視性規則は**宣言側モジュールの文法バージョン**で決まる（v1 モジュールは default public / ドット private 可、
     v2 モジュールは default private / ドット public のみ）。これで v1・v2 混在プログラムが動き、
     モジュール単位の段階的移行ができる

### `fcc migrate` の可視性の扱い（設計）

`fcc migrate main.fc` はプログラム全体（main + `use` で届く全モジュール）を v1 sema で解決し、各宣言について
「他モジュールから参照されているか」を集める。参照の種類は (a) `mod.name` のドット参照、(b) `use * from mod` 経由の
非修飾参照、(c) モジュール束縛の glob 再輸出（`use X;` を glob で配っている → `public use X;`、S6）。

- `--visibility=minimal`（既定案）: **他モジュールから参照されている宣言だけに `public`** を付ける。
  未参照で v1 では public だったものは private に落ちる。参照されていないので挙動は変わらず、v2 らしい最小インターフェースになる。
  ドットで private に届いていた 28 シンボルは (a) で拾われて `public` になる
- `--visibility=preserve`: v1 の実効可視性（ラベルとデフォルト public）をそのまま `public` キーワードに写し、
  さらに (a) の 28 シンボルに `public` を足す。結果はほぼ全部 `public` になるが、インターフェースは v1 と同じ
- **fclib はライブラリ**なので利用側プログラム 1 つの参照では public 集合が決まらない。fclib は preserve で移行するか、
  `fcc migrate --lib fclib/ main1.fc main2.fc ...` のように複数プログラムの和集合を取る。v1 で `private:` 配下だった
  fclib の宣言（`stdio.init` など）は、それを参照する利用者がいなければ private のまま
- 検証: 移行前後で asm が一致すること（可視性は名前解決にしか影響しないので、参照が全部通れば asm は同一になる）。
  castle / miku / test 全体でこれを回す

# アクティベーション単位のグローバル領域・検討メモ

2026-09-21。調査と設計のたたき台。未実装。導入バージョン・構文とも未決定。
[型付き alias 案](v2_storage_alias.md) とは独立した、より大きな機能として扱う。

同日の追加方針: 利用者は active の正しさの検証を実行時に行う方向を指定した。
以下は静的な有効期間の証明を必須にせず、配置のための静的な共存契約と実行時検証を分けた案。
追加検討: 既存コールグラフから必要領域を推論し、処理の入口・切替境界でまとめて検査する案を推奨する。
これは有効期間全体の静的証明を要求せず、実行時検査の回数を減らすための解析。

## 1. 意図と中心となる区別

アクティベーションは、関数の呼び出し期間とは独立した、グローバル変数群の有効期間を表す。
activate した関数が return しても有効で、複数のフレーム・コールバックをまたいで保持できる。
deactivate は任意の順序で行えるものを想定し、LIFO を要求しない。

最初に区別するものは「現在コードが実行されているか」と「内容を保持する必要があるか」。
配置上の active は後者を意味する。ゲームの更新を止めてメニューを開いても、ゲーム状態が必要なら
ゲーム領域は active のまま。処理していないことだけを理由にメニュー領域と重ねることはできない。

一つの宣言に対する実体は一つの singleton とする案。複数の敵インスタンスを作る仕組みとは分ける。
同じ activation の二重 activate はエラーとし、参照カウントや多重インスタンスは別の拡張課題。

## 2. 既存の近い仕組み

### NESFab: groups と mode

NES 向け言語 NESFab はグローバル変数を vars グループへ所属させ、異なる mode の変数に RAM を再利用する。
mode 遷移には goto mode を使い、呼び出しスタックを捨てる。preserves は遷移時に保持するグループの指定。
参照: [公式マニュアル §12・§16.11.2・§16.29](https://pubby.games/nesfab/doc.html)。

今回の提案との共通点は「グローバル変数群の寿命を配置に使う」こと。
相違点は、FC 案では呼び出しスタックやゲーム全体の一つの mode と切り離し、複数領域を独立に保持できること。
先例からそのまま構文・制御フローを取り込むのではなく、グループと共存関係の考え方を参考にする。

### Keil C51 / BL51: data overlay

関数の自動変数・引数を呼び出し関係に基づいて重ねる。同時に必要な呼び出し元と呼び出し先は分離し、
互いに呼ばない関数の領域を再利用する。対象が関数フレームなので、今回の長期保持するグローバル群とは異なる。
参照: [BL51 の説明](https://www.keil.com/support/docs/1854.htm)。

### GNU ld: OVERLAY

複数セクションへ同じ実行アドレスを与える。配置の機構であり、プログラムの有効期間を自動推論する機能ではない。
NOCROSSREFS はセクション間参照を禁止できるが、時間的な有効期間の正しさとは別の検査。
参照: [GNU ld OVERLAY](https://sourceware.org/binutils/docs/ld/Overlay-Description.html)。

### C++ Boost.Statechart: state-local storage

状態へ入る際に状態オブジェクトを作り、出る際に破棄して、状態ごとのデータを持つ。
状態に付随する寿命とモジュール分割の先例だが、固定アドレスの静的オーバーレイを保証するものではない。
参照: [Statechart rationale](https://www.boost.org/doc/libs/1_41_0/libs/statechart/doc/rationale.html#StateLocalStorage)。

## 3. FC では三つの層に分ける

1. 領域の宣言: どの変数がどの activation に属するか。
2. 共存規則: どの activation の組み合わせを同時に保持し得るか。
3. 有効期間の操作・検査: 実行中にどれが active か、アクセスが正しいか。

各モジュールは自分の変数群だけを宣言し、アプリケーション側がグループ名の組み合わせを指定する。
中央へ全 struct や変数の詳細を集める必要はない。ただし安全な共有配置には、共存関係の全体情報は必要。

以下は説明用の疑似構文で、予約語・属性表記を決定するものではない。

```fc
// menu.fc
public activation work {
    var cursor:uint8;
    var items:[32]uint8;
}

function update():void {
    work.cursor += 1;
}
```

activation の ID の公開と、内部変数の公開は分ける。外部は menu.work を有効化できても、
個々の変数は従来の public 規則を適用し、領域 ID の公開だけで全変数を公開しない。

## 4. 有効期間と共存の指定方法

### A. 共存可能な集合を宣言し、activate / deactivate を明示する

```text
allowed { audio.work, title.work }
allowed { audio.work, world.work, menu.work }
allowed { audio.work, world.work, dialog.work }
```

現在の active 集合は、いずれかの allowed 集合の部分集合でなければならない、と定義する。
これなら初期化・切替途中の部分集合も扱える。集合に書かれていない組み合わせは許可しない。
常駐の通常グローバル変数は、すべての activation と重ならない別の領域に置く。

```text
open_menu():
    activate(menu.work)
    menu.init()
    return                 // menu.work は active のまま

close_menu():
    menu.finish()
    deactivate(menu.work)
    return
```

この形は呼び出しスタックから独立し、ユーザー案に最も直接対応する。
ただし操作を追加するだけでは共有可能性は分からない。全プログラムの任意の実行経路を完全に解析する代わりに、
allowed を配置の契約として使い、操作時にその契約が守られることを検査する必要がある。

配置のための二者間の共存グラフは allowed 集合から作れるが、実行時の検査には集合の規則そのものを使う。
二者ずつ共存可能でも、三者同時は許可しない設計があり得るため。

### B. 名前付きの状態集合へ切り替える

```text
state title   = { audio.work, title.work }
state playing = { audio.work, world.work }
state menu    = { audio.work, world.work, menu.work }
state dialog  = { audio.work, world.work, dialog.work }
```

transition(menu) のように有効集合をまとめて切り替える。
old と new の共通領域は保持、old にだけある領域は終了、new にだけある領域は新規開始とする。
個別の activate/deactivate の記述漏れを減らせるが、全体状態の組み合わせが増えると宣言数も増える。
関数から return しても状態は続く。NESFab と異なり、スタックを捨てる操作にはしない案。

### C. 階層と排他グループで表す

title と game を排他、game の内部に field/menu/dialog を置くなど、状態機械の階層で表す。
親と子、並行する子は別領域。同時に選ばれない兄弟は重ねられる。
表現できる構造では必要サイズを「親のサイズ＋排他なら最大値／並行なら和」で計算しやすい。
ただし arbitrary な独立 activate を木構造へ押し込める制約があるため、最初から必須にしない。

推奨する概念の中心は A。B はよく使う切替を安全にまとめる上位機能、C は規則を短く書く補助表現として検討する。

## 5. 配置は静的、有効期間は実行時に変化できる

各 activation はビルドごとに固定アドレスを持ち、変数はその先頭＋固定オフセットになる。
activate 時に malloc・探索・移動を行わない。変数アクセス自体にポインタを導入しない。

同時に保持し得る二領域に競合の辺を張り、辺のある領域は重ねない。
辺のない領域は重ねてよいが、すべての非競合ペアが必ず同じ番地になるわけではない。
サイズ・アラインメント・領域種別の制約の下で、総確保量を小さくする配置問題になる。
同時 active サイズの最大値は下限であり、任意の共存グラフではその値ぴったりに配置できるとは限らない。
不明な関係を「非競合」と推測しない。非競合の契約または証明がない場合は分離する。

説明用サイズ:

| 領域 | サイズ | 共存 |
|---|---:|---|
| audio | 64 | 常時保持 |
| title | 128 | audio のみ |
| world | 256 | audio、menu または dialog |
| menu | 96 | audio、world |
| dialog | 80 | audio、world |

この例は通常合計624バイト、共有配置なら416バイトで足りる。
audio を +0..63、world を +64..319、menu/dialog を +320 から配置し、title を +64 から重ねる。
world の更新を停止して menu を表示しても、world の内容は保持される。

RAM の通常領域・SRAM・ZP など配置クラスの違いも守る。
既存 ld65.cfg では activation 用のまとめた BSS プールを一度だけ確保し、コンパイラが内部オフセットを割り当てる案。
プールの配置は既存の segment 設定に従い、独自 cfg の経路を残す。

## 6. 有効化・終了の意味

- active は内容を保持する権利を持つ期間。関数の実行中かどうかとは無関係。
- deactivate 後の内容は破棄可能。再 activate しても以前の値は保証しない。
- 初期化の方法は明示する。初案は init 関数で必ず必要な値を設定し、自動保存・復元は行わない。
  起動時にたまたまゼロだったことを再 activation 時にも期待してはいけない。
- ゼロクリアを選べる拡張は可能だが、領域サイズ相当の実行コストがある。
- 休止中も内容を残したい領域は active のまま。保存して領域を解放する機能は別機能。
- activate / deactivate は同種操作の重複をエラーにする案。暗黙の参照カウントは入れない。

推奨する実行時検証は二段階に分ける。

1. activate/deactivate 時の検査: active 集合の更新前に共存契約と二重 activate / 非 active の deactivate を検査する。
   違反は STP と診断。通常ビルドでも残す案とし、今回の用途では失敗を返して別の動的配置を探す方式にしない。
2. 処理の入口の検査: update / draw / イベントハンドラ等の明示した入口で、呼び出し先を含む必要集合が
   現在の active 集合に含まれるかを検査する。処理中の有効集合を安定させれば、毎アクセスの検査を避けられる。
   自由な途中切替や未追跡ポインタまで完全に検出する保証はない。使用地点の詳細検査は追加のデバッグ機能とする。

領域データのアドレスは固定で、release の通常アクセスは直接アクセスにできる。
active 状態のビット集合や切替検査には RAM・コード・実行時間が必要。
毎アクセスの検査を有効にすればその分のコストもあるため、「機能全体がゼロコスト」とは言わない。
初期の実装では操作の担当をメイン側に限定し、IRQ/NMI から activate/deactivate は行わない案。

## 7. 大きな設計課題はアクセス権と切替途中

### 関数が必要とする activation

ユーザーの追加案: コールグラフを使い、おおもとの処理・activation の切替時に検査を集約する。
これには次の解析で足り、一般的な有効期間の証明とは分けられる。

```text
direct(f)   = f が直接アクセスする activation の集合
required(f) = direct(f) ∪ 各呼び出し先 g の required(g)
```

再帰の閉路は集合が変化しなくなるまで伝播する。関数に付けるのはコンパイル時のメタデータであり、
全関数の実行時フレームへ集合を追加するわけではない。
グループ数 N に対し、検査は概念上 `required & ~active == 0` の ceil(N/8) バイト比較で済む。
検査の機械語・厳密なサイクル数は未試算。共有ポインタを毎アクセス検査する方式より回数を抑えやすい。

推奨する検査入口はメインループ自体ではなく、そのディスパッチ先の update / draw / callback 等。
main から到達する全処理を一括すると、排他の title と game まで両方必要になってしまう。
一つの処理内に排他的な分岐があり双方の領域を参照する場合も、単純な集合和は過大になる。
その場合は検査入口を分けるか、選択された下位処理の入口で検査する。

実行規則の初案:

1. 境界で active 集合の変更を適用し、共存契約を検査する。
2. 実際に実行する処理の required を active と照合する。
3. その処理と呼び出し先が戻るまで active 集合を変更しない。
4. 処理中の切替要求は予約し、戻った後の境界で適用する。

これなら関数内部は検査なしで直接アクセスでき、activation 自体は複数フレームをまたいで存続する。
初案の自由な activate/deactivate を即時実行する方式より制約が増えるため、採用は未決定。
即時切替も許す場合は、切替後のアクセスに追加の検査が必要で、呼び出し元へ戻る経路も考慮する。
入口で一度通った検査だけを根拠にしてはいけない。

active 集合が変わる時だけの検査をさらに狙うなら、現在登録されている各ハンドラの required も検査する必要がある。
同じ active 集合のまま呼び出し先を差し替えた場合は再検査する。
最初は各ハンドラ入口で検査し、active 集合とハンドラがともに不変な場合の省略は後の改善に回す。

### ポインタ・コールバック・asm

領域へのポインタを外へ保存すると、deactivate 後や別用途へ再利用後に古いポインタが残り得る。
関数ポインタはコードの寿命とは別に、コールバックが要求する activation を持つ。
ここを完全に静的検査するにはポインタ・関数型への効果／寿命情報など、alias より大きい仕組みが必要。
実行時検証を採用する初期案では、生ポインタの保存・寿命と asm 経由のアクセスは自己管理箇所として明示する。
通常の生ポインタには領域 ID が付かないため、直接の変数参照と同じ検査を完全には適用できない。
既知の間接呼び出し候補は required に含められるが、候補全部の和では排他領域まで要求する可能性がある。
入口で実際に選ばれた callback の必要集合を照合する場合は、コードアドレス／farfn のバンクとアドレスに
対応する別のメタデータ表や、登録時に決まるハンドラ記述子が必要。fn/farfn 自体の既存表現は変えない案。
asm や生ポインタだけのアクセスは uses/requires の明示宣言や assert_active(group) 等が必要。
不明な候補を「必要領域なし」と扱わない。
デバッグ時の active 検査だけでは、同じ領域を再 activate した後の古いポインタを区別できない。
完全な stale pointer 検出をうたうなら世代番号等が別途必要であり、初期案には含めない。

### IRQ/NMI・切替処理

割り込みから参照する領域は、割り込みが走り得る全期間について保持が必要。
旧領域の finish が終わる前に新領域の init が共有メモリを上書きしてはいけない。
新領域を公開する前に初期化し、旧コールバックを解除してから領域を再利用するなどの切替プロトコルが必要。
init/finish 中の一時的な共存も配置の競合に含める。遷移引数は旧領域を壊す前に常駐領域へ退避する。
NES の NMI は SEI で止まらないので、単に割り込み禁止で囲む設計では不十分。

## 8. 現行 fcc と alias の関係

現行 `internal/frames/frames.go` は呼び出し関係に基づくフレームの静的配置を持つ。
同じ考え方を使えるが、activation の競合は関数の到達関係からは決まらないため、
解析グラフと記憶領域のモデルを別に持つ必要がある。初期段階ではフレーム用プールとも分離する。
領域とフレームを重ねる高度な配置は、activation が return 後も存続する点を扱う追加解析が必要。

alias は「手動で確保した同じバイト列に別の型を付ける」機能。
activation は「個別に宣言した変数群の寿命・共存関係から、共有する配置を決める」機能。
後者なら利用者が最大32バイトなどの共有バッファを手で見積もる必要がなくなる。
alias を activation 領域へ適用する場合は、元領域の active 条件も引き継ぐ。
両機能は共存でき、alias の設計・実装を activation 全体の導入待ちにする必要はない。

## 9. 次の相談点

active の正しさは実行時検証を前提とする。推奨する段階は、(1) 名前付き変数群と共存契約、
(2) 明示切替の実行時検査・配置レポート、(3) コールグラフによる必要集合と処理入口の実行時検査。
静的効果型や一般的なポインタ寿命解析は導入の前提にしない。
次の相談点は、共存契約の表記と、処理中の切替を予約に限定するか。
宣言から外れた組み合わせで起動しようとした場合は、共有メモリを書き換える前に停止する。
実行時の観測履歴だけから安全な静的配置を決めることはできないので、共存契約の静的な指定は残る。

検討例として、メニュー表示中に world 全体を保持するのか、world の永続状態と一時作業領域を分割して
後者だけ解放するのかを具体化すると、グループの粒度と切替 API を決めやすい。

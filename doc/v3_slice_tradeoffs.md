# FC3: slice の長さ・ABI・sentinel・移行の検討

記録: 2026-09-20。[設計案](v3_slices_vector.md) と [API 利用例](v3_slices_api_examples.md) の補足。
**将来の `#fc 3` のアイデア。未実装・未確定。今すぐ言語機能や migrate を実装する指示ではない。**
現行ソースを使った測定は既存の struct の比較であり、FC3 の実装ではない。

## 1. 長さを 8 / 16 ビットに分ける場合

以下の Slice8 / Slice16 は説明用の名前で、文法案ではない。ポインタは 16 ビットを想定する。

| 項目 | Slice8 | Slice16 |
|---|---|---|
| 構造 | ptr 2 B + len 1 B | ptr 2 B + len 2 B |
| 記述子サイズ | 3 B | 4 B |
| 長さの表現範囲 | 0〜255 | 0〜65535（実際の領域・アドレス範囲による制約は別） |
| 空と 256 要素 | 同時には表せない | 普通に表せる |
| 64 個の記述子の合計 | 192 B | 256 B |

データ本体の大きさは同じ。要素を所有する vector は ptr を持たず、ヘッダの差だけなら 1 B。
256 要素を保持できる vector の長さには、空を含む 257 状態が必要。
「0 は 256」を採用すると空の表現を別に用意することになり、一般の slice の規則が複雑になる。

型を二種類にするコストは構文を一つ足すだけでは済まない。

- Slice8 → Slice16 は上位バイトを 0 にしてビューを作る。要素コピーは不要。
- Slice16 → Slice8 は長さが 255 以下と証明するか、動的検査が必要。256 は入らない。
- 引数・戻り値・struct フィールド・配列要素のレイアウトが変わる。`*Slice8` と `*Slice16` は互換にできない。
- slice の配列をまとめて変換する場合は記述子ごとの変換が必要。ポインタの付け替えだけでは済まない。
- 利用者ジェネリクスを導入しないなら、通常のライブラリは Slice16 に統一して入口で変換するか、
  二種類の関数を書くことになる。入口で常に広げるなら、引数コピーを小さくする利点は失われる。
- const / mutable と組み合わせると、要素型ごとに基本の二形態から四形態へ増える。
  さらに通常 / sentinel も全て組み合わせるなら八形態となる。記述子に実行時タグが必要という意味ではない。

現時点の推奨は、一般 API の slice は 16 ビット長を基本とすること。
小さいビューを大量保存する用途が見つかれば Slice8 を明示的な追加候補にする。
固定容量 vector の内部ヘッダだけを容量に応じて縮め、slice 化するときに広げる案もある。
この場合も vector のレイアウトと `.len` の公開型は別途決める必要がある。
熱い処理だけを `ptr + uint8` の専用 API にする選択肢は、言語全体を二系統にしなくても取れる。

## 2. 現行 ABI での引数コピーの試算と実測

2026-09-20 の working copy を使い、FC2 の `struct {ptr:*uint8; len:uint8/uint16;}` を比較した。
最適化は O2、emu で測定。引数用 global は volatile、通常の関数は noinline。
関数は `s.ptr[0] + (s.len as uint8)` を返す。data[0] = 42、len = 64 とし、両版とも 106 を返すことを確認した。
引数二つのケースは対応する値を二つ足し、両版とも 212 を返す。
長さの上位バイトを使う演算の差を避け、主に受け渡しの差を見る実験である。

### コピーそのものの費用

生成 asm の 1 バイトごとの load/store に基づく。JSR/RTS、関数本体、戻り値処理は含まない。

| コピー元 → 引数スロット | 3 B のコピー | 4 B のコピー | 差 | 追加コード量 |
|---|---:|---:|---:|---:|
| 通常 RAM → ZP | 21 cycles | 28 cycles | +7 | +5 B |
| ZP → ZP | 18 cycles | 24 cycles | +6 | +4 B |
| 通常 RAM → 通常 RAM | 24 cycles | 32 cycles | +8 | +6 B |

例えば通常 RAM → ZP は追加の `lda abs` と `sta zp` で +7 cycles。
8 → 16 ビットへ広げる場合の上位 0 を ZP に作る部分だけなら、`lda #0; sta zp` の 5 cycles。
これは通常の load/store を使った場合の値で、定数化・コピー除去後も必ず発生する費用ではない。

### 呼び出しを含む測定値

100 回の呼び出しをソース上で展開し、ループ制御の影響を除いた。
下表は bench 区間全体の値で、各列には共通の計測境界 6 cycles が含まれる。
「1 回の差」は両版の差を 100 で割ったもの。将来の slice 専用 ABI の性能を保証する値ではない。

| ケース | len8 / 100 回 | len16 / 100 回 | 1 回の差 |
|---|---:|---:|---:|
| global → ZP 引数、slice 相当一つ | 5206 | 5906 | +7 cycles |
| global → RAM 引数（zeropage:false） | 7106 | 7906 | +8 cycles |
| stack ABI | 10306 | 11106 | +8 cycles |
| main → forward → consume と二段渡す | 8806 | 10106 | +13 cycles |
| slice 相当を二つ渡す | 9106 | 10506 | +14 cycles |
| ptr と len を別引数にする | 5206 | 5906 | +7 cycles |
| struct 自体へのポインタを渡す | 8906 | 9906 | +10 cycles |

通常の一引数では呼び出し全体が約 52 → 59 cycles。100 回なら 700 cycles 増える。
一方、長い文字列のコピー本体や描画を含むゲーム全体の速度比にはそのまま換算できない。
二段渡しは global → ZP の +7 と ZP → ZP の +6 が重なる。

現行 ABI では 3 / 4 B の struct 全体を A レジスタ一つには渡さない。
ptr / len を分けると len8 は A に載る場合があるが、この実験では受け側で保存するため総費用は同じだった。
参照渡しもこの小さな例では速くならなかった。間接参照が増え、len16 版では uint8 へ cast する前に
不要な上位バイトまで読むコードが残り、+10 cycles になった。参照渡しの普遍的な費用ではない。

戻り値が struct の identity 関数も比較すると、100 回で 10306 → 12306 cycles（+20 / 回）。
引数に加え、結果の一時領域と代入先へのコピーも増える。
inline の比較は 5306 → 6106 cycles（+8 / 回）で、現状は inline 指定だけで記述子コピーが全て消えるわけではない。
この二つでは、展開した 100 箇所の一時領域のため静的 RAM が 302 → 402 B となった。
これは実験のコード形状と現在の一時領域割り付けの影響であり、一回の slice 呼び出しに 100 B 余分に必要という意味ではない。
将来は直接構築・結果先指定・不要な高位バイトの除去も検討できるが、ここでは最適化を実装しない。

比較に用いた最小ソースの形は次のとおり。len を uint16 にした版と比較し、指定行を 100 個並べる。
他ケースは consume を forward で包む、引数を二つにする、ABI オプションを替えるなどの差分である。
実験用ソース・ビルド出力は OS の一時ディレクトリに作成し、リポジトリの処理系やゲームは変更していない。

```fc
#fc 2
use * from stdio;
struct Slice { ptr:*uint8; len:uint8; }
var data:[256]uint8;
var g:Slice options(volatile: true);
var sink:uint8 options(volatile: true);
function consume(s:Slice):uint8 options(noinline: true) {
    return s.ptr[0] + (s.len as uint8);
}
function main():void {
    data[0] = 42; g.ptr = data; g.len = 64;
    bench_start();
    sink = consume(g); // 実験ではこの行を 100 回展開
    bench_end();
    print_int16(sink); exit(0);
}
```

実装の参照先: [引数のレジスタ割り当て](../internal/frames/frames.go)、
[引数のバイト単位コピー](../internal/codegen/llc.go)。バンク切替込みの実ゲームの計測は行っていない。

## 3. sentinel 終端の調査

### Zig での意味

Zig の `[:0]const u8` は実行時の長さを持ち、その位置の要素が 0 であることも保証する。
終端は長さに含まず、途中に 0 がないことまでは保証しない。
`[N:0]u8` は同様に位置 N に終端を持つ配列。
`data[start..end :0]` は終端を新しく書く操作ではなく、その位置の値を検証する。
出典: [Zig: Sentinel-Terminated Slices](https://ziglang.org/documentation/master/#Sentinel-Terminated-Slices)、
[Sentinel-Terminated Arrays](https://ziglang.org/documentation/master/#Sentinel-Terminated-Arrays)（2026-09-20 閲覧）。

### castle では使うか

**既存 API との接続には使い道がある。全てのゲーム用バッファを sentinel にする必要はない。**
これは次の実ソースからの判断である（FC の examples 内コピーではなく `C:\Work\castle`）。

| 実ソース | 現在の処理 | slice / sentinel での接続案 |
|---|---|---|
| `src/text.fc` の `_print` | 0 を見つけるまでゲーム文字コードを読む | 旧関数へは終端保証付き、新関数へは長さ付き |
| `src/menu.fc` の `text_print` / `text_print_width` | 同じく 0 で終了 | メニュー文言のリテラルや組み立て結果の境界で有用 |
| `src/common.fc` の `heap_strcpy` | strlen → len + 1 確保 → strcpy | 既知の長さを使えば strlen を省ける。旧形式を保持するなら終端もコピー |
| `src/text.fc` の `screen_print_str` | strlen / strcpy で作業領域へコピー | 長さ付き入力なら事前走査を省ける。作業コピー自体の要否は別 |
| `src/event.fc` のアイテム取得文 | 文字列のコピー・連結 | 途中は ByteBuffer、旧表示 API に渡す最後に 0 を付ける |
| `src/fs.fc` のバイナリ読み出し、PPU データ | データとサイズの管理 | 通常の slice。0 をデータとして扱い、終端規則は付けない |

文字変換は [internal/sema/builtins.go](../internal/sema/builtins.go) の `textmap` が変換後のコード列に 0 を追加している。
したがって `_T(...)` も終端保証の供給元にできる。
その長さは変換後のコード数であり、入力の UTF-8 バイト数や画面の文字幅ではない。
castle の `_print` は改行・濁点などを解釈するため、コード数と描画タイル数も同一視しない。
FS のファイルサイズには終端が含まれる場合があるが、バイナリ FS 自体は文字列形式を保証しない。
生成器とテキスト用読み出しラッパで契約を持たせる。

### FC3 への小さな導入案

以下は調査を踏まえた FC 向け提案であり、Zig の全機能を取り込む提案ではない。

1. 通常の API は `[]const uint8` を基本にする。長さで処理でき、0 を含むバイナリにも使える。
2. 終端を要求する境界用に `[:0]const uint8` を候補にする。まず読み取り専用のバイト文字列を主な対象とする。
3. sentinel の値は型情報として持たせ、実行時の記述子は通常の slice と同じ ptr + len にする。
   16 ビット長なら 4 B のまま。必要なのはデータ側の終端 1 B で、引数コピーには追加費用を持ち込まない。
4. 任意の型・任意の sentinel 値・sentinel 専用ポインタ・vector 全操作での終端維持は初期案の必須項目にしない。
   型を追加せず、ライブラリの `to_z` / `finish_z` の契約だけに留める案も比較対象に残す。

```fc
// 全て FC3 の構文 / API 案
var z:[:0]const uint8 = "hoge"; // len=4、z.ptr[4]=0
var s:[]const uint8 = z;        // 終端保証を落としたビュー、len=4
var head = s[..2];             // "ho"。直後は 'g' なので終端保証なし
```

通常 slice → sentinel slice は無条件には変換できない。
`s.ptr[s.len]` は通常 slice の範囲外なので、そこを勝手に検査するのも不可。
終端を含む元領域と位置が分かる checked な構築、既知のリテラル、明示的なコピーなどを入口にする。
終端保証付き slice → 通常 slice は保証を落とすだけなので要素コピー不要。
末尾まで取る部分範囲は保証を引き継げる候補だが、途中で切る範囲は通常 slice にするか別途検証する。
そのためだけに元文字列の途中を 0 に書き換えてはならない。

### 連結と既存 API への橋渡し

```fc
// API 案。capacity は終端用の 1 B も含む
var storage:[64]uint8;
var b = buffer.init(storage[..]);
buffer.append(&b, str.from_z("HP: ")); // 容量不足なら停止する通常版
str.append_uint(&b, hp);
var z = buffer.finish_z(&b);           // used の位置に 0、返す len は used
// ここでだけ、要素型を合わせた旧 API のラッパに z を渡す
```

`finish_z` は `used < storage.len` を確認し、終端を書いて保証付きビューを返す案。
通常版は容量不足で停止し、必要なら `try_finish_z` を用意する。
全容量をデータで埋めた後では終端を追加できないため、文字列用には 1 B を予約する。
既存の通常 slice から作るなら `to_z(dst, src)` でコピーと終端付加を行う。
既に終端保証があるリテラル・textmap 結果なら、このコピーは不要にできる。
ただし現行 API の `*int` と仮案の `*const uint8` の要素型・const の接続も移行時に整理する。

`finish_z` 後の append は古い終端を上書きするため、古い z の保証を失わせる。
借用検査を導入しない方針なら、「利用が終わるまでバッファを変更しない」を利用者の責任として明記する。
sentinel は寿命、ROM バンクの選択、他の参照からの書き換えまでは解決しない。

また、末尾が 0 でも途中に 0 があれば、slice API と従来の strlen / 表示 API で見える長さは違う。
全体を表示したいテキスト資産では、生成時に途中の 0 を禁止するなどの契約が別に必要。
`from_z` は最初の 0 までの範囲を返すので、この問題の意味は明確だが走査が発生する。
リテラル / textmap の既知の長さを使う経路とは使い分ける。

### 長さ推論配列との整合性

現行仕様を維持した `[?]uint8 = "hoge"` は終端込みの普通の `[5]uint8` という案がある。
その全体 slice の長さは 5。一方、文字列として直接作る sentinel slice は長さ 4 という区別が可能。
Zig 風の sentinel 配列そのものを導入するなら、論理長と格納要素数が異なる別の規則が必要になる。
どちらを採用するかは未決で、単なる記法移行に紛れて既存の `sizeof` やコピー長を変えない。
256 バイトの本文には終端込みで 257 B が必要。sentinel を付けても len8 の 256 問題は解決しない。

## 4. migrate の現状と将来の移行

**現行の migrate は残っていない。** [言語リファレンス](language_reference.md) と
[roadmap](roadmap.md) に、2026-09-19 に v1 処理系と `fcc migrate` を削除した記録がある。
[CLI](../cmd/fcc/main.go) に migrate コマンドはなく、`internal/migrate` も存在しない。
[lexer](../internal/syntax/lexer.go) の現行バージョンは 2。
v1 入力への診断に出る migrate は **fc 0.1 系の過去のツール**を指し、現在使えるコマンドではない。

今回の案を採用するときは、将来の v2 → v3 移行手段を別途設計する必要がある。
`#fc 3` は今は有効な言語バージョンではない。本書への記録だけでサポート追加やデフォルト変更は行わない。

| 現行コード | 将来の移行候補 |
|---|---|
| 初期値から長さを推論する `[]T` | 意味を保って `[?]T` に書き換える |
| 長さ省略の外部領域宣言など | 宣言用途ごとに判定。`[?]T` へ機械的に一括置換しない |
| `ptr + len` の API | 呼び出し先の契約も含めて slice 化。文法だけの migrate では決められない |
| 文字列 / textmap の配列と sizeof | 終端込みの格納長と論理長を区別し、既存の意味を維持する |
| 終端依存 API の引数 | 通常 slice の `.ptr` へ一括置換せず、終端保証または明示変換を使う |

文法の移行と、新しい API を使うための意味の変更は分けて確認する。
曖昧なケースを診断して残し、移行後のコンパイルとゲームの挙動を確認する方式を想定する。
具体的な migrate のコマンド名・オプション・自動変換範囲は未決。

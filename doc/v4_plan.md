# FC V4 検討メモ

作成: 2026-09-28。

**2026-09-28 決定: 整数の規則の意味の変更から fc 4（`#fc 4`）にする。** 主要なプロジェクト（castle・miku・darius）と fclib は
fc 3 に移行済みなので、fc 2 / fc 3 の意味は変えず、新しい規則は `#fc 4` のモジュールだけに入れる。版はモジュールごとなので、
fc 3 のモジュール（fclib など）を fc 4 のモジュールから使える。規則の中身（§1.3 の A〜F）は未決。

同じ版で入れるもの（2026-09-28 決定）: 互換性のために fc 3 で後回しにした 2 件（名前付きの文字列定数の終端の 0、`fastcall` の廃止。
§2）と、slice を使った標準ライブラリの大幅な拡充（§3）。どれも fc 3 からの移行（migrate）を合わせて用意する。

fc 3 までの検討は [v3_plan.md](v3_plan.md)（整数は §10.2）。

## 0. v4 にすると要るもの

- `#fc 4` の受け付け（今は `invalid version pragma`。`syntax.Version4` / `LatestVersion`）と、sema の規則の切り替え
  （式を書いたモジュールの版で選ぶ。`h.version()` の仕組みがある）
- **fc 3 → fc 4 の migrate は ROM を変えない（2026-09-28）。** 整数の規則の変更は書き方を変えずに意味を変えるので、今の migrate
  （構文木の位置によるトークンの置き換え。fc 2 → 3）では書けず、型の情報が要る。sema が fc 3 のソースをコンパイルして
  「v4 で意味が変わる式」を位置つきで報告し（構文木に `Pos` / `End` がある）、migrate がそこに `as` を足す
  （`var d:u16 = a + b` → `var d:u16 = (a + b) as u8`）。確かめ方は fc 2 → 3 と同じく、examples の castle・miku と
  test / bench を v4 に migrate して、今の ROM・出力とバイト単位で比べる。fc 2 のソースは fc 2 → 3 → 4 とつなぐ
  （ROM を変えない形にすると、移行の途中でも今の ROM の golden がそのまま検査に使える）
- v4 では「`as` が無いとエラー」にする規則も取れる（既存のコードは migrate が `as` を足して移す）。ただし厳しくするほど
  移した後のコードに `as` が増えるので、案の代価は「migrate が足す `as` の数」で数える
- **移行は 2 段に分ける**: ROM を変えずに移せるもの（整数の規則、文字列定数の長さ）と、生成コードが変わるもの（`fastcall` の
  廃止、fclib の新しい API への書き換え）。前者は ROM の golden とのバイト単位の一致で、後者は動作（test の出力、castle の
  自動プレイ `TestPlayCastle` / `TestMesenPlayCastle`、fuzz）で確かめる。前者を先に済ませて ROM の一致を確かめてから後者に進む

## 1. 整数の規則

### 1.1 今の規則（fc 2 / fc 3。2026-09-28 の main）

幅については「int が 8 ビットの C」とほぼ同じ（C の int への拡張と普通の算術変換を、int = 8 ビットで読んだもの）。
違うのは符号とリテラル。

| 項目 | 今の動き | 例 |
|---|---|---|
| 演算の型 | 大きいほう、同じ大きさなら符号付き（`types.Compatible`） | `u8 + i8` → i8、`i8 + u16` → u16（i8 は符号拡張）、`u16 + i16` → i16 |
| シフトの結果の型 | 左辺と右辺の互換型（右辺の型でも変わる） | `x << n`（x:u8 = 3、n:u16 = 7）は u16 の 384、`a << s`（a:u8 = 200、s:i8 = 1）は i8 の -112 |
| 代入先の型 | 式の中に伝わらない | `var d:u16 = a + 100`（a:u8 = 200）は 44 |
| リテラル | 型のない定数は相手の型に合わせる（2026-09-27）。収まらなければ演算は切り詰め、比較・case・`@min` などはエラー。定数のほうが大きい型なら広げる | `x + -1`（x:u8）は `x + 255`、`s < 200`（s:i8）はエラー、`x * 300` は u16 |
| 型を書かない配列リテラル | 要素の型の互換型 | `[128, -1]` は i8 で 128 が -128、`[11902, -3]` は u16 |
| 暗黙の縮小 | 代入・初期化・引数・戻り値で黙って下位バイト | `var c:u8 = 300` は 44、`var y:i8 = 200` は -56 |
| const の型の注釈 | 値の型との互換型（範囲外なら注釈が負ける） | `const B:u8 = 300` は u16 の 300、`const F:u8 = -1` は i8 |
| 単項マイナス | オペランドの型のまま | `-b`（b:u8 = 5）を i16 に入れると 251 |
| 除算・剰余 | 床除算（Python と同じ）。符号付きかは結果の型 | `a / b`（a:u8 = 200、b:i8 = 2）は i8 の -28 |
| 比較 | 必ず真・偽になる比較は警告（2026-09-27）。bool 同士の `==` は真理値（2026-09-27）。16 ビットを超える定数との比較は畳む | `x + dx > 100`（x:u8 = 200、dx:i8 = -1）は i8 の -57 で偽 |

例は 2026-09-28 に `fcc run` で確かめた。language_reference §2 の「サイズが合わない代入はエラー」は実装と食い違ったまま。
比較・除算・右シフトの幅と符号は IR の命令が持つ（`Op.Width` / `Op.Sign`。2026-09-28。ir/sign.go）ので、型から意味を決めるのは
sema と `ir.InferWidthSign` だけ。規則を変えても最適化・codegen は変えなくてよい。

### 1.3 決めること

#### A. 外側から広げるか（計算の幅）

**決定（2026-09-28）: A1。** migrate は、計算の幅が変わる所（castle 19 か所。§1.5）に `as u8` を足して ROM を変えない。

✅ 実装 2026-09-28（`sema/widen.go`）: sema は式を下から IR にするので、8 ビットの算術の結果が 16 ビットの値と出会う所
（`makeCompatible` と代入のような変換 `convert`）で、その結果を作った部分木の命令をその場で 16 ビットの計算に直す（結果の型を
広げ、符号付きの葉には符号拡張を前に足し、型のない定数は元の値から作り直す。区切りは算術以外の命令・`as`・比較・シフト量・
組み込みの `@min` など）。計算の符号は今の結果の型のまま（C0）。fc 3 のモジュールでは広げず `(式) as T` を報告する。castle の
書き換えは `(x * 2) as u8`、`(64 * t.cur_y) as u8`（`text.fc` の危ない所）、`mem.zero(buf, (width * height * 2) as u8)` など
（外せば fc 4 では正しく 16 ビットで計算される）。codegen の単項マイナスが結果より狭い入力の上のバイトで借りを伝えていなかった
のを直した（fc 3 では入力と結果が同じ大きさだった）。
型付きの定数どうしの演算（✅ 2026-09-29）: sema の畳み込みは結果の型で折り返すので、そのままでは広がらない
（`const A:u8 = 200; var d:u16 = A + 100`）。折り返し・オペランドの読み替え（型のない定数の切り詰め、`(253 as u8) | (127 as i8)`
の 253 → -3）で値が変わった畳み込みの結果に元の式の印（taint）を付け、広い型と出会ったら（定数の畳み込みの中の演算
`foldWidenArgs`、実行時の式の `widenArith`、広げる部分木の葉 `widen`）、fc 4 では元の式を `widen` と同じ手順でその幅で
畳み込み直す（`wideValue`: 演算は元の幅で畳み込んだ型の符号のまま広い幅で、区切り（`as`・比較・組み込み・名前）の中は元の値）。
広がらなければ畳み込んだ定数のままで IR は fc 3 と同じ。`as` は外からの広がりを止めるだけで、中の式にも「式の中の一番広い型」
の規則が効く（印は `as` の中でも付ける）。fc 3 のモジュールでは `(元の式) as T` を migrate に報告する。あわせて、広げた結果の
型（演算の符号のまま）と揃える先の型の符号が違うときは揃える先の型として読む（`(x / 139) >= (0 as u16)`（x:i8）が符号付きの
比較になっていた）。fc 4 の型付きの定数と変数の差分テスト `TestRandomConstFoldV4`（各式を `w = w + (式)`（w:u16）にも置く）で
見つけて直し、1000 本で通る。
プログラム全体の fc 4 版 `TestRandomProgramsV4`（✅ 2026-09-29）: 生成した fc 2 のプログラムに、fc 4 でエラーになる所（E・D）の
`as` だけを足して fc 4 にし（`MigrateOptions.Rules`。A1・F1 の fc 4 の意味がそのまま効く）、-O 0 / -O 2 / インタプリタで比べる
（A1 で広げた IR を最適化と codegen が正しく扱うか）。1000 種で食い違い 0。F1 の型の違いで E・D の書き換えだけでは直らない種は
飛ばす（本当の migrate は F1 の書き換えも当てる）。
migrate が自動で書き換えられない形: 左辺に呼び出しのある複合代入の縮小（`a[f(i)] += w`（a:[N]u8、w:u16））。文ごとの書き換え
`x = (x op y) as T` は左辺の呼び出しを 2 回評価する（sema は複合代入の左辺の呼び出しを先に 1 回だけ評価する）ので、手で一時変数に
分けるよう案内するエラーにした（`sema.CompoundCallMsg`。fuzz ではその種を飛ばして数える）

| 案 | 中身 |
|---|---|
| A0 | 今のまま（int が 8 ビットの C）。危ない形は B の警告で補う |
| A1 | 2026-09-26 に一度決めた規則: 式全体を「代入先の型」と「式の中で一番広い型」の広いほうで計算する。代入先が無く中身が全部 8 ビットなら 8 ビットのまま |

A1 の決めごと（2026-09-26 の案）:
- 1 つの式の区切り: 代入・初期化・引数・`return`・struct / 配列の要素の右辺。比較は両辺で 1 つの式
- 広がらない所: 呼び出しの中の引数（引数の型で別に決まる）、添字、シフトの右辺。`as` も区切り（`(a + b) as u8` は中を
  8 ビットで、`a as u16 + b` は明示的に広げる）
- 型のない定数は、その値の型（`0x2000` は u16）で「一番広い型」に数える。`var addr = 0x2000 + y * 64` は 16 ビットで計算する
- 注意: 式を分けると結果が変わる（`var t = a + b; var d:u16 = t;` は 44）。C の int の拡張と同じく「1 つの式の中だけ」と書く
- 良くなる例: `var d:u16 = a + b`、`score += pts * 10`（score:u16）、`ppu.put(0x2000 + y * 64, …)`、`var w:u16 = hi << 8 | lo`

材料（2026-09-26。一時的な検査で数えた）: 8 ビットの `+ - * <<` の結果が 16 ビットの値・演算に入る所は castle 18 か所、
miku・darius 0 か所。castle のほとんどは値が小さく（`x * 2`、x < 32）、危ないのは `text.fc` の `t.addr + 64 * t.cur_y`
（cur_y ≥ 4 で折り返す。窓の高さが 2 なので今は無事）。作者が避けている跡もある（`menu.fc` の `y:u16`、`en7.fc` の `y16`）。
castle はその後ソースが 30 ファイル変わったので数え直す。コスト: 16 ビットが絡む式だけ。`m as u16 + n` は 3 命令増えるだけで
最適だが、`m as u16 * n` は 16×16 の `__mul_16` を呼び（8×8→16 の `__mul_8t16` は未完成）、`((m as u16 + n) / 2) as u8` は
10 命令ほど（`clc / lda / adc / ror a` の 4 命令にできる）。A1 を入れるならこの 2 つの最適化も

#### B. 8 ビットの計算の途中で上の桁を捨てる形を警告するか

**決定（2026-09-28）: 警告にしない。** castle だけで約 190 件になり、ほとんどが意図どおりの書き方だった（§1.5）。代入先で広がらない
8 ビットの計算が 8 ビットで折り返すのは、int が 8 ビットの C と同じ定義された動きとして文書に書く。以下は決める前の案。

- 対象: 8 ビットの `+ - * <<` の結果の上の桁を後で使う形。`(x1 + x2) / 2`（200, 100 で 22）、`hp * 64 / max`、`(v * 3) >> 2`、
  `(a * b) >> 8`、`a.x + a.w > b.x`、`px + dx >= 240`
- 除外: 値の範囲（定数・`& m`・`% n` など）で収まると分かるもの。`u8 = u8 + u8` のように `+ - * << & | ^` だけで上の桁を
  使わない式（下位 8 ビットは同じ）
- 消し方: `(x1 + x2) as u8 / 2`（8 ビットのつもり）、`(x1 as u16 + x2) / 2`（広げる）。v4 では警告でなくエラーにもできる
- A1 を入れても、代入先の無い比較と、代入先が 8 ビットの式は残るので、A1 と組み合わせる前提。件数は未計測

#### C. 符号の混在

**決定（2026-09-28）: 今のまま（C0）。同じ大きさなら符号付きが勝つ**規則を踏襲する（Ruby 版の最初のコミット 2013-04-10 の
`TypeUtil.compatible_type?` からの規則。castle・miku・darius はこの上で書かれている）。理由をリファレンスに書く: ファミコンの
ゲームは u8 の座標に i8 の移動量を足す形が多く、座標に戻すだけ（`x += dx`）ならどの規則でもビットは同じで、移動量に小数部や
大きさを足して割る・比べる形（`(vy + giff) / 16`、`math.cos(angle) / speed`、`cx + dir2 <= 0`）は符号付きで解釈するのが正しい。
castle の 307 か所・miku / darius の 10 か所は書き換えなし。A1 の「一番広い型」で同じ大きさの符号が違うときも符号付き。
型を省いた変数（F5。`var n = x + dx`）も i8。残る罠（大きい座標と移動量を混ぜて代入先なしで比べる・割る）は文書に書く
（16 ビットの代入先があれば A1 で正しくなる）。以下は決める前の検討。

座標として比べるときの書き方（2026-09-28 に確かめた。x:u8 = 250、vx:i8 = -1）:
- `(x + vx) > 200` は fc 3 でもエラー（リテラルの規則。`200 does not fit in i8`）。`(x + vx) as u8 > 200` と書く（真）
- 黙って通る罠は 2 つの形だけ: 0〜127 の定数との比較（`x + vx > 100` が i8 の -7 > 100 で偽。`(x + vx) as u8 > 100` なら真）と、
  u8 の変数との比較（`x + vx > lim`（lim:u8）が符号付きの比較で偽）
- 案（未決。F6）: 同じ大きさで符号の違う値どうしの比較をエラーにして `as` で揃えてもらう（u8 の変数との比較の罠を塞ぐ）。
  castle・miku・darius・fclib で該当 0 か所（§1.5 の C の「変数どうしの比較 0」）。定数との比較は、`cx + dir2 <= 0` のように
  符号付きで比べるのが正しい書き方と型では区別できないので、文書に書くだけ

今の「同じ大きさなら符号付きが勝つ」は、調べた言語のどれとも違う。8 ビットの `+ - & | ^ <<` は符号付きでも符号なしでも結果の
ビットが同じなので、効くのは解釈の場面（比較、`/ % >>`、16 ビットへの拡張、型を省いた変数 `var y = x + dx`）だけ。

| 案 | 中身 | 近い言語 |
|---|---|---|
| C0 | 今のまま（符号付きが勝つ） | なし |
| C1 | 符号なしが勝つ | C / C++（int 以上の型どうし。`-Wsign-compare` で補う） |
| C2 | 両方を表せる型に広げる（u8 + i8 → i16） | C#（`byte + sbyte` → int、`int + uint` → long） |
| C3 | 代入先があればその型で計算する（A1 と同じ）。代入先の無い比較・`/ % >>`・型を省いた変数で符号が混ざったら警告（v4 ならエラー）して `as` を案内する | Go・Rust・Swift・Kotlin・Zig は混ぜるとエラー（Rust は `wrapping_add_signed`） |

- 変数どうしの比較は castle に残っていない
- C2 と A1 を組むと座標 + 速度が毎回 16 ビットになる（上位バイトを使わない 16 ビットの演算を 8 ビットに縮める最適化は今は無い。
  opt の splitWords は xor / and / or / シフトだけ）
- **「C に合わせる」の中身**: C の本当の規則は、int より狭い型を int（16 ビット以上）に広げてから計算するので、`u8 + i8` は int で
  正しい値になる（C2 に当たる）。符号なしが勝つのは int 以上の型どうし（16 ビットの int なら `u16 + i16` → u16。C1 に当たる）。
  今の fc の幅の説明「int が 8 ビットの C」で読むと、8 ビットどうしも符号なしが勝つ（C1）
- **計測（2026-09-28）**: 符号の混ざった演算は castle 307 か所（`u8 + i8` 192、`i8 + u8` 68、`u8 - i8` 18、`i8 * u8` 12 など。
  全部 8 ビットどうし）、miku 10、darius 10。そのうち結果を解釈するのは castle 77・miku 6・darius 6（§1.5）で、全部が
  「符号付きが勝つ」に頼って正しく動いている。残りは `x += dx` のように 8 ビットの代入先に入れるだけで、どの規則でもビットは同じ
- ROM を変えない migrate なので、どの案でも castle は壊れない。違いは、migrate が castle に足す `as` の数と、新しく書くコードの
  書きやすさ:

| 案 | migrate が castle に足す `as` | 新しく書くコード |
|---|---|---|
| C0 今のまま | 0 | 速さ + 小数部・速さ ÷ 大きさなどは今どおり。罠は、大きい符号なしの値（座標 ≥ 128）と符号付きを混ぜて代入先なしで比べる・割る形（A1 で 16 ビットの代入先がある所は正しくなる） |
| C1 符号なしが勝つ（int が 8 ビットの C） | 解釈する約 90 か所に `as i8` | `(vy + giff) / 16` が黙って符号なしの割り算になる（罠が一番よく書く形に移る） |
| C2 i16 に広げる（本当の C・C#） | 解釈する約 90 か所に `as i8`（8 ビットのまま） | 値は正しいが、混ざった結果が i16 になるので D（縮小はエラー）とぶつかる: `x += dx`（x:u8）が i16 → u8 の縮小でエラー（castle で約 230 か所）。C と同じく「混ざった結果の 8 ビットへの縮小は許す」などの例外が要る。解釈する所は 16 ビットの計算になる |
| Go・Rust 流（混ぜるとエラー） | 307 か所 | `x += dx as u8` のように毎回書く（Rust はこの用途に `wrapping_add_signed` を用意している） |

#### D. 暗黙の縮小

**決定（2026-09-28）: エラーにする**（✅ 実装 2026-09-28: `sema/convert.go` の `convert`。migrate は `c as T`）（縮小は明示の `as` で書く。Go・Rust と同じ。language_reference §2 の「サイズが合わない代入は
エラー」が本当になる）。castle で 4 か所だけで、作者は `hi = addr >> 8` のような縮小にすでに `as` を書いていた（§1.5）。migrate は
その 4 か所に `as` を足す。

- 対象は大きさが減る変換だけ（u16 / i16 → u8 / i8）。**同じ大きさで符号だけ違う変換（i8 → u8、u16 → i16）は今までどおり暗黙に
  通す**（ビットがそのまま）。`x = x + vx`（x:u8、vx:i8。右辺は i8）は通る。これもエラーにすると Go・Rust と同じになるが、
  castle の座標 + 移動量（`u8 + i8` 192 か所など）がエラーになるのでしない。定数は E の規則（値が収まらなければエラー。
  `var x:u8 = -1` はエラー）
- 決める前の案: 今のまま許してリファレンスを直す / 変数の縮小を警告する / エラー

#### E. 範囲外の定数と const の型の注釈

**決定（2026-09-28）: エラーにする**（✅ 実装 2026-09-28: `sema/convert.go` の `convert` と `checkConstRange`。組み込みの
`cos(x)` は fc 4 では `sin((x + 64) as i8)` に展開する（角度の i8 の折り返し。`cos(127)` の 191 を i8 の引数に渡すため））（Go・Rust・Zig と同じ。v3 の調査（§10.1・§10.2）で出した方向）。

- 対象: 定数（型のない定数・型付きの定数）の値が、代入先の型に収まらないとき。代入・初期化・引数・戻り値・struct / 配列の要素・
  const の型の注釈（`var c:u8 = 300`、`var y:i8 = 200`、`return -1`（戻り値 u8）、`f(256)`（引数 u8）、`const B:u8 = 300`）。
  今は黙って切り詰める（const の注釈は値の型に負ける）
- 明示の `as` は通す（`-1 as u8`、`256 as u8`、`200 as i8`。切り詰めを書いた人の意図として残す）
- 演算の中のリテラルの規則（2026-09-27。相手の型に合わせ、収まらなければ演算は切り詰め・比較はエラー）は変えない。E は
  代入のような変換の話
- migrate: 収まらない定数に `as` を足す（`return -1` → `return -1 as u8`、`ppu.put_in_lock(…, 256)` → `256 as u8`）。
  ROM は変わらない。const の型の注釈が値の型に負けていたもの（`const B:u8 = 300` は今 u16 の 300）は、注釈を値の型に直す
- 影響（§1.5）: castle 19 か所（u8 への `-1` が 16、大きさの引数への `256` など）、fclib 1 か所（`math.sign` の `return -1`）、
  test 32 か所（test_var の `const INT16:int = 65535` など。fc 2 のソースは fc 2 → 3 → 4 の migrate が直す）

  ✅ 実装 2026-09-28（`sema/convert.go` の `shiftByLeft`。シフト量は型を揃えない。定数の畳み込みも左辺の型。fc 3 の migrate は

  正しくなる）。ROM を変えない migrate はこの 19 か所に `as u8` を足す（`(x * 2) as u8`）
- **B**: 警告にすると castle だけで約 190 件で、ほとんどが意図どおりの書き方。`(speed + giff) / 16`（速さに小数部の
  ディザを足して 16 で割る固定小数点。89 件）、`(cur + 1) % n`（メニューの巡回）、`(y + 8) / 16 * 16 - 8`（マス目への丸め）、

  `% 2^k` を除いても大半は残る。**警告・エラーには向かない**
- **C**: 全部が「同じ大きさなら符号付きが勝つ」を前提にして正しく動いている。`(t + giff) / 16`（i8 の速さ + u8 のディザを

- **E**: castle の 19 か所は、u8 の戻り値・変数への `-1`（「無し」の印。16 か所）と、u8 の大きさの引数への `256`

- **F3**: `-sin_table[x - 128]`（u8 の表の値を負にして i8 で返す）、`-atan_table[…]`（角度の折り返し）など、8 ビットの

## 2. 互換性のために後回しにしたもの（2026-09-28: v4 に入れる）

- **名前付きの文字列定数を slice にすると終端の 0 が入る**（`const NM = "joe"` の `@len(NM)` と `f(NM)`（`[]const u8`）が 4、
  `f("joe")` は 3。描画ルーチンが 0 まで描く。roadmap「互換性のため今はこのまま、後で直す候補」）。v4 ではリテラルと同じく
  終端を含めない長さにする（データの終端の 0 は残す）。migrate は長さを見る所（`@len`、slice への変換）を sema で見つけて、
  今の長さを保つ書き方に直す（ROM を変えない側。書き方は実装のときに決める）。
  ✅ 実装 2026-09-29（`sema/strconst.go`）: 長さを初期値の文字列から決めた名前付きの配列定数（型を書かない・`[?]u8`・ポインタ型の
  宣言。`ir.Value.StrConst`）は、fc 4 のモジュールから見ると `@len`・slice への変換・for-each・`a[lo..]` の終わりに終端の 0 を
  含めない（リテラルと同じ `strLen`。`@sizeof` と添字はデータのまま）。長さを書いた配列（`[4]u8 = "xyz"`）は今のまま。fc 3 → 4 の
  migrate は、fc 3 のモジュールで長さを見る所があれば、使う所ではなく宣言を長さつき（`const NM = "joe"` → `const NM:[4]u8 = "joe"`）
  に書き換える（使う所の IR が変わらない）。castle・miku・darius には名前付きの文字列定数が無く、test の test_var・test_basic・
  test_lzw の宣言が書き換わる
- **`fastcall` の廃止**（v3_plan.md §5 C「FC3 の最初の版では残す。廃止は後の版で別に決める」。ユーザー補足「fastcall は今後
  不要」）。生成コードが変わるので、移行の後の段（§0）。asm で書いた関数（fclib の mem.asm・stdio.asm、castle の asm）との
  呼び出し規約を指定する手段（`@(abi: …)` など）を別に用意するかは決めるときに
  **決定（2026-09-29）: fc 4 から fastcall を完全になくす。** 本体のある関数の `@(fastcall)` は migrate が消す（コンパイラが呼び出し
  規約を決める。castle の測る場面のサイクル数と bench のサイクル数・大きさは外しても同じだった: どちらもゼロページに `sta` で引数を
  書くため）。`fastcall fn` 型は属性からだけ生まれる（型としては書けない）ので fc 4 のモジュールでは作れない（fc 3 のモジュールの fastcall の関数は呼べる）。fclib の asm の fastcall の extern は、引数の多いもの（mem.set / zero / copy /
  compare、nes の stdio.ppu_put）は fc に書き直すか asm のまま別の規約に、0〜1 個のもの（lzw.read_bit / read_vln / read_vln16、
  nes の stdio.print）は cc65 の規約（A / X）に。利用者の asm の fastcall の extern は migrate のエラーで案内する（castle・miku・
  darius には無い）。fc 3 のモジュールは今までどおり使える。**fclib はこの作業で fc 4 に移す（2026-09-29 決定）。**
  計測（2026-09-29、1000 バイト、呼び出しを含む）: fc で書いた copy は asm の +0.8%、set は +34%（ループの中で変わらない値
  `c` を毎回読み直す。A に置いたままにする最適化で縮む見込み）。
  **asm の関数の呼び出し規約（2026-09-29 決定）:** fastcall の代わりに、asm の関数も fc の関数と同じ静的フレームで受け取る規約
  `@(abi: "frame")` を足す（`stack` と `static` は紛らわしいので名前は `frame`）。
  - `abi: "frame"`: フレーム `F_sym` に戻り値（オフセット 0、型の大きさ）→ 引数（宣言の順に詰める。下位バイトが先）。**引数と
    戻り値にレジスタを使わない**（fc の関数にかける A / Y で渡す最適化はかけない）。A / X / Y は壊してよい。呼ぶ側は `F_sym+k` に
    書いて `jsr`、戻り値は `F_sym+0〜` から読む。フレームは fc の関数と同じく静的フレームの領域に置く（深い順にゼロページ、
    同時に動かない関数と重ねる）。asm には `F_sym` と引数ごとの位置のシンボルを出す
  - `scratch: N`: 戻り値と引数の後ろに asm が自由に使う N バイトを足す（任意）
  - 制約（最初の版）: 葉（ほかの関数を呼ばない）、再入しない、アドレスを取れない。割り込みから届く関数の扱いは fc の関数と同じ
  - 本体のある関数にも書ける（asm から呼ぶ関数の呼び方を固定する）
  - fc 4 の extern は規約（`abi: "frame"` / `"stack"` / `"cc65"`）を書くのが必須で、書かなければエラー。本体のある関数は書かなければ
    コンパイラが決める（今の static / entry / stack とレジスタ渡しの最適化）
  - fc 3 は今のまま（extern の既定は stack、fastcall も使える）。migrate: 規約を書かない extern に `@(abi: "stack")` を足す、本体のある
    関数の fastcall を消す、fastcall の extern はエラー（asm を直す必要がある）
  - `FC_FASTCALL_REG` は fc 3 の fastcall と cc65 の規約の受け渡しのために残す（fc 3 をやめるときに外せる）

  ✅ 実装 2026-09-29（仕様は language_reference.md §4.2・§4.5）:
  - sema（`sema/abi.go` の `checkABI`）: abi の値、`scratch` は abi "frame" の extern だけ、"frame" と fastcall の併用はエラー。fc 4 では
    fastcall と、abi を書かない extern がエラー
  - frames: `ir.Lambda.FrameABI` / `Scratch`。abi "frame" の extern は呼び出しグラフの葉としてフレームを配置する（大きさは戻り値 + 引数 +
    scratch）。本体のある abi "frame" の関数は asm から参照されても Entry にせず、レジスタ渡しもしない。`_frames.inc` に
    `F_sym__<引数名>` と `F_sym__scratch`、fc から呼ばれない extern には仮の `F_sym = FC_SZP`（asm のファイルは丸ごと入るので、
    参照が未定義だとアセンブルできない）。asm の extern のフレームはゼロページに要る（入らなければエラー、`zeropage: false` で RAM）
  - 制約「葉」は検査にした: include した asm のファイルが参照する関数（asm から呼ばれうる関数）は、呼び出し元がグラフに見えないので
    フレームをどの関数とも重ねない（`frames.Graph.hidden`。割り込みの木と同じ扱い。これは fastcall 以前からの Entry にもあった穴で、
    asm から呼ばれる Entry の関数のフレームが呼ぶ側の fc の関数と重なりえた）。インラインアセンブラの参照は、それを含む関数からの
    呼び出しの辺にする。検出できないのは同じモジュールの asm の関数どうしの呼び出し（extern への自分のモジュールの asm の参照は

  - asm のシンボルの検出（`ir.AsmSymbols`。sema と frames で別々だった正規表現をまとめた）を語の境界つきにした。以前は castle の

  - migrate（`migrate/v4.go` の `abiRules`）: 本体のある関数の fastcall を消す、abi を書かない extern に `abi: "stack"` を足す、
    fastcall の extern はエラー

    fc に書き直した。rle / inflate は `abi: "stack"`
  - 確かめたこと: stdout の golden・TestPlayCastle / TestSmoke* が同じ動作、bench のサイクル数と大きさは同じ。IR / asm / ROM の golden
    は更新した。`TestRandomMigrate` は fc 2 のプログラムが fastcall を使うと ROM ではなく実行結果（-O 0 / -O 2）で比べる

## 3. 標準ライブラリの拡充（2026-09-28 方針）

slice が入ったので、v4 で fclib を大幅に拡充する。中身は未決。

今の fclib（fc 3、364 行）:

| モジュール | API | 形 |
|---|---|---|
| mem | set / zero / copy / compare、strlen / strcpy | ポインタ + 長さ（u16）、終端 0 の文字列 |
| stdio（emu / nes） | print / puts（ポインタ）、print_slice、print_int16 / print_sint16、exit、NES の ppu_put(addr, ptr, size) / wait_vsync | 文字列はポインタが主、slice は print_slice だけ |
| math | sin / atan（i8 の表）、rand、sign、abs | |
| rle / lzw / inflate | unpack(dest, src) | 出力の大きさを渡さない |
| unittest | assert_true / assert_equal | メッセージはポインタ |
| nes | nes.fc（レジスタ）、pad（update とボタンの定数） | |

これまでの検討: [v3_slices_api_examples.md](v3_slices_api_examples.md)（書き込みバッファ、長さ付き文字列、固定容量 vector、
数値 ID の readonly FS、PPU 転送、castle のメッセージの組み立て）、[v3_slice_tradeoffs.md](v3_slice_tradeoffs.md) §4
（「文法の移行と、新しい API を使うための意味の変更は分けて確認する」。この節の migrate の現状の記述は古い）、roadmap の
「fclib と NES の開発の流れ」（slice 版の print / mem、nes/ppu.fc、マッパーのライブラリ、math の直し、NES の stdio）。

移行の考え方（案）:

- 言語の移行（ROM を変えない）の間は、移したコードが今の API をそのまま呼べるようにする。候補は、fc 3 の fclib を
  fc 3 のモジュールとして残す（版はモジュールごとなので fc 4 から呼べる）か、新しい fclib に今の API を互換の関数として残して
  fc 4 では非推奨の警告にするか
- API の移行は migrate の別の規則で、生成コードが変わるので動作で確かめる（§0 の後の段）。ポインタ + 長さの意味が呼び出し側で
  決まる所など、機械的に書き換えられないものは診断を出して手で直す
- 新しい API が今と同じモジュール名・関数名を使うなら、fc 3 のモジュールと fc 4 のモジュールで `use mem;` が指すものを版で
  引き分けるか、別の名前にするかを決める

決めること: 拡充する範囲（文字列・バッファ・コンテナ・PPU・マッパー・数学・圧縮など）、今の API の扱い（残す / 置き換える）、
版による引き分けの要否。asm の規約は `abi: "frame"` に決まり、今の fclib は fc 4 に移した（§2）。

## 4. 進め方（案）

1. `#fc 4` の受け付けと、型を見る migrate の土台（sema が位置つきで書き換えを報告する仕組み） ✅ 2026-09-28: `syntax.Version4`
   （`LatestVersion`）、`sema.Rewrite` / `rewriteAs`（fc 3 のモジュールで fc 4 の意味と違う所を集める）・`Program.Overlay`、
   `migrate.ToV4`、`driver.Compiler.Migrate`（fc 2 → 3 → 4。`fcc migrate` はこれ）。`TestMigrateExamples`（castle / miku を
   fc 4 に移して ROM の golden と一致）、`TestMigrateGoldenPrograms` / `TestMigrateBench` は fc 4 まで移す。この時点の fc 4 は
   fc 3 と同じ意味。migrate はソースが fc 3 としてコンパイルできることが要る（以前の構文だけの書き換えは、コンパイルの
   エラーがあっても書き換えられた）
2. 整数の規則（§1）と文字列定数の長さ（§2）: ROM を変えない移行。examples・test・bench の golden と一致することを確かめる
   （E・D・A1・F1 ✅ 2026-09-28。castle には u8 への `-1` を `-1 as u8` に、縮小に `as u8` を、大きさの引数の `256` を
   `256 as u8` に、計算の幅が変わる所に `(x * 2) as u8` などを足す書き換えが入り、ROM は同じ。テストは internal/driver/v4_test.go。
   残りは文字列定数の長さ、A1 の型付きの定数の畳み込み、fc 4 のランダムテスト）。
   fuzz: `TestRandomMigrate` は生成した fc 2 のプログラムを fc 4 まで移して ROM が元のままと同じかを見る（2026-09-28。40 種の
   うち 31 種で書き換えが入る。1000 種で通る）。これで見つけて直したもの: 複合代入 `x op= e` の縮小は文ごと
   `x = (x op e) as T` に書き換える（脱糖した式に位置が無い）、同じ型への `as` はどの版も包まない（書き換えで足した `(式) as T`
   と元のソースの `as` で IR がずれない。ROM・golden は変わらなかった）、定数の畳み込みのシフトにも F1 の書き換え
   （`32 << (6 as u8)` は fc 3 では u8 の 0、fc 4 では 2048）
3. `fastcall` の廃止（§2）と fclib の拡充・API の移行（§3）: 生成コードが変わる。動作で確かめる
   （`fastcall` の廃止と fclib の fc 4 への移行 ✅ 2026-09-29）

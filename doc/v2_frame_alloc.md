# フレーム割付の見直し（frame size over の解消と静的フレーム）

2026-09-14 検討メモ（レビュー用）。対象: `frame size over` の緩和、fastcall の 16 バイト制限、
go_evolution_plan.md F3「スタックフレーム制約の緩和」。

---

## 1. 今の仕組みと、なぜあふれるか

ゼロページの配置（`share/*/base.asm`、castle は `data.asm` に同じものを持つ）:

| 領域 | サイズ | 用途 |
|---|---|---|
| `L` = FC_LOCAL | 16 | **レジスタ領域**。関数呼び出しをまたがない変数と一時変数。呼び出し先が自由に壊す（caller-saved 相当だが退避はしない。またぐ変数はフレームに置く） |
| `reg` = FC_REG | 16 | コード生成の作業用（間接参照のポインタ、乗除算の引数など） |
| FC_FASTCALL_REG | 16 | fastcall 関数の**引数 + 戻り値 + ローカル + 一時変数の全部** |
| `S` = FC_STACK | 128 | フレームスタック。X がフレームポインタ。`S+n,x` |

`regalloc.AllocateRegister` の規則:

- 戻り値・引数・呼び出しをまたぐ変数・`&` を取られた変数・配列・struct → フレーム（`S+addr,x`。fastcall なら FC_FASTCALL_REG）
- それ以外の生きている変数 → レジスタ領域。live range（[min,max] の区間近似）が重ならないもの同士で 1 つの
  「レジスタ」を共有し、**レジスタは常に 2 バイト単位**（1 バイト変数でも 2 バイト使う）
- 8 レジスタ（16 バイト）を超えると `frame size over`。fastcall はフレーム分も同じ 16 バイトに入るので
  `引数 + 戻り値 + 配列 + レジスタ ≤ 16`

あふれる典型:

1. 式が深い / 短命な変数が多い関数で、同時に生きる一時変数が 8 個を超える（1 バイト変数も 2 バイト消費するので実質もっと早い）
2. fastcall 関数: 引数 3 個（3〜6 バイト）+ ローカル数個で簡単に 16 に届く。fastcall はほかを呼べないので
   「またぐ」概念がなく、全部がこの 16 バイトに入る
3. 区間近似: `a` を使い切った後に `b` が生まれても、ループで区間が伸びると共有できない

castle のゼロページ予算: NSD（サウンドドライバ）の `ZEROPAGE` が $00〜$2F、fc が $30〜$5F（48 バイト）、castle 自身の
固定アドレス変数が $60〜$7F、スタック $80〜$FF。**ZP に空きは無い**（ld65.cfg の ZP は size $60 で満杯。
2026-09-14 訂正: 当初「48 バイト空き」と書いたが NSD の分を見落としていた）。

## 2. 方針: 二段構え

| 段 | 内容 | 効果 | 規模 |
|---|---|---|---|
| **A. いま直す**（1 日）✅ 2026-09-14 | (1) 1 バイト変数をバイト単位で詰める (2) 普通の関数はレジスタが足りなければフレームに**あふれさせる**（エラーにしない） (3) fastcall 領域を広げられるようにする（既定 32、`options(fastcall_reg: N)`） | `frame size over` は fastcall で N を超えたときだけになる。普通の関数からは消える | 小 |
| **B. 静的フレーム**（1〜2 週） | コールグラフから各関数のフレームを**固定アドレス**に割り付ける（オーバーレイ）。X によるフレームポインタ、`inx/dex`、`call` マクロ（25 サイクル）が消え、`S+n,x`（4 サイクル）が `addr`（ZP 3 サイクル）になる。fastcall と普通の関数の区別もほぼ消える | 速度・サイズ・制限の根本解消。castle 規模で効果大 | 大（ABI 変更） |

A は B の後も残る（B でもレジスタ領域は関数のフレームの一部になるだけで、詰め方は同じ）。
**まず A を入れて castle を通し、B は別ブランチで**。

## 3. A の設計（実装済み 2026-09-14。A-1〜A-4 のとおり。既定の FC_FASTCALL_REG は 32、castle は ZP に空きが無いので
`options(fastcall_reg: 16)` のまま。生成 asm は各モジュールで `.assert FC_FASTCALL_REG_SIZE >= 必要量`）

### A-1 バイト単位のレジスタ詰め

`NewAllocator` は live range が重ならない変数を 1 レジスタにまとめ、`regSize += 2`。これを
「サイズ付きの区間割付」にする: 変数を（サイズ降順で）順に見て、既存のスロット列のうち
「その変数の全バイトについて区間が重ならない」最初の位置に置く。2 バイト変数は偶数境界に置かなくてよい
（`lda 1+<L+3` は普通に書ける）。1 バイト変数だけの関数なら容量が実質 2 倍になる。

ダンプ（allocir golden）の `addr=` が変わるので golden 更新。asm は変わりうる（アドレスだけ）。

### A-2 普通の関数: レジスタから外れた変数はフレームへ

割付後、レジスタ領域（16 バイト）に入りきらない変数は `LocFrame` にする（`S+addr,x`）。
フレームは 128 バイトのスタックの一部なので、深い呼び出し連鎖で溢れる可能性は残るが静的には検出できない
（今もそう）。速度差は 1 サイクル/アクセス。どの変数を追い出すかは「使用回数（`uses` の数）が少ないもの」から。

`A` レジスタ・コンディションレジスタ割付は今のまま先に行う。

### A-3 fastcall

fastcall はスタックを使わない（X を触らない）ことが規約なので、あふれ先も静的領域しかない。
FC_FASTCALL_REG を広げる:

- 既定 16 → 32。main モジュールの `options(fastcall_reg: N)` で変更可（16〜64）
- base.asm の `.res` はこの N から生成する。castle のように base を自前で持つプロジェクトは
  `.res` を合わせる必要がある → 生成 asm に `.assert` を出して不一致をリンク時に検出（`FC_FASTCALL_REG_SIZE` を
  `.exportzp`/`.import` して `.assert FC_FASTCALL_REG_SIZE = N`）
- fastcall 関数どうしは同時に活性にならない（fastcall から呼べない）ので 1 領域を共有でよい。
  割込みハンドラは今のところ asm なので問題なし（fc で書けるようにするなら §4-5）

castle は ZP に空きが無いので 16 のまま（`options(fastcall_reg: 16)`）。広げるならスタック $80 を削るか NSD の配置を変える。

### A-4 診断

`frame size over` のメッセージに「必要 N バイト / 上限 M」「大きい変数の一覧」を出す。
どの関数で何がいくつ要るかが見えないのが今つらい。

## 4. B の設計（静的フレーム、オーバーレイ割付）

### 4-1 考え方

関数 f のフレーム（引数・戻り値・ローカル・一時変数）を固定アドレス `F_f` に置く。
同時に活性になりうる関数（呼び出し連鎖上にある）のフレームは重ねず、そうでないもの（兄弟）は重ねる。
コールグラフが DAG なら、トポロジカル順に

```
base(f) = max over caller c of (base(c) + size(c))     // 根（main）は 0
```

で決まる（cc65 の `--static-locals`、SDCC / PIC 系コンパイラのオーバーレイと同じ）。

### 4-2 コールグラフ

- 直接呼び出し: `call {lit sym}` から確定
- 関数ポインタ経由: 「アドレスを取られた関数」（`&f` / 値として使われた f）の集合 T を作り、
  間接呼び出し 1 箇所につき T 全部への辺を張る（保守的）
- extern（asm）関数: 既定では葉（何も呼ばない）とみなす。asm から fc を呼ぶ場合は `options(calls: [a, b])` で申告
- 再帰（SCC）: そのサイクルに属する関数は静的にできない → **従来のスタック方式のまま**（混在可、§4-4）
- 割込み: fc の割込みハンドラ（`options(interrupt: true)`、将来）は任意の時点で走るので、
  その部分木のフレームは**全関数と重ねない**（base = 全体の最大の後ろ）

### 4-3 引数の受け渡し

- 直接呼び出し: 呼び出し側が `F_callee+i` に直接書く（`sta F_g+2`、3 サイクル）。戻り値は `F_g+0` から読む。
  `inx/dex`・`call` マクロは不要
- 間接呼び出し: 呼び出し先が分からないので `F_callee` に書けない。T の関数は
  **共通の引数バッファ** `FC_IARG`（最大引数サイズ）で受け、プロローグで自分のフレームにコピーする
  （T の関数を直接呼ぶときも同じ経路にすれば規約が 1 つで済む。コピーは引数バイト数 × 6 サイクル程度）
- fastcall との関係: 静的フレームは「fastcall を全関数に広げたもの」。`fastcall` オプションは
  互換のため残すが意味は「FC_FASTCALL_REG を使う」から「静的フレーム」に統一できる。
  fastcall の制約「ほかを呼べない」は不要になる

### 4-4 スタック方式との混在

再帰関数と `options(abi: "stack")` を付けた関数（既存 asm が `S+n,x` で引数を読む castle の ppu.asm など）は
今の規約のまま。呼び出し側は callee の規約を型から知って push する。静的フレームの関数から
スタック関数を呼ぶときは X が「今のスタックの底」を指していればよい（静的関数は X を動かさないので、
main から見て X は常に底のまま）。

### 4-5 配置先とゼロページの予算

全関数のフレームの総和（重ねた後）が ZP に入るとは限らない（castle: 関数 ~300、fastcall 31）。

- 深さ（呼び出し連鎖の長さ）と呼び出し回数で「熱い」関数を ZP、残りを RAM（`$0300〜` の専用領域、絶対アドレス 4 サイクル）
- `options(zeropage: true/false)` で明示もできる
- 予算: ZP は `FC_STATIC_ZP: .res N`、RAM は `FC_STATIC_RAM: .res M` を base.asm に持つ

### 4-6 モジュール分割コンパイルとの両立（F-mod）

配置は**リンク直前の全体処理**。各モジュールは `F_<fn>+off` の**シンボル参照**でコードを出し、
自分のフレームサイズとコールグラフ（直接呼び出し先・アドレスを取った関数）を要約として出力する。
driver が全モジュールの要約から配置を計算し `frames.s`（`F_main = $10` … の `.exportzp` / `.export`）を生成して
一緒にリンクする。モジュール本体の再コンパイルは要らない（配置が変わっても再リンクだけ）。
これなら F-mod のキャッシュとも矛盾しない。

### 4-7 影響範囲

- regalloc: フレームと L の区別が消え、関数ごとの「フレーム内オフセット」の割付になる（A-1 の詰め方を流用）
- codegen: `S+n,x` / `L+n` → `F_f+n`（シンボル）。call の並び、引数・戻り値の受け渡し、`jsr_reg`。fastcall の分岐を統合
- driver: コールグラフ集計と `frames.s` の生成、割込み・extern の申告
- 既存資産: castle の `ppu.asm`（`S+2,x` で引数を読む）は `abi: "stack"` にするか書き換え。`share/runtime.asm` の
  `interrupt` は変更なし（asm ハンドラのまま）
- golden: ir は不変、allocir / asm / bin は全面更新。stdout golden（挙動）で検証。castle ROM は挙動確認（自動プレイ + 実機）

### 4-8 期待効果（概算）

- 呼び出し 1 回: `call` マクロ 25 サイクル + 引数 push（4/バイト）→ `jsr` 6 + 引数 store（3/バイト）
- 変数アクセス: 4 → 3 サイクル、命令 1 バイト短い（`S+n,x` は 2 バイト ZP,X、絶対 ZP も 2 バイト。RAM 配置なら 3 バイト）
- 制限: 関数ごとの上限が消え、総量（ZP + RAM の予算）だけになる

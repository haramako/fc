## 1. ifdef 相当の static if

**2026-09-25 決定（未実装）**:

- 構文は `@if (条件) { … } else { … }`（`else @if (…)` も続けられる）。`static` という予約語は増やさない
- 書ける場所はトップレベル（宣言・`use`・`@include`）と関数の中の文。struct のフィールドの並びなどは最初の版では対象外
- `@if` は新しいスコープを作らない。中の宣言は外側（モジュール / 関数）に登録する（D の static if と同じ）
- 選ばれなかった側も構文は検査し（構文エラーは報告）、名前解決・型検査はしない。`use` のモジュールは読み込まず、
  `@include` のファイルも要求せず、宣言の登録もコードの出力もしない。`fcc fmt` / lint は両側を対象にする
- **ビルドの定義値は、上書きできる `const`**。宣言はモジュールが既定値つきで行い、設定ファイルと CLI は値の上書きだけ:
  ```fc
  // fclib/stdio.fc (ライブラリ)
  public const BUF_SIZE:u8 = 64 @(build);
  // src/common.fc (プロジェクト)
  public const DEBUG = false @(build);
  // 使う側: 普通の const として参照し、@if の条件にも使える
  @if (common.DEBUG) {
      use debug_menu;
  }
  ```
  ```toml
  # fc.toml (メインのソースの隣または親のディレクトリ。値の上書きだけで、宣言はしない)
  [define.stdio]
  BUF_SIZE = 128
  [define.common]
  DEBUG = true
  ```
  CLI は `-D common.DEBUG=true`（設定ファイルの後に当たり、上書きする）
  - 名前は宣言したモジュールのもの（`stdio.BUF_SIZE`）なので、ライブラリ同士でも衝突しない。同じモジュールでの重複は
    普通の const の重複のエラー。ライブラリの既定値を、ライブラリを書き換えずにプロジェクトの `fc.toml` で変えられる。
    ライブラリ自身も自分の定義値で `@if` できる。値はビルド全体で 1 つ
  - `@(build)` はトップレベルの `const` だけ、初期値はリテラル（bool / 整数）だけ。他の定数からの計算や `@if` の中での
    宣言は不可（読み込み・評価の順序で値が変わらないように）。上書きの値の型が合わなければエラー
  - `@if` の条件に書けるのはリテラルと `@(build)` の定数、その演算（`&&` `||` `!` `==` `<` …）だけ（普通の `const` は不可）
  - 宣言されていない定義値の上書きはエラー（綴り間違い対策。全て宣言されるので ifdef 相当の存在判定は要らない）。
    ただし `@if` でそのビルドに含まれないモジュールへの上書きは警告にとどめる。存在しないモジュール名（ライブラリの
    探索パスにも無い）はエラー
- 設定ファイルは `fc.toml`（必要な分だけ `[section]` と `key = value` を自前で読む）。`fcc check --json` / 差分ビルドも
  同じ設定を読み、`fcc build -d` は使った定義値とその出所（設定ファイル / CLI）を表示する
- migrate は無し（新しい機能）。castle の使われていない `const DEBUG = 0` は手で置き換える

以下は決定前の検討の記録。

### 要望と現状

コンパイル時に条件でコードを選択する機能を検討する。
define の指定元をコマンドラインまたはプロジェクト共通の設定ファイルに限定する案が提示された。
**ユーザー確認済み: 無効側も構文は検査し、名前解決・型検査を省く。**
パース前にコードを除外する方式は採らない。
**設定ファイルの範囲も確認済み: プロジェクト全体で共有する。ユーザー環境全体の設定ではない。**

現行の通常の `if` は両側を意味解析してから IR を生成する。
定数条件の最適化があっても、無効側の未定義名や存在しない API を隠せる static if と同じではない。
CLI / ビルドオプションには、今回の要望に対応する define の受け渡しはない。
参照: [意味解析](../internal/sema/hlc.go)、[CLI](../cmd/fcc/main.go)、[ビルドオプション](../internal/driver/driver.go)。

### 検討案

```fc
// FC3 仮案。define の参照表記も未決
static if (build.DEBUG) {
    use debug_menu;
}

function update():void {
    static if (build.DEBUG) {
        debug_menu.update();
    }
}
```

モジュールの宣言・`use`・`include` の選択と、関数内の処理の選択を候補にする。
無効な枝の `use` / `include` はファイルを要求せず、宣言を登録せず、コードや CHR を出力しない案。
通常の `if` のブロックスコープをそのまま使うと条件付き宣言を外から使えないため、
選択した宣言を囲んでいるスコープへ登録するかも決める必要がある。

| 方式 | 無効側の扱い | 主な違い |
|---|---|---|
| 構文解析後の選択（確認済みの方針） | FC の構文としては解析するが、名前解決・型検査をしない。依存解決も省く案 | AST、整形、診断との連携が比較的単純 |
| パース前の選択（今回の対象外） | 無効側は通常の FC 文法では解析しない | 未対応構文も隠せるが、条件・入れ子・文字列・コメントを扱う走査規則が必要 |

無効側の文法エラーは診断するが、無効側でしか使わない型や API が未定義でもよい。
define を後から書き換える仕組みや、テキスト置換マクロまで導入することは現時点の要望に含めない。
条件を外部のビルド定数だけに限定するか、FC の通常の const も許すかは未決。
後者はモジュールの読み込み・定数評価の順序と条件選択が相互依存しないようにする必要がある。

### define の管理候補

- ソース内で define / undef を変更せず、ビルド開始時に全モジュールで同じ設定を共有する案。
- 設定ファイルと CLI の優先順位は「設定ファイル → 明示した CLI で上書き」を候補にする。
- まず bool / 整数など小さな値の集合を対象とし、式や文字列の置換機構にはしない。
- 未定義名を false とするかエラーにするかを決める。綴り間違い対策ではエラーが有力。
  ifdef そのものが必要なら存在判定を別に用意する選択肢もある。
- 設定の出所と有効値をビルド時に確認できるようにする。差分ビルドのキーにも含める。
- プロジェクト共通の設定をバージョン管理できる形にし、CLI の上書きも含めてビルド条件を再現可能にする。

設定ファイルの形式・配置場所・探索方法、CLI の指定構文は今後の設計事項。

## 2. CHR include のパディング

**ユーザー確認済み: 各 CHR を指定サイズまで埋める機能と、開始位置を境界に揃える機能の両方を検討に含める。**

### 現状

`include("font.chr")` は `CHARS` セグメントに `.incbin` を出力する。
各 include のサイズを埋める指定や、開始位置を揃える指定は処理されていない。
自動生成リンカ設定では CHR 全体の領域に `fill = yes` があるが、個々の素材間の隙間を指定する機能ではない。
参照: [include の解析](../internal/sema/hlc.go)、[CHR 出力](../internal/codegen/llc.go)、
[リンカ設定生成](../internal/driver/driver.go)。

castle の `src/main.fc` は CHR ファイルを順に include し、`src/common.fc` に `CBANK_*` の定数を持つ。
素材サイズの変更で後続の位置をずらしたくない場面では、明示的なパディングに用途がある。

### 意味を分けて検討する

| 指定候補 | 意味 | 例 |
|---|---|---|
| size | その include が占める領域を指定サイズにする | 3 KB の CHR を 4 KB に埋める。5 KB ならエラー |
| align | include の開始を CHR 出力領域内の境界に揃える | 現在位置 3 KB なら 1 KB 埋めて 4 KB から開始 |
| fill | 隙間に書くバイト | 既定 0 を候補にする |

```fc
// 両方の機能を検討に含める。キーワード・構文は仮案
include("font.chr") @(size: 4096, fill: 0);
include("sprite.chr") @(align: 4096, fill: 0);
```

固定サイズと境界合わせは別物なので、一つの曖昧な `padding` 値に両方の意味を持たせない。
サイズ超過を黙って切り捨てず、ビルド時に診断する案。
両方を指定した場合は「開始位置を合わせる → データ → 指定サイズまで末尾を埋める」の順を候補にする。
開始前の隙間は、その include の size には含めない案。
複数モジュールの CHR を結合する場合も、最終 CHR 領域での位置が保証される必要がある。
PRG の CPU アドレス、マッパーの CHR バンク単位、iNES の全容量単位とは区別する。
生成済み CHR ファイル自体の書き換えはせず、ROM 出力側の配置として扱う案。

境界サイズや fill 値は指定可能な候補として記録し、現時点で一律のサイズには固定しない。
キーワード名、指定値の制約、既定値は今後の設計事項。

## 3. バンクを名前で指定し、対応を集中管理する

**2026-09-25 の方針（未実装）: マルチバンクのプログラムも fc だけで書け、ld65.cfg は特殊な場合の脱出口にする。**
castle の `ld65.cfg`（125 行、切替バンク 23 個）を分類した結果:

| 分類 | castle の例 | 扱い |
|---|---|---|
| fc のソース・設定に持たせられる | モジュール → バンク / スロット（`game: load = ROM0` 等 約 50 行。`options(bank:)` と `PBANK_*` と三重管理）、固定領域（ROML）、ZP / FC_STACK / BSS / BSS_EX、固定番地（セーブデータ $7E00）、ページ境界（`ROM_IRQ0`〜`6` の 256 バイト）、ヘッダ・ベクタ・CHR、外部オブジェクト（cc65 の NSD）のセグメントの置き場所 | fc だけで書けるようにする。ページ境界は配置制約（候補一覧 §5）、固定番地は `@(address:)` / セグメントの指定を広げる |
| 特別な機能が要る | 複数のバンクにまたがる 1 つの領域（`ROMF` $8000 から 48KB の `fs_data`。読む位置からバンクを計算する）、2 スロット続きの 16KB バンク（`ROM20` の NSD） | 言語で扱うか断片の脱出口に回すかを決める |
| 脱出口に残す | fc が知らないマッパー・バンクの割り当て方（MMC3 の $C000 切替モード、MMC1 / MMC5 など）、ROM から RAM に写して動かすコード（`load` と `run` が違う）、特殊な出力形式（PRG / CHR の別ファイル、ディスクシステム） | cfg を書く |

脱出口は 2 段にする: (1) 普段は fc が cfg を全部作る。(2) 特殊な部分だけ利用者が cfg の断片（追加の `MEMORY` / `SEGMENTS`）を
渡し、fc が作った cfg に足す（fc は自分の領域と重ならないかを検査する）。(3) それでも足りなければ今の
`options(linker_config:)` で丸ごと手で書く。castle は `fs_data` と `ROM20` を断片で渡せば残りは fc だけで書ける見込み。

### 確認済みの目的と現状

**ユーザー確認済み: `.fc` のバンク指定・手動切替用の `PBANK_*` 等の定数・リンカ配置を、一つの情報源で管理したい。**
**独自の `ld65.cfg` を直接書く既存の経路も維持する。**
大規模なプロジェクトでは手書きのリンカ設定が適する可能性があるため、中央設定からの自動生成を必須にしない。
これらは V3 の設計要件として記録し、構文・設定形式・実装方法は未確定とする。

castle では `ld65.cfg` の SEGMENTS がモジュール名を ROM 領域に対応付けており、
**配置をまとめて変更する仕組み自体は既にある。**
一方、各 `.fc` の `options(bank: 数値)`、`common.fc` の `PBANK_*`、リンカの `bank = N` に関連情報が分散している。
例えば bg_mmc には `options(bank: 8)`、`PBANK_BG_MMC = 8`、`bg_mmc: load = ROM8` がある。
今回の目的は、この三者の重複更新と不整合を減らすこと。

現行では、自動生成リンカ設定は `options(bank: N)` を配置に使う。
独自リンカ設定では配置は cfg が決め、FC の bank は far call 判定に使われる。
far call に出力する実際のバンク番号はリンカの `.bank(シンボル)` で得る。
`N >= 0` を切替バンク、負または指定なしを固定扱いとするため、番号だけ変えても全ての意味は統一できない。
参照: [言語リファレンス §1.5 / §4.4](language_reference.md)、[リンカ設定生成](../internal/driver/driver.go)。

### 実現方法の比較（未確定）

| 案 | 利点 | 残ること |
|---|---|---|
| 既存の共通 const と cfg で管理 | 新しい言語機能が少ない。モジュール options は現状でも定数評価される | 独自 cfg とランタイム用の番号の同期は別途必要 |
| `.fc` は論理名、中央設定で物理配置 | 番号変更の波及を減らせる。fixed / switchable なども対応表で表せる | FC、asm、リンカの情報源と生成・検証方法を決める必要 |
| 配置は cfg に一本化して FC から参照 | castle の現在の構成を活かせる | リンク前に必要な far call 判定の情報をどう得るかが課題 |

モジュール単位の options は定数評価するが、宣言に付ける options の評価経路は同じではない。
「全 options で任意の定数式が使える」とはせず、既存機能で足りる範囲を先に確認する。
参照: [モジュール options](../internal/sema/hlc.go)、[宣言 options](../internal/sema/cexpr.go)。

```fc
// 中央設定を導入する場合の仮案。現在は名前を物理バンクに解決する機能はない
@(bank: "background");
```

集中管理する方針は確認済み。新しい bank 文法の具体形は未確定とする。
論理名から番号・CPU 配置先・固定 / 切替を管理し、
必要な FC 定数・asm 定数・リンカ設定を同じ情報源から生成または照合する案が有力。
設定ファイルの形式や自動配置まで今決める必要はない。
`near` は実行時に常にマップされているという契約でもあるため、単に名前を付けただけで自動的に正しくなるものではない。
PRG と CHR は空間・切替単位が異なるので、同一の番号表として混ぜない。

### 自動生成と独自 ld65.cfg の共存

次の二つの経路を残すことを設計の前提とする。

- **自動生成の経路:** プロジェクトの共通配置情報から、FC の論理名の解決・切替用定数・リンカ設定を得る。
- **独自設定の経路:** 利用者が `ld65.cfg` を直接管理し、詳細な MEMORY / SEGMENTS の配置を指定できる。
  既存の `options(linker_config: "...")` による利用を維持し、自動生成への移行を要求しない。

独自設定と一元管理を組み合わせる方法は、今後の検討事項。
例えば cfg / リンク結果を基準に定数を得る案と、共通配置情報から必要な情報だけ生成して手書き cfg と照合する案を比較する。
手書き cfg は自動で上書きせず、既存 cfg の全構文を FC が解釈できることも必須条件にしない。
どちらの経路でも、配置を決める情報源と、不一致を診断する範囲を明確にする。

特に、物理バンク番号をリンク時に得られても、far call 判定に必要な固定 / 切替やマッピングの情報は
それ以前に必要になる。設定の読み込み・コード生成・リンクの順序を含めて設計する。
独自 cfg を使う場合に番号の手作業による三重管理を再び要求しない接続方法を目指すが、具体方式はまだ決めない。

## 4. 差分コンパイルの現状と候補

### 現状（2026-09-20 のソース確認）

**ビルド間でコンパイル結果を再利用する差分コンパイルは未実装。**

| 機能 | 状況 |
|---|---|
| `fcc watch` | ソース配下と fclib の対象拡張子を 0.5 秒間隔で監視。更新時刻・サイズの変化、追加・削除で通常の Build を呼ぶ |
| FC の解析・コード生成 | 毎回新しい Program を作り、読み込まれるモジュールを解析。全体の呼び出し・フレーム解析と各モジュールの生成を行う |
| ca65 | 対象ソースを毎回アセンブル。並列実行は実装済み |
| ld65 | 通常ビルドでは毎回リンク。compile-only はリンクしない |
| `.fc-build` | 中間生成物を保存するが、存在するだけで再利用するキャッシュではない |
| `FromFcm` | 条件分岐・フィールドはあるが、現行 Loader に永続キャッシュを読み書きする経路はない |

モジュールを同じ一回のビルド中に重複ロードしない仕組みと、次回ビルドでの再利用は区別する。
watch は実際の依存グラフではなくディレクトリ監視なので、配下の未使用ファイルでも再ビルドし得る。
ソース配下・fclib の外に置いた資産や、対象外の拡張子も依存関係として追えるようにする余地がある。
参照: [watch](../cmd/fcc/watch.go)、[Loader](../internal/sema/program.go)、
[Build / assembleAll](../internal/driver/driver.go)、[roadmap](roadmap.md)。

### 検討の進め方

差分コンパイルは文法変更を必須としない開発環境の改善。V3 検討一覧に置くが、実装時期は未定。

1. まず解析・最適化・アセンブル・リンクの所要時間を実プロジェクトで分けて測る。
2. 生成 asm と依存入力が同じなら ca65 の `.o` を再利用する段階を候補にする。
   `.s` だけでなく `.inc`、asm の include / incbin、生成 `_frames.inc`、ツールと引数も対象。
3. FC の構文木・意味解析・IR のキャッシュは、モジュールの公開情報と実装への依存を整理してから検討する。
   const、型レイアウト、inline 関数などは宣言が同じでも利用側に影響する。
4. 全体の到達解析・呼び出し規約・静的フレーム配置が変われば、変更していない関数の生成結果にも影響し得る。
   変更した `.fc` だけを再生成すればよいとはしない。

キーにはソース・資産・コンパイラの版、target、最適化・デバッグ設定、define、バンク設定を含める案。
static if の条件変更では依存するモジュール集合も変わる。
CHR の内容だけでなく、サイズ・パディング・順序の変更も出力に影響する。
最終的な確認はクリーンビルドとの成果物・診断の一致、依存ファイルの追加・削除を含めて行う。
本メモでは高速化率の測定や実装は行っていない。

## 5. マクロ的な組み込み・予約語・言語機能の有効化

### 要望と現状

マクロ的に動作する関数と通常の関数の区別、機能追加による予約語・名前の衝突への対策を検討する。
ユーザーからの候補は、Zig を参考にした `@sizeof` などの `@` 表記と、
`use ...` による組み込み機能の使用許可の切り替え。両者は独立に比較し、採用を確定しない。
**ユーザー確認済み: `use` で切り替える対象は組み込み機能の使用許可。`use` に応じて予約語・構文そのものは切り替えない。**
これは V3 全体の予約語・文法を変更しないという意味ではない。
**既存の予約語を使う機能のうち、使用頻度の低いものを `@` 表記へ移す案も検討対象に含める。**
`options(...)` の代替表記は **`@(...)` に決定済み**（§5 C）。
利用者ジェネリクスを導入せず必要な処理を組み込みで提供する既存方針と合わせて整理する。
利用者が定義する汎用マクロやテキスト置換機構の導入まで決めたものではない。

現行 FC には異なる仕組みが混在している。

| 現行の例 | 扱い | 検討点 |
|---|---|---|
| `sizeof`、`bitcast`、`incbin` | 予約語として構文解析する | 呼び出し風の組み込みへ整理すれば、通常の識別子を予約せずに済むか |
| `textmap`、`printf`、`min` / `max` / `clamp`、`asm` | 通常の名前で引く組み込みマクロ | 特別な引数・展開・定数評価を行うことを表記で区別するか |
| `_T(...)` | `textmap` が返す変換器の呼び出し | 組み込みを呼んで得た値の呼び出しも特別表記にする必要があるか |
| `use ...` | モジュールや public 宣言を取り込む | 言語機能の使用許可とは別。現状では文法を切り替えない |

`printf` などは stdio / math の読み込みを要求するが、現状はプログラム内に対象モジュールが存在するかの検査であり、
呼び出し元のファイルが言語機能を明示的に有効化する制度ではない。
参照: [予約語](../internal/syntax/lexer.go)、[組み込み](../internal/sema/builtins.go)、
[名前解決・use の現行仕様](language_reference.md)。

### Zig から参考にする部分

Zig のコンパイラ組み込みは `@` で始まり、サイズ取得は `@sizeOf(T)` と書く。
予約語などを識別子として使うための `@"名前"` は、それとは別の構文。
`@import` はファイル / モジュールを取り込む機能であり、ここで検討する FC の `use` による文法切り替えと同一視しない。
出典: [Builtin Functions](https://ziglang.org/documentation/master/#Builtin-Functions)、
[@sizeOf](https://ziglang.org/documentation/master/#sizeOf)、
[String Identifier Syntax](https://ziglang.org/documentation/master/#String-Identifier-Syntax)、
[@import](https://ziglang.org/documentation/master/#import)（2026-09-20 閲覧）。

### A. `@` 表記と名前の衝突への対策

**2026-09-25 決定（未実装）**: 次を `@名前(...)` にする。`@` の名前はコンパイラ専用で、同名の利用者の関数・変数と
衝突しない（`sizeof` / `min` などは普通の名前として使えるようになる）。綴りは今の名前のまま（小文字と `_`。Zig 風の
`@sizeOf` にはしない）。引用識別子 `@"名前"` は設けない。

| FC2 | FC3 | castle / その他の使用数（2026-09-25） |
|---|---|---:|
| `sizeof(T)` | `@sizeof(T)` | 0 / 0 |
| `bitcast<T>(x)` | `@bitcast(T, x)`（`<T>` の構文をなくす） | 10 / 0 |
| `incbin("f")` | `@incbin("f")` | 12 / 0 |
| `include("x.asm")` / `include("x.chr") options(...)` | `@include("x.chr", size: 4096, align: 4096, fill: 0)`（属性は名前付きの引数） | 26 / 8 |
| `asm("...")` | `@asm("...")` | 25 / 12 |
| `textmap("f")` | `@textmap("f")`（返り値の `_T(...)` は普通の定数の呼び出しのまま） | 3 / 0 |
| `min` / `max` / `clamp` | `@min` / `@max` / `@clamp` | 0 / 0 |
| `unittest_run_tests()` | `@` の組み込み（名前は実装時に決める） | 0 / 少 |
| `options(...)` | `@(...)`（§C） | 156 / 70 |

そのまま残す予約語: `function` / `var` / `const` / `struct` / `soa`、型を作る `fn` / `farfn`、`use` / `from` / `as` /
`public`、`true` / `false` / `null`、制御構文（`switch` / `case` / `default` / `loop` / `elsif` など）。
`private` は予約語の表にあるだけで文法では使われていない（使用 0）ので、FC3 では予約語から外す。
`printf` は §9（ログポイント）で扱いを決めるので、この一覧から外す。

- 型を取る組み込み（`@sizeof(T)`、`@bitcast(T, x)`）は、パーサが組み込みの一覧を持ち、名前ごとにどの引数が型かを決める
- FC3 で旧表記（`sizeof(x)` が未定義の関数の呼び出しになるなど）を書いたら、`@sizeof` と `fcc migrate` を案内する診断を出す
- migrate は構文木の位置で書き換える（コメント・文字列の中や、利用者の同名の関数は書き換えない）

```fc
// FC3 の候補。綴り・引数の規則は未確定
var bytes = @sizeof(Player);
const _T = @textmap("font.txt");
@copy(dst, src);
```

- `@name` をコンパイラ専用の名前空間として扱い、利用者の同名関数と衝突・隠蔽しない案。
  普通の `sizeof` / `textmap` などの名前を利用者が使えるようにするかも合わせて決める。
- `@` は「コンパイラが特別に扱う」印とし、コンパイル時専用という意味には限定しない。
  `@copy` のように実行時のコードを出す処理も含み得る。
- 型を渡す `@sizeof(T)` は普通の値引数の関数呼び出しとは異なる。
  FC では型を一般の値にする機能やジェネリクスを導入せず、組み込みに必要な引数規則を定める案。
- 現在の `sizeof(x)` のような式からの型取得を維持するか、型引数と分けるかは未決。
  表記変更だけで引数式の評価回数や副作用の扱いを変えない。
- 普通の関数で提供できる処理はライブラリ関数のままにする選択肢もある。
  `printf`、`cos`、テスト列挙などを全て機械的に `@` 化するかは、機能ごとに判断する。
- `if` / `var` などの基本構文まで `@` 化する案ではない。
  残る予約語との衝突には Zig 風の引用識別子や文脈依存キーワードも比較候補になるが、別途採否を決める。

既存の予約語も見直しの対象とし、低頻度の機能を `@` 側へ移すことで通常の識別子として使える名前を増やす案。
`sizeof` / `bitcast` / `incbin` / `include` などは整理対象の例だが、全てを低頻度と判断したものではない。
採否は castle などでの使用頻度に加え、構文上の役割・読みやすさ・移行の容易さを見て決める。
宣言・文・型引数を持つ機能は、見た目を `@name(...)` にしても通常の関数と同じ意味になるとは限らない。
移すと決めた構文は V3 で共通に扱い、`use` の有無で旧キーワードに戻す方式にはしない。

先行する slice 資料の `@copy` / `@append` / `@slice` も、この表記の検討と揃える。
Zig の大文字小文字をそのまま採用するか、FC の `@sizeof` のような綴りを使うかは未決。

### B. `use ...` による有効・無効

「名前を取り込む」と「機能の使用を許可する」を区別する。
ユーザーの回答により、`use` の有無で文法そのものを切り替える方式は今回の対象外とする。
V3 への移行時に共通の文法を改めることは対象に含む。下表には比較のため残す。
無効な機能を使った場合は診断する案であり、黙って通常の関数として扱ったりコードを削除したりはしない。

| 方式 | 例となる意味 | 主な影響 |
|---|---|---|
| 現行のモジュール import | 通常の関数・型・定数を見えるようにする | 言語の機能制限にはならない |
| 機能の使用許可（確認済みの検討対象） | 構文は共通に解析し、有効化した機能だけ意味解析時に使用を認める | 整形・診断・static if との整合を取りやすい |
| 予約語・文法の切り替え（今回の対象外） | 指定したファイルなどでのみ新しい構文を認識する | ファイルごとの文法差、先読み、import 順序、ツール対応が増える |

構文は共通に保ち、`@` の専用名前空間と組み込みの使用許可を組み合わせる案を検討する。
機能切り替え自体が必要かも含めて検討し、全ての組み込みに有効化宣言を必須にするとは決めない。

検討事項:

- 有効化の単位はファイル / モジュール / プロジェクトのどれか。`use` の再輸出・間接 import で引き継ぐか。
- 既存の `use` と機能指定をどう区別するか。機能名と通常のモジュール名の衝突を避ける方法。
- `#fc 3` による言語バージョン指定、プロジェクト設定の define、static if との役割分担。
- static if の無効側も構文は検査する確認済み方針との整合。
  使用許可方式なら構文を共通に保ち、無効側で使用許可の診断も省く案を取れる。
- ソース内の宣言順や別モジュールの読み込み順で、同じコードの解釈が変わらない規則。
- 有効な機能集合を、整形・エディタ診断・差分コンパイルでも一致させる方法。

具体構文・機能一覧・既定の有効範囲は今後の設計事項。

### C. `options(...)` → `@(...)`（決定済み・未実装）

**2026-09-25 の追加決定（未実装）**:

  中の宣言の既定値、宣言の後ろならその宣言の属性。今は `bss` だけだが、将来まとめて既定にできる属性を増やしても同じ形。

  ```fc
  @(bss: "IRQ_DATA") {
      public var b:u8;
      var c:u8 @(segment: "BSS");
  }
  ```
- `include` の属性は `@include("font.chr", size: 4096, ...)` の名前付きの引数にする（§A。`@include(...) @(...)` と
  `@` を 2 つ並べない）
- `fastcall` は FC3 の最初の版では残す（なくすと生成コードが変わり、migrate の ROM 一致の方針と両立しないため。

**2026-09-20、ユーザーが `@(inline:true)` 形式の採用を決定。**
V3 では `options(...)` を `@(...)` に変更する。`@with(...)` / `with(...)` は採用しない。
これは V3 の仕様方針の決定であり、現在の FC2 処理系への実装開始を意味しない。

モジュール設定と、変数・定数・関数などに付ける属性に同じ記法を使う。
今回の決定は表記と適用対象の区別についてであり、設定の意味・評価規則の変更とは分ける。

先行する V3 資料で旧表記が残る場合も、V3 の属性表記は本節に従う。
現行 FC2 の説明・実測用ソースにある `options(...)` は現行記法として維持する。
本書の CHR パディングとバンク名指定の V3 例は `@(...)` に揃えた。各機能の詳細は引き続き未確定。

#### 既存言語との比較と採用理由（2026-09-20）

公式資料を調べたうえで比較し、`@(...)` を採用した。

| 言語 | 参考になる記法・仕組み | FC で考える点 |
|---|---|---|
| [Odin](https://odin-lang.org/docs/overview/#attributes) | `@(link_name="...")` など、宣言の前に属性をまとめる | `@(...)` は実例がある。FC では既存の `key: value` と後置も比較できる |
| [D](https://dlang.org/spec/attribute.html#uda) | ユーザー定義属性に `@(...)` がある | 外見の参考。FC にユーザー定義属性・反射まで導入する必要はない |
| [Rust](https://doc.rust-lang.org/reference/attributes.html) | `#[...]` は後続の対象、`#![...]` は囲んでいる対象に適用 | 属性の対象を明確に区別する考え方が参考になる |
| [Swift](https://docs.swift.org/swift-book/ReferenceManual/Attributes.html) | `@属性名(引数)` | 個別の属性名が目立つが、FC の `@` 組み込み呼び出しと同じ外見になる |
| [Zig](https://ziglang.org/documentation/master/#Grammar) | `align(...)` / `linksection(...)` / `callconv(...)` などの宣言用構文もある | Zig も全てを `@` に統一してはいない。FC で予約語を減らすなら、そのままの模倣はしない |

**`@(...)` を属性の共通表記にする。**
`@name(...)` はコンパイラ組み込みの操作、`@(key: value)` は設定・属性の集合、と見分けられる。
キーを追加するたびに通常の識別子を予約する必要がなく、複数の指定も一組にまとめられる。
`@with(...)` も成立するが、属性の意味を専用の `@(...)` に与えるなら `with` を挟む必然性は小さい。
裸の `with(...)` は予約語または文脈依存構文を増やすため採用しない。

```fc
// FC3: 属性の @ 記法は決定済み・未実装。バンク名・CHR 属性の詳細は検討中
@(bank: "background"); // モジュールに対する単独の指定

var flag:uint8 @(volatile: true);
var vram:uint8 @(address: 0x2007);

function draw():void @(inline: true, segment: "game") {
    // ...
}

include("font.chr") @(size: 4096, align: 4096, fill: 0);
```

宣言属性は、既存の options と同じ後置にする。
宣言が名前・型から始まる並びを保て、短い属性なら一行で読める。長ければ同じ属性位置で改行する。
前置の属性は属性自体が目立つ利点があるが、単独のモジュール指定との読み違いに注意が必要。
前置・後置の両方は提供せず、後置に揃える。

単独の `@(...);` はモジュール設定、宣言に付く `@(...)` はその宣言の属性とする。
単独指定を「次の宣言だけに付く属性」としても解釈する規則は設けない。
モジュール指定の重複や順序、プロジェクト全体のキーとモジュール固有のキーの区別は、現行の意味と照らして別途整理する。

**ユーザーの追加方針: `@(inline)` のように `: true` を省略する形も採用する。**
`@(inline)` は `@(inline: true)` と同じ意味とし、値を明示する形も残す。
省略できるのは真偽値フラグとして定義されたキーだけとする案。`bank` / `address` / `segment` などは値が必要。
`@(inline, segment: "game")` のような混在も同じ規則で表せる。
`false` を指定する場合は、対応する属性で `@(zeropage: false)` のように明示する。
未定義キーや不適切な適用先の診断、属性値の定数評価は意味解析で行う案。
予約語を含み得る属性キーは属性位置の名前として扱い、`inline` などを通常の変数参照と混同しない。
コロンの前後などの整形規則、`options` の予約解除、V3 での旧表記の受理・診断は別途決める。

#### 真偽値属性の利用頻度（2026-09-20 調査）

実プロジェクト `C:\Work\castle\src` の 39 個の `.fc` と、FC の `fclib` の 10 個の `.fc` を別々に集計した。
コメントを除外したソース上の options のキー指定数。関数の実行回数や展開後の出現数ではない。
テスト、ドキュメント、examples 内の castle のコピーは除く。
fclib は emu / NES 両ターゲットのソースを含むため、一つの ROM に全て使われるという意味ではない。

| 明示した属性 | castle 本体 | fclib |
|---|---:|---:|
| `fastcall: true` | 0 | 16 |
| `inline: true` | 0 | 3 |
| `near: true` | 2 | 0 |
| `farcall: true` | 1 | 0 |
| `volatile: true` | 1 | 0 |
| true の合計 | 4 | 19 |
| 全属性のキー指定数 | 185 | 50 |

false の明示はこの調査範囲では 0 件。options のまとまりの数は castle が 171、fclib が 47。
castle の true 4 件のうち、3 件はモジュール設定、1 件は変数属性。
fclib の 19 件は全て関数属性で、16 個の関数宣言に分布する（うち 3 個に fastcall と inline の両方が付く）。

castle では `segment` 83 件、`symbol` 37 件、`bank` 29 件、`address` 16 件など、値を持つ属性が中心。
したがって `: true` の省略が短縮する箇所は現時点では少ない。
fclib の true は全属性指定の 38% だが、その多くは既存の fastcall 指定。
**ユーザー補足: fastcall は今後不要であり、省略形の主な用途として期待するのは inline。**
したがって fastcall の 16 件を、V3 における省略形の有用性の根拠には数えない。
上の集計から fastcall だけを除けば、true 指定は castle 4 件・fclib 3 件と少数になる。
この件数はその他の属性を V3 に全て維持すると決めたものでもない。
例えば [math.fc](../fclib/math.fc) の rand / sign / abs は調査時点で `options(fastcall: true, inline: true)` だが、
今後の例は fastcall を前提にせず `@(inline)` とする。
省略形は大量の既存指定を短縮するためというより、今後明示的に inline を指定する場面で簡潔に書くためと評価する。
今回の補足は設計記録であり、現行の fastcall や asm との接続をここで削除・変更するものではない。

処理系で使う真偽値・有無による主なフラグは、`inline`、`noinline`、`fastcall`、`interrupt`、
`volatile`、`near`、`farcall`、`zeropage` の 8 種類（調査時点の一覧。V3 の採用一覧ではない）。
全てが今回の実用ソースに現れるわけではなく、`zeropage` は既定を変える `false` 指定に意味がある。
固定アドレス変数は現在 `address` の指定だけで volatile になるため、明示の volatile 件数は低レベルアクセスの総数ではない。

実装時の注意: 現行の `inline` / `volatile` などには値ではなくキーの有無（`Options.Has`）を見る箇所がある。
そのため、全フラグの `: false` が現在既に無効化として動くとは扱わない。
V3 で省略形を true として正規化する際、false の意味・可否も属性ごとに明確にする。
今回の作業では現行処理系の挙動は変更しない。
参照: [Options.Has](../internal/ir/module.go)、[属性の意味解析](../internal/sema/hlc.go)、
[inline 判定](../internal/opt/inline.go)、[フレーム属性](../internal/frames/frames.go)。

### V2 からの移行

**仕組み（2026-09-25、ブランチ `feature/v3`）**:

- 文法バージョンはソースごとに先頭行の `#fc 2` / `#fc 3` で選ぶ（無ければ移行期間は fc 2 = `syntax.DefaultVersion`）。
  コンパイラは両方を受け付け、1 つのプログラムに混ぜられる（`syntax.File.Version` → `ir.Module.Version`。版で意味が
  変わる規則はモジュールの版で分岐する）
- `fcc migrate [-l|-w|-d] <file.fc> ...` が fc 2 のソースを fc 3 に書き換える（`internal/migrate`）。fc 2 として解析し、
  規則（`migrate.Rules`）がトークンの位置に対する置き換え（`Edit`）を足す。構文木を印字し直さないので、コメント・空行・
  書式は残る。最後にプラグマを `#fc 3` にし、fc 3 として解析し直せなければエラー（規則の不具合）。fc 3 のソースは
  そのまま（何度かけても同じ）
- **文法を変えるときは、migrate の規則とテストを一緒に足す**。`internal/driver/migrate_test.go` が castle / miku /
  bench / golden のテストプログラムと fclib を migrate して fc 3 としてビルドし、fc 2 のままのビルドと ROM・バイナリが
  バイト単位で一致することを確かめる（`TestMigrateExamples` / `TestMigrateGoldenPrograms` / `TestMigrateBench`）。
  意味を変える変更（`int` の幅など）でも、migrate した結果が同じコードになることを要求する
- 起点は main の 3625001（fc 2 の最後）。この時点の fc 2 のソースは全部 migrate で fc 3 にできることを保つ

将来の migrate では、予約語の構文と組み込みへの参照を特定して書き換える。
利用者の同名関数・ローカル変数を、単なる文字列置換で `@` 付きにしない。
`textmap` が返す `_T` のような値、型 / 式を受ける構文、モジュールの別名も区別する。
機能宣言を導入する場合は、その追加位置・適用範囲も移行対象になる。
既存の予約語から `@` 表記への変更と、モジュール・宣言に付ける `options(...)` の変更も migrate の検討に含める。
属性の対象を構文木で特定し、キーと値、宣言との対応、コメントを保つ方法を検討する。
この節は V3 の検討追加のみで、現行の予約語・組み込み名・`use` の意味は変更しない。

## 6. interrupt の既知の問題（記録のみ・修正しない）

記録: 2026-09-20。これは現行処理系の問題であり、V3 で追加する機能ではない。
**ユーザー方針: 割り込み処理には厳密なタイミングの要求があり、FC の interrupt 属性はほぼ使わない想定。
問題は記録に留め、今回は修正しない。修正・自動退避・新しい診断の実装を開始する指示ではない。**

### 演算ルーチンの共有作業領域を保護していない

`options(interrupt: true)` を付けても、割り込み関数やその呼び出し先で、
乗算・除算・剰余のランタイムルーチン呼び出しは禁止されない。
通常の変数同士の掛け算などは、共有領域 `reg` に引数を書き、`__mul_8` / `__mul_16` 等を呼ぶ。
標準の割り込み入口は CPU の A・X・Y を退避・復帰するが、この `reg` は保存しない。

例えば、通常処理が `reg` に演算の入力や途中結果を置いている間に割り込みが入り、
割り込み側でも同じ作業領域を使う演算を行うと、通常処理の再開時に値が壊れている可能性がある。
毎回発生するとは限らず、割り込みが入る位置と実際の生成コードに依存する。

現行の interrupt 対応は、FC 関数の静的フレームを他の関数と重ねず、到達先の stack ABI を拒否するもの。
演算ルーチンはコード生成で暗黙に呼ばれるため、このフレーム保護だけでは共有 `reg` の破壊を防げない。
**したがって interrupt 属性が付いているだけで、生成される全処理が割り込みに対して安全になるわけではない。**
ソースを追って確認した問題であり、今回、割り込みを注入する再現試験は行っていない。

`x * 4` など、定数畳み込みやシフト命令への展開で演算ルーチンを使わない場合は、
この共有領域の問題とは区別する。ただし、それだけで割り込み処理全体の安全性を保証するものではない。

将来必要になった場合の候補として、割り込みとその到達先で共有領域を使う暗黙の呼び出しを診断する方法、
専用領域を使う方法、必要な作業領域を退避する方法がある。どれも未採用で、現時点では着手しない。
対象は直接書いた掛け算だけでなく、呼び出し先・暗黙のランタイム処理まで確認する必要がある。

参照: [乗除算・剰余のコード生成](../internal/codegen/arith.go)、
[割り込み入口と演算ルーチン](../share/runtime.asm)、[呼び出し解析・フレーム配置](../internal/frames/frames.go)。

## 7. `int` の廃止と整数型名の整理

**2026-09-25 決定（未実装）**:

- 正式名は短い `u8` / `i8` / `u16` / `i16`。エラーメッセージや IR のダンプの表示もこれにそろえる
- FC3 では古い名前（`int` / `uint` / `sint` / `int8` / `int16` / `uint8` / `sint8` / `uint16` / `sint16`）を全て受け付けず、
  `fcc migrate` を案内するエラーにする（別名は残さない）
- `u8` / `i8` / `u16` / `i16` は FC3 では宣言できない名前にする（型名は型の位置でスコープより先に引くので、同名の
  宣言は黙って隠れてしまう。2026-09-25 時点で既存ソースに同名の識別子は無い）
- migrate: `int` / `uint` / `int8` / `uint8` → `u8`、`sint` / `sint8` → `i8`、`int16` / `uint16` → `u16`、`sint16` → `i16`。
  構文木の型名（`NamedType`。`sizeof(T)` の引数も型）だけを書き換え、幅と符号は変えない
- `char`（§8）は扱わない（文字として使っている `int` も一律に `u8`。char は導入するときの別の作業）

以下は決定前の検討の記録。

**ユーザー方針: V3 では幅・符号が曖昧な `int` を廃止する。**
正式な表記は `sint8` / `uint8` を使うか、短い `i8` / `u8` にするかを検討する。
当初の記載の `int8` は `sint8` の誤記とユーザーが訂正済み。
符号付き / 符号なしを表す名前の選択であり、既存 `int8` をそのまま符号付きへ読み替える案ではない。

| 役割 | 長い表記の候補 | 短い表記の候補 |
|---|---|---|
| 符号付き 8 ビット | `sint8` | `i8` |
| 符号なし 8 ビット | `uint8` | `u8` |
| 符号付き 16 ビット | `sint16` | `i16` |
| 符号なし 16 ビット | `uint16` | `u16` |

16 ビット側も一貫した表記にする候補として併記した。正式名や別名の併存は未決。
現行の `int` / `uint` / `int8` は `uint8` の別名、`int16` は `uint16` の別名。
将来の migrate は元の幅・符号を保ち、`int` を `uint8` または `u8` に変換する必要がある。
`uint` / `sint` / `int8` / `int16` など、残る別名の廃止・互換受理も同時に整理する。
型名の変更に、整数リテラルの型推論・数値変換・演算の意味の変更を紛れ込ませない。
参照: [基本型の定義](../internal/types/types.go)、[現行の型仕様](language_reference.md)。

先行する V3 資料の `uint8` / `uint16` 等は、型名を決定するまでは説明用として維持する。
現行 FC2 のソース・実測例は現行の型名のまま扱う。

## 8. `char` 型の導入

**ユーザーの検討方針: 基本的には uint8 と同じで、文字列として出力するときの扱いだけを変える char 型を導入する。**
8 ビットの格納・数値的な操作を基本とし、Unicode の一文字全体を表す多バイト型にはしない。
数値出力と文字出力を、出力側が型から区別できるようにすることが目的。

```fc
// 構文 / API の利用イメージ。@print の採否は §9 で検討
var n:uint8 = 65;
var c:char = n as char;
@print(n); // 数値として表示する案: 65
@print(c); // 文字として表示する案: ASCII を使う出力先なら A
```

格納表現は同じでも、完全な型別名として区別を消すと、出力時に char かどうか判断できなくなる。
コンパイラ内では区別を残す案。これだけで実行時の型タグ・追加の格納領域を要求するものではない。
表示結果は文字コード表に依存するため、char だけで ASCII・UTF-8 のバイト・ゲーム独自コードを自動判別しない。

今後整理すること:

- `char` と符号なし 8 ビット整数の代入・比較・算術の互換性。式を計算した後も char を保つか。
- 文字列リテラル / `textmap` の要素型を char にするか。char 一要素のリテラル表記を設けるか。
  現行の文字列記法の意味は今回変更しない。
- `[]const char` を文字列出力に使い、`[]const uint8` をバイナリとして扱うか。
  byte slice / char slice の変換と既存のメモリ API との接続を、余計なコピーなしで表す方法。
- 文字の数、格納バイト数、ゲーム文字コードの数、表示幅の区別。
  UTF-8 の複数バイトを順に char として送る場合も、表示側がどう組み立てるかを決める。
- 終端 0 と長さは、char の導入だけでは決まらない。通常 slice / sentinel slice の議論と合わせる。

先行の文字列 API 資料は `[]const uint8` を仮定しているため、char の採用範囲が固まったら調整する。
今回の追加だけで全バイト配列を char 配列に置き換えるものではない。

## 9. `printf` の見直しと NES エミュレータのログポイント

### ユーザーが求めるもの

**対象は、実機向け ROM を動かす Mesen 等の NES エミュレータ。FC の CLI emu の出力改善が主目的ではない。**
NES 側で数値の十進変換・文字列連結などを行わず、Lua 等のホスト側で表示文を構成したい。
さらに、**特定の命令位置に PC が来たことをエミュレータ側で検出し、NES 側の追加コストなしに出力する形が理想。**
通常の出力関数というより、実行を止めずに観測するデバッガのログポイントとして検討する。

当初の MMIO による通知案も比較対象として残すが、値の転送や通知に NES の命令を使うため、
ゼロ追加コストを目指す主案は PC / 実行アドレスへのフックとする。
ゲーム画面に表示する文字列の生成と、ホスト側のデバッグログは別の用途として扱う。

### Mesen 2 での実現可能性

Mesen 2 の公式 Lua API 資料には、`emu.addMemoryCallback` と `emu.callbackType.exec` があり、
指定アドレスで CPU が命令を実行し始めた際のコールバックを登録できる。
`emu.getState`、`emu.read`、`emu.log`、CPU アドレスと ROM / RAM アドレスを対応付ける `emu.convertAddress` もある。
このため、命令位置を観測し、値を読んでホスト側でログを作るための基本機能は揃っている。
出典: [Mesen 2 の Lua API 定義](https://github.com/SourMesen/Mesen2/blob/master/UI/Debugger/Documentation/LuaDocumentation.json)
（2026-09-20 閲覧）。ここでは資料による確認のみで、実際のフック動作試験は行っていない。

資料を踏まえると、既存命令への観測だけなら、ログのために NES 側の命令やサイクルを増やさない設計が可能と考えられる。
これはホスト側の処理負荷もゼロという意味ではない。Lua の処理・表示による実時間の負荷は発生する。

### 主案: 命令を出さないログ注釈と、ホスト用メタデータ

```fc
// FC3 の利用イメージ。@log の名称・構文は未決
hp -= damage;
@log("HP: ", hp); // この地点の値をホストで表示。NES 側の関数呼び出しにはしない案
```

将来の構成案:

1. ソースのログ地点を、最適化後の既存の命令位置へ対応付ける。
   必要なラベルはアドレスを表すだけとし、ログのための NOP・JSR・MMIO 書き込みを生成しない。
2. ログ地点と表示する値の所在・型、文字列テンプレートを、ROM 外のメタデータまたは Lua に出力する。
   リンク結果から最終アドレスを解決する。
3. エミュレータはその命令位置にフックを登録し、レジスタ・メモリを読み、Lua 側で表示する。

最初の候補は関数入口などの安定した命令位置と、グローバル変数・定数の観測。
任意のソース行や最適化されたローカル変数へ広げるほど、位置情報・値の復元が難しくなる。
別案として、FC ソースに注釈を書かず、シンボル名を使って Lua / デバッガ側だけでログポイントを設定する方法も比較する。
通常の `printf` のように引数を CPU 上で評価して渡す API とは契約が異なるため、名前と意味を区別する。

### ゼロ追加コストの条件と未決事項

- **値の所在:** ローカル変数が A / X / Y、静的フレーム、定数のどれかを地点ごとに伝える。
  最新値がレジスタにありメモリ側は古い場合もあるので、変数の固定アドレスだけでは十分ではない。
- **最適化:** 消えた値や命令位置を観測するために、変数の寿命延長・退避・最適化の抑制を行えばコストが変わる。
  ゼロ追加コストのモードでは、復元できない値は診断または unavailable とする案を基本にし、暗黙に命令を追加しない。
- **地点の意味:** 命令の前 / 後、分岐の経路、inline 展開された複数の地点、同じアドレスに重なる注釈を整理する。
  ソース上の注釈と、最適化後に実行される地点が常に一対一とは限らない。
- **副作用:** ログ用に FC 関数を実行したり、I/O を通常の CPU アクセスとして読み直したりしない。
  ホスト側で再現可能な純粋な式と観測可能な値に範囲を限定し、副作用を起こさないデバッグ読み取りを使う。
- **バンク:** 同じ CPU アドレスに別の PRG バンクが載る。CPU の PC だけでなく物理 ROM 位置 / バンクを識別する。
  Mesen の memoryType 指定やアドレス変換をどう使うか、対象版で確認する。
- **表示:** 数値の幅・符号・char・文字列の長さと文字コードをホストへ伝える。
  ROM の文字列を読む場合は、その地点のバンク状態も考慮する。
- **成果物:** ROM とログ用情報が同じビルドであることを確認し、リンク後のアドレスを用いる。
  ログ有無で ROM のバイト列と NES 側の実行サイクルが変わらないことを、将来の検証条件にする。

上記は設計上の課題で、現状の FC のデバッグ情報が全てを表現できるという意味ではない。
ログ地点を理由に interrupt の共有作業領域問題（§6）の修正や、NES 側の演算処理を追加しない。

### 比較案: MMIO 通知とホスト側整形

PC フックが使えない場合や、明示的なイベント送信が必要な用途では、
イベント ID と値を所定領域に書き、最後の通知書き込みを Lua 等が検出する案も残す。
ホスト側が ID に対応するテンプレートで文を作るため、NES 側の文字列組み立ては省ける。
ただし値の格納・通知命令のコストは発生し、主案のゼロ追加コストとは区別する。
イベント形式・通知アドレス・対応エミュレータは未決。主案から無断でこの方式へ切り替えない。

### 現行の printf と関連資料

現行 FC の `printf` は C 形式の書式文字列を解釈する関数ではなく、
引数の型に応じて `stdio.print` / `print_int16` を呼ぶ組み込みマクロ。
一般的な出力 API の代替として `@print(...)` やライブラリ関数も比較するが、PC ログポイントとは分けて検討する。
利用者ジェネリクスや文字列補間の導入を前提にはしない。

CLI の emu 用 stdio は既にメモリマップ I/O を経由してホスト側で表示するが、今回の主対象ではない。
その専用アドレスや出力プロトコルを NES エミュレータへそのまま流用する案ではない。
参照: [printf の展開](../internal/sema/builtins.go)、[emu 用 stdio](../fclib/emu/stdio.fc)。
既存の [Mesen 自動プレイ試験](../internal/nes/mesen_test.go) にも、Lua がゲームのメモリを読みログを組み立てる例がある。
これは検討材料であり、上記の PC ログポイント生成が実装済みという意味ではない。
今回の作業は V3 メモの更新のみ。処理系・ROM・エミュレータ・Lua スクリプトは変更しない。

## 1. ifdef 相当の static if

**2026-09-25 決定・実装済み（feature/v3）**: 構文 `StaticIfStmt`（`@if`）、`sema/staticif.go`（条件の検査と評価、
`@(build)` の const の上書き、`Program.CheckDefines`）、トップレベルは `moduleDecls.expandStaticIfs`（use を読み込んでから
評価して選ばれた側を集める。入れ子も繰り返す）、`driver/config.go`（fc.toml を基準ディレクトリから親へ探す。`[section]` と
`key = value` だけを読む）、`BuildOptions.Defines` / CLI の `-D` / `fcc check -D`、`fcc build -d` の `defines:` の表示、
`TestV3StaticIf`。決定の内容:

- 構文は `@if (条件) { … } else { … }`（`else @if (…)` も続けられる）。`static` という予約語は増やさない
- 書ける場所はトップレベル（宣言・`use`・`@include`）と関数の中の文。struct のフィールドの並びなどは最初の版では対象外
- `@if` は新しいスコープを作らない。中の宣言は外側（モジュール / 関数）に登録する（D の static if と同じ）
- 選ばれなかった側も構文は検査し（構文エラーは報告）、名前解決・型検査はしない。`use` のモジュールは読み込まず、
  `@include` のファイルも要求せず、宣言の登録もコードの出力もしない。`fcc fmt` / lint は両側を対象にする
- **ビルドの定義値は、上書きできる `const`**。宣言はモジュールが既定値つきで行い、設定ファイルと CLI は値の上書きだけ:
  ```fc
  // fclib/stdio.fc (ライブラリ)
  public const BUF_SIZE:u8 = 64 @(build);
  // src/common.fc (プロジェクト)
  public const DEBUG = false @(build);
  // 使う側: 普通の const として参照し、@if の条件にも使える
  @if (common.DEBUG) {
      use debug_menu;
  }
  ```
  ```toml
  # fc.toml (メインのソースの隣または親のディレクトリ。値の上書きだけで、宣言はしない)
  [define.stdio]
  BUF_SIZE = 128
  [define.common]
  DEBUG = true
  ```
  CLI は `-D common.DEBUG=true`（設定ファイルの後に当たり、上書きする）
  - 名前は宣言したモジュールのもの（`stdio.BUF_SIZE`）なので、ライブラリ同士でも衝突しない。同じモジュールでの重複は
    普通の const の重複のエラー。ライブラリの既定値を、ライブラリを書き換えずにプロジェクトの `fc.toml` で変えられる。
    ライブラリ自身も自分の定義値で `@if` できる。値はビルド全体で 1 つ
  - `@(build)` はトップレベルの `const` だけ、初期値はリテラル（bool / 整数）だけ。他の定数からの計算や `@if` の中での
    宣言は不可（読み込み・評価の順序で値が変わらないように）。上書きの値の型が合わなければエラー
  - `@if` の条件に書けるのはリテラルと `@(build)` の定数、その演算（`&&` `||` `!` `==` `<` …）だけ（普通の `const` は不可）
  - 宣言されていない定義値の上書きはエラー（綴り間違い対策。全て宣言されるので ifdef 相当の存在判定は要らない）。
    ただし `@if` でそのビルドに含まれないモジュールへの上書きは警告にとどめる。存在しないモジュール名（ライブラリの
    探索パスにも無い）はエラー
- 設定ファイルは `fc.toml`（必要な分だけ `[section]` と `key = value` を自前で読む）。`fcc check --json` / 差分ビルドも
  同じ設定を読み、`fcc build -d` は使った定義値とその出所（設定ファイル / CLI）を表示する
- migrate は無し（新しい機能）。castle の使われていない `const DEBUG = 0` は手で置き換える

以下は決定前の検討の記録。

### 要望と現状

コンパイル時に条件でコードを選択する機能を検討する。
define の指定元をコマンドラインまたはプロジェクト共通の設定ファイルに限定する案が提示された。
**ユーザー確認済み: 無効側も構文は検査し、名前解決・型検査を省く。**
パース前にコードを除外する方式は採らない。
**設定ファイルの範囲も確認済み: プロジェクト全体で共有する。ユーザー環境全体の設定ではない。**

現行の通常の `if` は両側を意味解析してから IR を生成する。
定数条件の最適化があっても、無効側の未定義名や存在しない API を隠せる static if と同じではない。
CLI / ビルドオプションには、今回の要望に対応する define の受け渡しはない。
参照: [意味解析](../internal/sema/hlc.go)、[CLI](../cmd/fcc/main.go)、[ビルドオプション](../internal/driver/driver.go)。

### 検討案

```fc
// FC3 仮案。define の参照表記も未決
static if (build.DEBUG) {
    use debug_menu;
}

function update():void {
    static if (build.DEBUG) {
        debug_menu.update();
    }
}
```

モジュールの宣言・`use`・`include` の選択と、関数内の処理の選択を候補にする。
無効な枝の `use` / `include` はファイルを要求せず、宣言を登録せず、コードや CHR を出力しない案。
通常の `if` のブロックスコープをそのまま使うと条件付き宣言を外から使えないため、
選択した宣言を囲んでいるスコープへ登録するかも決める必要がある。

| 方式 | 無効側の扱い | 主な違い |
|---|---|---|
| 構文解析後の選択（確認済みの方針） | FC の構文としては解析するが、名前解決・型検査をしない。依存解決も省く案 | AST、整形、診断との連携が比較的単純 |
| パース前の選択（今回の対象外） | 無効側は通常の FC 文法では解析しない | 未対応構文も隠せるが、条件・入れ子・文字列・コメントを扱う走査規則が必要 |

無効側の文法エラーは診断するが、無効側でしか使わない型や API が未定義でもよい。
define を後から書き換える仕組みや、テキスト置換マクロまで導入することは現時点の要望に含めない。
条件を外部のビルド定数だけに限定するか、FC の通常の const も許すかは未決。
後者はモジュールの読み込み・定数評価の順序と条件選択が相互依存しないようにする必要がある。

### define の管理候補

- ソース内で define / undef を変更せず、ビルド開始時に全モジュールで同じ設定を共有する案。
- 設定ファイルと CLI の優先順位は「設定ファイル → 明示した CLI で上書き」を候補にする。
- まず bool / 整数など小さな値の集合を対象とし、式や文字列の置換機構にはしない。
- 未定義名を false とするかエラーにするかを決める。綴り間違い対策ではエラーが有力。
  ifdef そのものが必要なら存在判定を別に用意する選択肢もある。
- 設定の出所と有効値をビルド時に確認できるようにする。差分ビルドのキーにも含める。
- プロジェクト共通の設定をバージョン管理できる形にし、CLI の上書きも含めてビルド条件を再現可能にする。

設定ファイルの形式・配置場所・探索方法、CLI の指定構文は今後の設計事項。

## 2. CHR include のパディング

**ユーザー確認済み: 各 CHR を指定サイズまで埋める機能と、開始位置を境界に揃える機能の両方を検討に含める。**

### 現状

`include("font.chr")` は `CHARS` セグメントに `.incbin` を出力する。
各 include のサイズを埋める指定や、開始位置を揃える指定は処理されていない。
自動生成リンカ設定では CHR 全体の領域に `fill = yes` があるが、個々の素材間の隙間を指定する機能ではない。
参照: [include の解析](../internal/sema/hlc.go)、[CHR 出力](../internal/codegen/llc.go)、
[リンカ設定生成](../internal/driver/driver.go)。

castle の `src/main.fc` は CHR ファイルを順に include し、`src/common.fc` に `CBANK_*` の定数を持つ。
素材サイズの変更で後続の位置をずらしたくない場面では、明示的なパディングに用途がある。

### 意味を分けて検討する

| 指定候補 | 意味 | 例 |
|---|---|---|
| size | その include が占める領域を指定サイズにする | 3 KB の CHR を 4 KB に埋める。5 KB ならエラー |
| align | include の開始を CHR 出力領域内の境界に揃える | 現在位置 3 KB なら 1 KB 埋めて 4 KB から開始 |
| fill | 隙間に書くバイト | 既定 0 を候補にする |

```fc
// 両方の機能を検討に含める。キーワード・構文は仮案
include("font.chr") @(size: 4096, fill: 0);
include("sprite.chr") @(align: 4096, fill: 0);
```

固定サイズと境界合わせは別物なので、一つの曖昧な `padding` 値に両方の意味を持たせない。
サイズ超過を黙って切り捨てず、ビルド時に診断する案。
両方を指定した場合は「開始位置を合わせる → データ → 指定サイズまで末尾を埋める」の順を候補にする。
開始前の隙間は、その include の size には含めない案。
複数モジュールの CHR を結合する場合も、最終 CHR 領域での位置が保証される必要がある。
PRG の CPU アドレス、マッパーの CHR バンク単位、iNES の全容量単位とは区別する。
生成済み CHR ファイル自体の書き換えはせず、ROM 出力側の配置として扱う案。

境界サイズや fill 値は指定可能な候補として記録し、現時点で一律のサイズには固定しない。
キーワード名、指定値の制約、既定値は今後の設計事項。

## 3. バンクを名前で指定し、対応を集中管理する

**2026-09-25 の方針（未実装）: マルチバンクのプログラムも fc だけで書け、ld65.cfg は特殊な場合の脱出口にする。**
castle の `ld65.cfg`（125 行、切替バンク 23 個）を分類した結果:

| 分類 | castle の例 | 扱い |
|---|---|---|
| fc のソース・設定に持たせられる | モジュール → バンク / スロット（`game: load = ROM0` 等 約 50 行。`options(bank:)` と `PBANK_*` と三重管理）、固定領域（ROML）、ZP / FC_STACK / BSS / BSS_EX、固定番地（セーブデータ $7E00）、ページ境界（`ROM_IRQ0`〜`6` の 256 バイト）、ヘッダ・ベクタ・CHR、外部オブジェクト（cc65 の NSD）のセグメントの置き場所 | fc だけで書けるようにする。ページ境界は配置制約（候補一覧 §5）、固定番地は `@(address:)` / セグメントの指定を広げる |
| 特別な機能が要る | 複数のバンクにまたがる 1 つの領域（`ROMF` $8000 から 48KB の `fs_data`。読む位置からバンクを計算する）、2 スロット続きの 16KB バンク（`ROM20` の NSD） | 言語で扱うか断片の脱出口に回すかを決める |
| 脱出口に残す | fc が知らないマッパー・バンクの割り当て方（MMC3 の $C000 切替モード、MMC1 / MMC5 など）、ROM から RAM に写して動かすコード（`load` と `run` が違う）、特殊な出力形式（PRG / CHR の別ファイル、ディスクシステム） | cfg を書く |

脱出口は 2 段にする: (1) 普段は fc が cfg を全部作る。(2) 特殊な部分だけ利用者が cfg の断片（追加の `MEMORY` / `SEGMENTS`）を
渡し、fc が作った cfg に足す（fc は自分の領域と重ならないかを検査する）。(3) それでも足りなければ今の
`options(linker_config:)` で丸ごと手で書く。castle は `fs_data` と `ROM20` を断片で渡せば残りは fc だけで書ける見込み。

**2026-09-25 決定・実装済み（feature/v3）: 配置は `fc.toml` にバンクの表を書き、モジュールは名前で指定する。**
実装: `driver/layout.go`（`[target]` / `[bank.*]` / `[ram.*]` / `[linker] extra` を読み、番号を決め、ld65.cfg と iNES のヘッダを
作る。固定の領域は 1 つのメモリ領域にまとめて最後の 6 バイトをベクタに）、モジュールの `@(bank: "名前")` は意味解析で番号に
（"fixed" は -1。以降の far call の判定などは今の番号のまま）、`@bank("名前")`（コンパイル時の u8）、マッパーのプロファイル
NROM / MMC3 / UxROM / MMC1（16KB モード）、トランポリン `fclib/nes/farcall_uxrom.asm` / `farcall_mmc1.asm`、内蔵 NES
エミュレータに UxROM と MMC1、`TestLayoutMMC3` / `TestLayoutNROM` / `TestLayout16K` / `TestLayoutErrors`。
最初の版で入れなかったもの: 16KB のバンク（MMC3 の 2 スロット続き。トランポリンが 1 スロットしか切り替えないので、cfg の
断片に回す）、関数ごとの `@(bank:)`、容量の超過の使用量の一覧（今は ld65 のエラーのまま）、同じバンクのモジュール同士を
near にすること、castle の番号のバンクを名前に移すこと（castle は ld65.cfg を丸ごと書く道のまま）。

```toml
# fc.toml
[target]
mapper = "MMC3"          # 必要ならモードも (mode = ...)
prg = "256K"
chr = "128K"

[bank.game]              # 論理名。index を書かなければ fcc が空いている番号を割り当てる
slot = 0x8000
[bank.sound]
slot = 0x8000
size = "16K"             # 2 スロット続き
index = 20               # 番号を固定したいときだけ
segments = ["CODE", "RODATA", "nsd_bgm", "nsd_se"]   # 外部オブジェクト (cc65 の NSD) のセグメントの置き場所

[ram.save]               # 名前つきの RAM 領域 (固定番地)。変数は @(segment: "save") で置く
start = 0x7E00
size = 0x200
```
```fc
@(bank: "en");                          // モジュールの置き場所
function f():void @(bank: "fixed") { }  // 関数ごとの指定。"fixed" は常に見えている領域の予約名
mmc3.set_pbank(0, @bank("en1"));         // コンパイル時に決まるバンク番号 (PBANK_* が要らなくなる)
```

- 情報源は `fc.toml` の 1 つ（今は `options(bank: 数値)` / `PBANK_*` / cfg の `load = ROMn` の三重管理）。static if の定義値と
  同じファイルで、`fcc check` / 差分ビルドも同じ情報を読む。番号はコンパイル時に分かるので、far call の判定・同じバンクの
  切り替えの省略・容量の検査に使える
- 番号は省略すれば fcc が割り当て、必要なものだけ `index` で固定する（自動の番号はバンクを足すとずれうる。安定させたい
  なら全部固定で書く）
- 1 つのバンクに入らなければエラーにして使用量の一覧を出す（fcc がモジュールを自動で振り分けることはしない。どの呼び出しが
  far になるかが勝手に変わるため）
- **マッパーのプロファイル**: fcc がマッパーごとに「どの番地にどの大きさの切り替えのスロットがあり、どこが常に見えているか」
  の表を持ち、`mapper`（と `mode`）で選ぶ。`"fixed"` の実際の位置と大きさはプロファイルが決める（UxROM / MMC1 の 16KB
  モードは $C000〜、MMC3 は $C000〜$FFFF、FME-7 は $E000〜 の 8KB など）。切り替えの単位（8 / 16 / 32KB、CHR は 1〜8KB）と
  トランポリン（`fclib/nes/farcall_*.asm`。UxROM / AxROM はバスの衝突を避ける書き方）もプロファイルごと
- 最初の版のプロファイルは NROM / UxROM / MMC1（16KB モード）/ MMC3。固定の領域が無いマッパー（AxROM、MMC1 の 32KB モード
  など。常に見えるべきコードを全バンクの同じ番地に写す必要がある）とその他のマッパーは、最初の版では cfg の脱出口に回す

### 確認済みの目的と現状

**ユーザー確認済み: `.fc` のバンク指定・手動切替用の `PBANK_*` 等の定数・リンカ配置を、一つの情報源で管理したい。**
**独自の `ld65.cfg` を直接書く既存の経路も維持する。**
大規模なプロジェクトでは手書きのリンカ設定が適する可能性があるため、中央設定からの自動生成を必須にしない。
これらは V3 の設計要件として記録し、構文・設定形式・実装方法は未確定とする。

castle では `ld65.cfg` の SEGMENTS がモジュール名を ROM 領域に対応付けており、
**配置をまとめて変更する仕組み自体は既にある。**
一方、各 `.fc` の `options(bank: 数値)`、`common.fc` の `PBANK_*`、リンカの `bank = N` に関連情報が分散している。
例えば bg_mmc には `options(bank: 8)`、`PBANK_BG_MMC = 8`、`bg_mmc: load = ROM8` がある。
今回の目的は、この三者の重複更新と不整合を減らすこと。

現行では、自動生成リンカ設定は `options(bank: N)` を配置に使う。
独自リンカ設定では配置は cfg が決め、FC の bank は far call 判定に使われる。
far call に出力する実際のバンク番号はリンカの `.bank(シンボル)` で得る。
`N >= 0` を切替バンク、負または指定なしを固定扱いとするため、番号だけ変えても全ての意味は統一できない。
参照: [言語リファレンス §1.5 / §4.4](language_reference.md)、[リンカ設定生成](../internal/driver/driver.go)。

### 実現方法の比較（未確定）

| 案 | 利点 | 残ること |
|---|---|---|
| 既存の共通 const と cfg で管理 | 新しい言語機能が少ない。モジュール options は現状でも定数評価される | 独自 cfg とランタイム用の番号の同期は別途必要 |
| `.fc` は論理名、中央設定で物理配置 | 番号変更の波及を減らせる。fixed / switchable なども対応表で表せる | FC、asm、リンカの情報源と生成・検証方法を決める必要 |
| 配置は cfg に一本化して FC から参照 | castle の現在の構成を活かせる | リンク前に必要な far call 判定の情報をどう得るかが課題 |

モジュール単位の options は定数評価するが、宣言に付ける options の評価経路は同じではない。
「全 options で任意の定数式が使える」とはせず、既存機能で足りる範囲を先に確認する。
参照: [モジュール options](../internal/sema/hlc.go)、[宣言 options](../internal/sema/cexpr.go)。

```fc
// 中央設定を導入する場合の仮案。現在は名前を物理バンクに解決する機能はない
@(bank: "background");
```

集中管理する方針は確認済み。新しい bank 文法の具体形は未確定とする。
論理名から番号・CPU 配置先・固定 / 切替を管理し、
必要な FC 定数・asm 定数・リンカ設定を同じ情報源から生成または照合する案が有力。
設定ファイルの形式や自動配置まで今決める必要はない。
`near` は実行時に常にマップされているという契約でもあるため、単に名前を付けただけで自動的に正しくなるものではない。
PRG と CHR は空間・切替単位が異なるので、同一の番号表として混ぜない。

### 自動生成と独自 ld65.cfg の共存

次の二つの経路を残すことを設計の前提とする。

- **自動生成の経路:** プロジェクトの共通配置情報から、FC の論理名の解決・切替用定数・リンカ設定を得る。
- **独自設定の経路:** 利用者が `ld65.cfg` を直接管理し、詳細な MEMORY / SEGMENTS の配置を指定できる。
  既存の `options(linker_config: "...")` による利用を維持し、自動生成への移行を要求しない。

独自設定と一元管理を組み合わせる方法は、今後の検討事項。
例えば cfg / リンク結果を基準に定数を得る案と、共通配置情報から必要な情報だけ生成して手書き cfg と照合する案を比較する。
手書き cfg は自動で上書きせず、既存 cfg の全構文を FC が解釈できることも必須条件にしない。
どちらの経路でも、配置を決める情報源と、不一致を診断する範囲を明確にする。

特に、物理バンク番号をリンク時に得られても、far call 判定に必要な固定 / 切替やマッピングの情報は
それ以前に必要になる。設定の読み込み・コード生成・リンクの順序を含めて設計する。
独自 cfg を使う場合に番号の手作業による三重管理を再び要求しない接続方法を目指すが、具体方式はまだ決めない。

## 5. マクロ的な組み込み・予約語・言語機能の有効化

### 要望と現状

マクロ的に動作する関数と通常の関数の区別、機能追加による予約語・名前の衝突への対策を検討する。
ユーザーからの候補は、Zig を参考にした `@sizeof` などの `@` 表記と、
`use ...` による組み込み機能の使用許可の切り替え。両者は独立に比較し、採用を確定しない。
**ユーザー確認済み: `use` で切り替える対象は組み込み機能の使用許可。`use` に応じて予約語・構文そのものは切り替えない。**
これは V3 全体の予約語・文法を変更しないという意味ではない。
**既存の予約語を使う機能のうち、使用頻度の低いものを `@` 表記へ移す案も検討対象に含める。**
`options(...)` の代替表記は **`@(...)` に決定済み**（§5 C）。
利用者ジェネリクスを導入せず必要な処理を組み込みで提供する既存方針と合わせて整理する。
利用者が定義する汎用マクロやテキスト置換機構の導入まで決めたものではない。

現行 FC には異なる仕組みが混在している。

| 現行の例 | 扱い | 検討点 |
|---|---|---|
| `sizeof`、`bitcast`、`incbin` | 予約語として構文解析する | 呼び出し風の組み込みへ整理すれば、通常の識別子を予約せずに済むか |
| `textmap`、`printf`、`min` / `max` / `clamp`、`asm` | 通常の名前で引く組み込みマクロ | 特別な引数・展開・定数評価を行うことを表記で区別するか |
| `_T(...)` | `textmap` が返す変換器の呼び出し | 組み込みを呼んで得た値の呼び出しも特別表記にする必要があるか |
| `use ...` | モジュールや public 宣言を取り込む | 言語機能の使用許可とは別。現状では文法を切り替えない |

`printf` などは stdio / math の読み込みを要求するが、現状はプログラム内に対象モジュールが存在するかの検査であり、
呼び出し元のファイルが言語機能を明示的に有効化する制度ではない。
参照: [予約語](../internal/syntax/lexer.go)、[組み込み](../internal/sema/builtins.go)、
[名前解決・use の現行仕様](language_reference.md)。

### Zig から参考にする部分

Zig のコンパイラ組み込みは `@` で始まり、サイズ取得は `@sizeOf(T)` と書く。
予約語などを識別子として使うための `@"名前"` は、それとは別の構文。
`@import` はファイル / モジュールを取り込む機能であり、ここで検討する FC の `use` による文法切り替えと同一視しない。
出典: [Builtin Functions](https://ziglang.org/documentation/master/#Builtin-Functions)、
[@sizeOf](https://ziglang.org/documentation/master/#sizeOf)、
[String Identifier Syntax](https://ziglang.org/documentation/master/#String-Identifier-Syntax)、
[@import](https://ziglang.org/documentation/master/#import)（2026-09-20 閲覧）。

### A. `@` 表記と名前の衝突への対策

**2026-09-25 決定・実装済み（feature/v3）**: 字句解析が fc 3 のソースでだけ `@名前` を読み（`@sizeof` / `@bitcast` / `@incbin` /
`@include` は専用のトークン、それ以外は名前に `@` の付いた識別子）、`sizeof` / `bitcast` / `incbin` / `include` を予約語から
外す。名前で引く組み込みは `@名前` でも登録し（`sema.V3Builtins`）、fc 3 のモジュールからは `@` の無い名前では見えない
（`ir.Scope.Hidden`。見つからないときは `@名前` と `fcc migrate` を案内する）。migrate の規則 `at-builtins`、
`TestV3AtBuiltins`。`unittest_run_tests` は `@run_tests`。`cos` は一覧に無いので今のまま。次を `@名前(...)` にする。`@` の名前はコンパイラ専用で、同名の利用者の関数・変数と
衝突しない（`sizeof` / `min` などは普通の名前として使えるようになる）。綴りは今の名前のまま（小文字と `_`。Zig 風の
`@sizeOf` にはしない）。引用識別子 `@"名前"` は設けない。

| FC2 | FC3 | castle / その他の使用数（2026-09-25） |
|---|---|---:|
| `sizeof(T)` | `@sizeof(T)` | 0 / 0 |
| `bitcast<T>(x)` | `@bitcast(T, x)`（`<T>` の構文をなくす） | 10 / 0 |
| `incbin("f")` | `@incbin("f")` | 12 / 0 |
| `include("x.asm")` / `include("x.chr") options(...)` | `@include("x.chr", size: 4096, align: 4096, fill: 0)`（属性は名前付きの引数） | 26 / 8 |
| `asm("...")` | `@asm("...")` | 25 / 12 |
| `textmap("f")` | `@textmap("f")`（返り値の `_T(...)` は普通の定数の呼び出しのまま） | 3 / 0 |
| `min` / `max` / `clamp` | `@min` / `@max` / `@clamp` | 0 / 0 |
| `unittest_run_tests()` | `@` の組み込み（名前は実装時に決める） | 0 / 少 |
| `options(...)` | `@(...)`（§C） | 156 / 70 |

そのまま残す予約語: `function` / `var` / `const` / `struct` / `soa`、型を作る `fn` / `farfn`、`use` / `from` / `as` /
`public`、`true` / `false` / `null`、制御構文（`switch` / `case` / `default` / `loop` / `elsif` など）。
`private` は予約語の表にあるだけで文法では使われていない（使用 0）ので、FC3 では予約語から外す。
`printf` は §9（ログポイント）で扱いを決めるので、この一覧から外す。

- 型を取る組み込み（`@sizeof(T)`、`@bitcast(T, x)`）は、パーサが組み込みの一覧を持ち、名前ごとにどの引数が型かを決める
- FC3 で旧表記（`sizeof(x)` が未定義の関数の呼び出しになるなど）を書いたら、`@sizeof` と `fcc migrate` を案内する診断を出す
- migrate は構文木の位置で書き換える（コメント・文字列の中や、利用者の同名の関数は書き換えない）

```fc
// FC3 の候補。綴り・引数の規則は未確定
var bytes = @sizeof(Player);
const _T = @textmap("font.txt");
@copy(dst, src);
```

- `@name` をコンパイラ専用の名前空間として扱い、利用者の同名関数と衝突・隠蔽しない案。
  普通の `sizeof` / `textmap` などの名前を利用者が使えるようにするかも合わせて決める。
- `@` は「コンパイラが特別に扱う」印とし、コンパイル時専用という意味には限定しない。
  `@copy` のように実行時のコードを出す処理も含み得る。
- 型を渡す `@sizeof(T)` は普通の値引数の関数呼び出しとは異なる。
  FC では型を一般の値にする機能やジェネリクスを導入せず、組み込みに必要な引数規則を定める案。
- 現在の `sizeof(x)` のような式からの型取得を維持するか、型引数と分けるかは未決。
  表記変更だけで引数式の評価回数や副作用の扱いを変えない。
- 普通の関数で提供できる処理はライブラリ関数のままにする選択肢もある。
  `printf`、`cos`、テスト列挙などを全て機械的に `@` 化するかは、機能ごとに判断する。
- `if` / `var` などの基本構文まで `@` 化する案ではない。
  残る予約語との衝突には Zig 風の引用識別子や文脈依存キーワードも比較候補になるが、別途採否を決める。

既存の予約語も見直しの対象とし、低頻度の機能を `@` 側へ移すことで通常の識別子として使える名前を増やす案。
`sizeof` / `bitcast` / `incbin` / `include` などは整理対象の例だが、全てを低頻度と判断したものではない。
採否は castle などでの使用頻度に加え、構文上の役割・読みやすさ・移行の容易さを見て決める。
宣言・文・型引数を持つ機能は、見た目を `@name(...)` にしても通常の関数と同じ意味になるとは限らない。
移すと決めた構文は V3 で共通に扱い、`use` の有無で旧キーワードに戻す方式にはしない。

先行する slice 資料の `@copy` / `@append` / `@slice` も、この表記の検討と揃える。
Zig の大文字小文字をそのまま採用するか、FC の `@sizeof` のような綴りを使うかは未決。

### B. `use ...` による有効・無効

「名前を取り込む」と「機能の使用を許可する」を区別する。
ユーザーの回答により、`use` の有無で文法そのものを切り替える方式は今回の対象外とする。
V3 への移行時に共通の文法を改めることは対象に含む。下表には比較のため残す。
無効な機能を使った場合は診断する案であり、黙って通常の関数として扱ったりコードを削除したりはしない。

| 方式 | 例となる意味 | 主な影響 |
|---|---|---|
| 現行のモジュール import | 通常の関数・型・定数を見えるようにする | 言語の機能制限にはならない |
| 機能の使用許可（確認済みの検討対象） | 構文は共通に解析し、有効化した機能だけ意味解析時に使用を認める | 整形・診断・static if との整合を取りやすい |
| 予約語・文法の切り替え（今回の対象外） | 指定したファイルなどでのみ新しい構文を認識する | ファイルごとの文法差、先読み、import 順序、ツール対応が増える |

構文は共通に保ち、`@` の専用名前空間と組み込みの使用許可を組み合わせる案を検討する。
機能切り替え自体が必要かも含めて検討し、全ての組み込みに有効化宣言を必須にするとは決めない。

検討事項:

- 有効化の単位はファイル / モジュール / プロジェクトのどれか。`use` の再輸出・間接 import で引き継ぐか。
- 既存の `use` と機能指定をどう区別するか。機能名と通常のモジュール名の衝突を避ける方法。
- `#fc 3` による言語バージョン指定、プロジェクト設定の define、static if との役割分担。
- static if の無効側も構文は検査する確認済み方針との整合。
  使用許可方式なら構文を共通に保ち、無効側で使用許可の診断も省く案を取れる。
- ソース内の宣言順や別モジュールの読み込み順で、同じコードの解釈が変わらない規則。
- 有効な機能集合を、整形・エディタ診断・差分コンパイルでも一致させる方法。

具体構文・機能一覧・既定の有効範囲は今後の設計事項。

### C. `options(...)` → `@(...)`（決定済み・未実装）

**2026-09-25 の追加決定（実装済み・feature/v3）**: 文法の `attrs`（`@(...)`、値を省いたキーは true）、`OptionEntry.Bare`、
`PlacementBlock` の前置の形、fc 3 で `options(...)` / `block { } options(...)` を書いたら案内つきのエラー（`syntax.checkVersion`）、
`ir.Options.Flag` / `ir.FlagOptions`（inline / noinline / fastcall / interrupt / volatile / near / farcall / zeropage。値を省けるのは
これだけ）、migrate の規則 `attributes`（`: true` は省く）、`TestV3Attributes`。`options(inline: false)` がキーがあるだけで
inline になっていたのも直った（fc 2 のソースに `false` の指定は無かった）。

- 宣言のまとまりへの既定値は、`block { ... } options(bss: ...)` をやめて前置の `@(...) { ... }` にする（`block` という
  文脈依存の名前も無くす。D の「属性 `{` 宣言 `}`」と同じ考え方）。`@(...)` の後ろが `;` ならモジュールへの指定、`{` なら
  中の宣言の既定値、宣言の後ろならその宣言の属性。今は `bss` だけだが、将来まとめて既定にできる属性を増やしても同じ形。
  2026-09-25 時点で `block` の使用は 0（castle / miku / fclib / bench / test）
  ```fc
  @(bss: "IRQ_DATA") {
      public var b:u8;
      var c:u8 @(segment: "BSS");
  }
  ```
- `include` の属性は `@include("font.chr", size: 4096, ...)` の名前付きの引数にする（§A。`@include(...) @(...)` と
  `@` を 2 つ並べない）
- `fastcall` は FC3 の最初の版では残す（なくすと生成コードが変わり、migrate の ROM 一致の方針と両立しないため。
  廃止は後の版で別に決める）
- `@(inline)` のような `: true` の省略は採用し、`false` の意味を属性ごとにそろえる（今は `Options.Has` でキーの
  有無しか見ない箇所がある）

**2026-09-20、ユーザーが `@(inline:true)` 形式の採用を決定。**
V3 では `options(...)` を `@(...)` に変更する。`@with(...)` / `with(...)` は採用しない。
これは V3 の仕様方針の決定であり、現在の FC2 処理系への実装開始を意味しない。

モジュール設定と、変数・定数・関数などに付ける属性に同じ記法を使う。
今回の決定は表記と適用対象の区別についてであり、設定の意味・評価規則の変更とは分ける。

先行する V3 資料で旧表記が残る場合も、V3 の属性表記は本節に従う。
現行 FC2 の説明・実測用ソースにある `options(...)` は現行記法として維持する。
本書の CHR パディングとバンク名指定の V3 例は `@(...)` に揃えた。各機能の詳細は引き続き未確定。

#### 既存言語との比較と採用理由（2026-09-20）

公式資料を調べたうえで比較し、`@(...)` を採用した。

| 言語 | 参考になる記法・仕組み | FC で考える点 |
|---|---|---|
| [Odin](https://odin-lang.org/docs/overview/#attributes) | `@(link_name="...")` など、宣言の前に属性をまとめる | `@(...)` は実例がある。FC では既存の `key: value` と後置も比較できる |
| [D](https://dlang.org/spec/attribute.html#uda) | ユーザー定義属性に `@(...)` がある | 外見の参考。FC にユーザー定義属性・反射まで導入する必要はない |
| [Rust](https://doc.rust-lang.org/reference/attributes.html) | `#[...]` は後続の対象、`#![...]` は囲んでいる対象に適用 | 属性の対象を明確に区別する考え方が参考になる |
| [Swift](https://docs.swift.org/swift-book/ReferenceManual/Attributes.html) | `@属性名(引数)` | 個別の属性名が目立つが、FC の `@` 組み込み呼び出しと同じ外見になる |
| [Zig](https://ziglang.org/documentation/master/#Grammar) | `align(...)` / `linksection(...)` / `callconv(...)` などの宣言用構文もある | Zig も全てを `@` に統一してはいない。FC で予約語を減らすなら、そのままの模倣はしない |

**`@(...)` を属性の共通表記にする。**
`@name(...)` はコンパイラ組み込みの操作、`@(key: value)` は設定・属性の集合、と見分けられる。
キーを追加するたびに通常の識別子を予約する必要がなく、複数の指定も一組にまとめられる。
`@with(...)` も成立するが、属性の意味を専用の `@(...)` に与えるなら `with` を挟む必然性は小さい。
裸の `with(...)` は予約語または文脈依存構文を増やすため採用しない。

```fc
// FC3: 属性の @ 記法は決定済み・未実装。バンク名・CHR 属性の詳細は検討中
@(bank: "background"); // モジュールに対する単独の指定

var flag:uint8 @(volatile: true);
var vram:uint8 @(address: 0x2007);

function draw():void @(inline: true, segment: "game") {
    // ...
}

include("font.chr") @(size: 4096, align: 4096, fill: 0);
```

宣言属性は、既存の options と同じ後置にする。
宣言が名前・型から始まる並びを保て、短い属性なら一行で読める。長ければ同じ属性位置で改行する。
前置の属性は属性自体が目立つ利点があるが、単独のモジュール指定との読み違いに注意が必要。
前置・後置の両方は提供せず、後置に揃える。

単独の `@(...);` はモジュール設定、宣言に付く `@(...)` はその宣言の属性とする。
単独指定を「次の宣言だけに付く属性」としても解釈する規則は設けない。
モジュール指定の重複や順序、プロジェクト全体のキーとモジュール固有のキーの区別は、現行の意味と照らして別途整理する。

**ユーザーの追加方針: `@(inline)` のように `: true` を省略する形も採用する。**
`@(inline)` は `@(inline: true)` と同じ意味とし、値を明示する形も残す。
省略できるのは真偽値フラグとして定義されたキーだけとする案。`bank` / `address` / `segment` などは値が必要。
`@(inline, segment: "game")` のような混在も同じ規則で表せる。
`false` を指定する場合は、対応する属性で `@(zeropage: false)` のように明示する。
未定義キーや不適切な適用先の診断、属性値の定数評価は意味解析で行う案。
予約語を含み得る属性キーは属性位置の名前として扱い、`inline` などを通常の変数参照と混同しない。
コロンの前後などの整形規則、`options` の予約解除、V3 での旧表記の受理・診断は別途決める。

### V2 からの移行

**仕組み（2026-09-25、ブランチ `feature/v3`）**:

- 文法バージョンはソースごとに先頭行の `#fc 2` / `#fc 3` で選ぶ（無ければ移行期間は fc 2 = `syntax.DefaultVersion`）。
  コンパイラは両方を受け付け、1 つのプログラムに混ぜられる（`syntax.File.Version` → `ir.Module.Version`。版で意味が
  変わる規則はモジュールの版で分岐する）
- `fcc migrate [-l|-w|-d] <file.fc> ...` が fc 2 のソースを fc 3 に書き換える（`internal/migrate`）。fc 2 として解析し、
  規則（`migrate.Rules`）がトークンの位置に対する置き換え（`Edit`）を足す。構文木を印字し直さないので、コメント・空行・
  書式は残る。最後にプラグマを `#fc 3` にし、fc 3 として解析し直せなければエラー（規則の不具合）。fc 3 のソースは
  そのまま（何度かけても同じ）
- **文法を変えるときは、migrate の規則とテストを一緒に足す**。`internal/driver/migrate_test.go` が bench / golden のテスト
  プログラムと fclib を migrate して fc 3 としてビルドし、fc 2 のままのビルドと ROM・バイナリがバイト単位で一致することを
  確かめる（`TestMigrateGoldenPrograms` / `TestMigrateBench`）。castle / miku は実プロジェクトも fc 3 になったので、fc 2 の版の
  ソースと `TestMigrateExamples` は 2026-09-27 に削除した。
  意味を変える変更（`int` の幅など）でも、migrate した結果が同じコードになることを要求する
- 起点は main の 3625001（fc 2 の最後）。この時点の fc 2 のソースは全部 migrate で fc 3 にできることを保つ

将来の migrate では、予約語の構文と組み込みへの参照を特定して書き換える。
利用者の同名関数・ローカル変数を、単なる文字列置換で `@` 付きにしない。
`textmap` が返す `_T` のような値、型 / 式を受ける構文、モジュールの別名も区別する。
機能宣言を導入する場合は、その追加位置・適用範囲も移行対象になる。
既存の予約語から `@` 表記への変更と、モジュール・宣言に付ける `options(...)` の変更も migrate の検討に含める。
属性の対象を構文木で特定し、キーと値、宣言との対応、コメントを保つ方法を検討する。
この節は V3 の検討追加のみで、現行の予約語・組み込み名・`use` の意味は変更しない。

## 6. interrupt の既知の問題（記録のみ・修正しない）

記録: 2026-09-20。これは現行処理系の問題であり、V3 で追加する機能ではない。
**ユーザー方針: 割り込み処理には厳密なタイミングの要求があり、FC の interrupt 属性はほぼ使わない想定。
問題は記録に留め、今回は修正しない。修正・自動退避・新しい診断の実装を開始する指示ではない。**

### 演算ルーチンの共有作業領域を保護していない

`options(interrupt: true)` を付けても、割り込み関数やその呼び出し先で、
乗算・除算・剰余のランタイムルーチン呼び出しは禁止されない。
通常の変数同士の掛け算などは、共有領域 `reg` に引数を書き、`__mul_8` / `__mul_16` 等を呼ぶ。
標準の割り込み入口は CPU の A・X・Y を退避・復帰するが、この `reg` は保存しない。

例えば、通常処理が `reg` に演算の入力や途中結果を置いている間に割り込みが入り、
割り込み側でも同じ作業領域を使う演算を行うと、通常処理の再開時に値が壊れている可能性がある。
毎回発生するとは限らず、割り込みが入る位置と実際の生成コードに依存する。

現行の interrupt 対応は、FC 関数の静的フレームを他の関数と重ねず、到達先の stack ABI を拒否するもの。
演算ルーチンはコード生成で暗黙に呼ばれるため、このフレーム保護だけでは共有 `reg` の破壊を防げない。
**したがって interrupt 属性が付いているだけで、生成される全処理が割り込みに対して安全になるわけではない。**
ソースを追って確認した問題であり、今回、割り込みを注入する再現試験は行っていない。

`x * 4` など、定数畳み込みやシフト命令への展開で演算ルーチンを使わない場合は、
この共有領域の問題とは区別する。ただし、それだけで割り込み処理全体の安全性を保証するものではない。

### ポインタの読み書きも共有作業領域を使う（2026-09-26 追記）

`reg` を使うのは演算ルーチンだけではない。ゼロページに無いポインタ変数を通した読み書きは、毎回ポインタを `reg` に写して
`(reg),y` で読み書きする（`r = *p;` が `lda p / sta reg+0 / lda p+1 / sta reg+1 / ldy #0 / lda (reg),y`。2026-09-26 に生成コードで確認）。
通常処理はポインタを触るたびにこの形を使うので、割り込み側でポインタを 1 回でも使うと、通常処理の `reg` を壊しうる
（まれにしか起きず再現しにくい）。割り込みの中で安全に書けるのは、グローバル変数・配列の直接の読み書き、定数の添字、
シフトに展開される定数の乗算など、`reg` を使わない単純な処理だけ。ポインタ・`*` `/` `%`（ランタイムの呼び出し）・関数ポインタの
呼び出し・mem などの関数は避ける。castle と miku は NMI を asm（`ppu.asm`）で書いている。
**割り込みは asm で書く前提とする**（§10.5 の決定: 未定義なら空のハンドラを作り、stdio の NMI とぶつからないようにするだけにし、
fc で割り込みを書きやすくする方向は優先しない）。

将来必要になった場合の候補として、割り込みとその到達先で共有領域を使う暗黙の呼び出しを診断する方法、
専用領域を使う方法、必要な作業領域を退避する方法がある。どれも未採用で、現時点では着手しない。
対象は直接書いた掛け算だけでなく、呼び出し先・暗黙のランタイム処理まで確認する必要がある。

参照: [乗除算・剰余のコード生成](../internal/codegen/arith.go)、
[割り込み入口と演算ルーチン](../share/runtime.asm)、[呼び出し解析・フレーム配置](../internal/frames/frames.go)。

## 7. `int` の廃止と整数型名の整理

**2026-09-25 決定・実装済み（feature/v3）**: `types.IntTypeNames` / `V2IntTypeNames`、`Universe.NamedIn`（fc 3 は短い名前だけ）、
`ir.Scope.Reserved`（fc 3 のモジュールで u8 などの宣言を禁止）、migrate の規則 `int-types`、`TestV3IntTypes`。fc 2 でも短い
名前を使える（fc 2 のソースに同名の識別子は無かった）。

- 正式名は短い `u8` / `i8` / `u16` / `i16`。エラーメッセージや IR のダンプの表示もこれにそろえる
- FC3 では古い名前（`int` / `uint` / `sint` / `int8` / `int16` / `uint8` / `sint8` / `uint16` / `sint16`）を全て受け付けず、
  `fcc migrate` を案内するエラーにする（別名は残さない）
- `u8` / `i8` / `u16` / `i16` は FC3 では宣言できない名前にする（型名は型の位置でスコープより先に引くので、同名の
  宣言は黙って隠れてしまう。2026-09-25 時点で既存ソースに同名の識別子は無い）
- migrate: `int` / `uint` / `int8` / `uint8` → `u8`、`sint` / `sint8` → `i8`、`int16` / `uint16` → `u16`、`sint16` → `i16`。
  構文木の型名（`NamedType`。`sizeof(T)` の引数も型）だけを書き換え、幅と符号は変えない
- `char`（§8）は扱わない（文字として使っている `int` も一律に `u8`。char は導入するときの別の作業）

以下は決定前の検討の記録。

**ユーザー方針: V3 では幅・符号が曖昧な `int` を廃止する。**
正式な表記は `sint8` / `uint8` を使うか、短い `i8` / `u8` にするかを検討する。
当初の記載の `int8` は `sint8` の誤記とユーザーが訂正済み。
符号付き / 符号なしを表す名前の選択であり、既存 `int8` をそのまま符号付きへ読み替える案ではない。

| 役割 | 長い表記の候補 | 短い表記の候補 |
|---|---|---|
| 符号付き 8 ビット | `sint8` | `i8` |
| 符号なし 8 ビット | `uint8` | `u8` |
| 符号付き 16 ビット | `sint16` | `i16` |
| 符号なし 16 ビット | `uint16` | `u16` |

16 ビット側も一貫した表記にする候補として併記した。正式名や別名の併存は未決。
現行の `int` / `uint` / `int8` は `uint8` の別名、`int16` は `uint16` の別名。
将来の migrate は元の幅・符号を保ち、`int` を `uint8` または `u8` に変換する必要がある。
`uint` / `sint` / `int8` / `int16` など、残る別名の廃止・互換受理も同時に整理する。
型名の変更に、整数リテラルの型推論・数値変換・演算の意味の変更を紛れ込ませない。
参照: [基本型の定義](../internal/types/types.go)、[現行の型仕様](language_reference.md)。

先行する V3 資料の `uint8` / `uint16` 等は、型名を決定するまでは説明用として維持する。
現行 FC2 のソース・実測例は現行の型名のまま扱う。

## 8. `char` 型の導入

**ユーザーの検討方針: 基本的には uint8 と同じで、文字列として出力するときの扱いだけを変える char 型を導入する。**
8 ビットの格納・数値的な操作を基本とし、Unicode の一文字全体を表す多バイト型にはしない。
数値出力と文字出力を、出力側が型から区別できるようにすることが目的。

```fc
// 構文 / API の利用イメージ。@print の採否は §9 で検討
var n:uint8 = 65;
var c:char = n as char;
@print(n); // 数値として表示する案: 65
@print(c); // 文字として表示する案: ASCII を使う出力先なら A
```

格納表現は同じでも、完全な型別名として区別を消すと、出力時に char かどうか判断できなくなる。
コンパイラ内では区別を残す案。これだけで実行時の型タグ・追加の格納領域を要求するものではない。
表示結果は文字コード表に依存するため、char だけで ASCII・UTF-8 のバイト・ゲーム独自コードを自動判別しない。

今後整理すること:

- `char` と符号なし 8 ビット整数の代入・比較・算術の互換性。式を計算した後も char を保つか。
- 文字列リテラル / `textmap` の要素型を char にするか。char 一要素のリテラル表記を設けるか。
  現行の文字列記法の意味は今回変更しない。
- `[]const char` を文字列出力に使い、`[]const uint8` をバイナリとして扱うか。
  byte slice / char slice の変換と既存のメモリ API との接続を、余計なコピーなしで表す方法。
- 文字の数、格納バイト数、ゲーム文字コードの数、表示幅の区別。
  UTF-8 の複数バイトを順に char として送る場合も、表示側がどう組み立てるかを決める。
- 終端 0 と長さは、char の導入だけでは決まらない。通常 slice / sentinel slice の議論と合わせる。

先行の文字列 API 資料は `[]const uint8` を仮定しているため、char の採用範囲が固まったら調整する。
今回の追加だけで全バイト配列を char 配列に置き換えるものではない。

## 9. `printf` の見直しと NES エミュレータのログポイント

### 決定した計画（2026-09-25）

以下を決めた。後ろの「ユーザーが求めるもの」以降は検討の記録。

- **名前と構文:** `@log("HP: {} / {}", hp, max_hp);`（文として書く。値を返さない）。
- **書式:** `{}`（順番）/ `{0}`（位置指定）。`{:x}` / `{:X}` / `{:04x}` / `{:b}` / `{:c}`（文字）のように見せ方を `:` の後ろに書く。
  `{{` / `}}` は波括弧そのもの。型はコンパイラが知っているので、printf の `%d` のような型の指定は無い。
  既定の見せ方は、整数は 10 進、bool は true / false、enum はメンバー名（`{:d}` で数値）、ポインタは `$1234`。
  引数の数・位置番号・型に合わない指定はコンパイル時のエラー。名前の埋め込み（`"{hp}"`）は後で足せるようにしておく。
- **NES 側のコストはゼロ:** 命令・サイクル・ROM のバイト列は、`@log` があってもなくても同じ。
  `@log` は IR の命令にせず「次の命令の直前」の注釈として持ち、最適化で命令が消えたり融合されたりしたら後ろの命令へ引き継ぐ。
  注釈は最適化の判断（隣り合う命令・ラベルの有無・値の生存）に数えない。
- **値:** グローバル変数・定数・struct のフィールド・定数添字の要素に加えて、**ローカル変数・引数も最初から**扱う。
  ローカルはレジスタ割り付けの結果から、その地点の所在（A / X / Y・ゼロページ・静的フレーム）を記録する。
  その地点で値が死んでいる・取れない場合は「?」と表示し、コンパイル時に警告する。値を生かすためにコードは変えない。
  副作用のある式（関数呼び出し・I/O の読み出し）は書けない。
- **成果物:** `-g` のときだけ、ROM の隣に `game.fclog.json`（地点のアドレスと PRG ROM 上の位置、書式、値の所在と型）と
  Mesen 2 用の `game.fclog.lua` を出す。Lua は `emu.addMemoryCallback`（exec）でフックし、`emu.convertAddress` で
  PRG ROM 上の位置まで照合してから（同じ CPU アドレスに別のバンクが載るため）、`emu.read` で値を読んで整形する。
  `-g` 無しなら `@log` は完全に無視される。
- **自前のエミュレータ:** internal/nes も同じ json を読んで表示する（Mesen の無い環境での自動テストと `fcc run`）。
- **検証:** `@log` 入りと `@log` を取り除いたソースの ROM がバイト単位で一致すること。castle / miku と fuzz でも確かめる。

段階:

| 段階 | 内容 |
|---|---|
| 1 | 構文・書式の解析と検査、注釈の仕組み（最適化のパスを通しての引き継ぎ）、グローバル・定数・ローカル・引数、enum の名前表示、json / Lua / 自前エミュレータ、ROM 一致の検証 |
| 2 | ポインタの参照先・slice の中身・文字列（`*u8` を 0 まで読む。バンクの状態に注意）の表示、名前の埋め込み `"{hp}"` |
| 3 | 固定小数点の表示、条件付きログ、ホスト側の間引き（同じ地点を毎フレーム出さない）など |

最初の難所は注釈の引き継ぎ。SSA の値の付け替え・写しの統合・融合などのパスが注釈の中の値も書き換える必要があるが、
それを「使用」と数えると生存区間が延びて生成コードが変わる。使用に数えない弱い参照として扱う仕組みを最初に作り、
ROM 一致の検査で確かめる。

#### 段階 1 の実装（2026-09-25）

- 注釈は `ir.Op.Logs`（`ir/log.go`）。命令を消すのは `ir.DropOp`（次に実行される命令へ: 無条件ジャンプなら飛び先、
  ラベルとラベルの間なら前のラベル）、置き換えは `ir.ReplaceOp`、融合は `ir.MergeDrop`、到達しないコードは
  `ir.DiscardOp`（注釈も捨てる）。命令列を作り直すパス（ywalk / split / ループの回転・展開・インライン展開）は自分で
  注釈を引き継ぎ、取りこぼしはパスごとの `ir.KeepLogs` が拾う。
- ジャンプの連鎖の畳み込みで素通りしたブロックの注釈は、無条件ジャンプならそのジャンプへ、条件分岐なら
  「成立したときだけ」の注釈（`LogPoint.OnTaken`）へ。コード生成が飛び先に地点を置き、直前がその分岐のときだけ出す。
- SSA は注釈の引数を、その地点の版の定数・コピー元に書き換える（生きているか同じブロックに定義があるときだけ）。
  死んだ代入を消した変数は `Value.LogStale`、更新を別の変数に置き換えた変数（ywalk のポインタ）は `LogNoValue`。
- コード生成は、IR のコメント行に印を付け、ピープホールの後でラベルに置き換える（その関数の `@` ローカルラベルは
  普通のラベルに書き換える。バイト列は同じ）。値の所在は定数・メモリ（番地は `sym = 式` を dbgfile で解決）・
  スタックフレーム（S + X）・レジスタ（常駐・割り付け）・バイトごと（split）。生きていない値は「直前に触った」
  （分岐・ラベル・呼び出しを越えずに遡って触っていて、間に同じ場所を書く値が無い）ときだけ。付け替えた注釈では
  生きている値だけ。取れなければ「?」とコンパイル時の警告。
- 合流点の地点（同じ番地の後ろのラベルへほかの経路から来る）は、この地点の経路の直前の命令（上から落ちてくる命令と、
  前の同じ番地のラベルへの分岐）を実行した直後だけ出す（`prevs`。Mesen の Lua は、直前が条件分岐なら 1 命令分の
  サイクル差、jsr ならスタックポインタが戻ったこと、ほかは印だけで判定。emu は rts の後を戻り先の jsr の後とみなす）。
  ループの直前の `@log` が周ごとに出ない、何も出さない else の `@log` が then の後に出ない。ラベルの注釈は
  「ラベルの前」の地点なので、ジャンプの連鎖で飛び先のラベルの注釈は拾わず、ループ展開は 2 つめからの写しのヘッダの
  先頭のラベルに注釈を写さない（`TestLogLoopEntry`）。
- 検証: `TestLogZeroCost` は fuzz のプログラムの全部の文の前に、見えている変数を全部出す `@log` を置いて、ROM と出力が
  変わらないこと（-O 0 / -O 2）を確かめる。値は -O 0 と -O 2 で比べてログに出す。

既知の制限（精度）: -O 2 で文の命令がすべて消えたとき、地点は次の命令へずれる。丸ごと畳まれたループ（本体が空）の
写しは同じ命令に集まり、順番や回数がずれることがある。`if` の分岐の最後の `@log` は、分岐の後ろの地点として警告する。
Mesen 2 の Lua（`.fclog.lua`）は MesenCE 2.2.1 の testrunner で emu と同じ表示になることを確かめている
（`internal/nes` の `TestMesenLog`。-O 0 / 1 / 2）。未確認: 切替バンクの地点（PRG ROM 上の位置の照合）。
Lua の重さ: `emu.getState()` は 1 回 100 マイクロ秒ほどかかる（毎回呼ぶと 1 フレーム 1000 回の地点で 10 倍遅い）ので、
レジスタ・スタックの値と、直前が条件分岐・jsr の合流点のときだけ呼ぶ。それ以外は 1 回数マイクロ秒で、
Mesen の exec コールバック自体のほうが重い（castle に毎フレームの地点を置いて 1 割ほど）。

### ユーザーが求めるもの

**対象は、実機向け ROM を動かす Mesen 等の NES エミュレータ。FC の CLI emu の出力改善が主目的ではない。**
NES 側で数値の十進変換・文字列連結などを行わず、Lua 等のホスト側で表示文を構成したい。
さらに、**特定の命令位置に PC が来たことをエミュレータ側で検出し、NES 側の追加コストなしに出力する形が理想。**
通常の出力関数というより、実行を止めずに観測するデバッガのログポイントとして検討する。

当初の MMIO による通知案も比較対象として残すが、値の転送や通知に NES の命令を使うため、
ゼロ追加コストを目指す主案は PC / 実行アドレスへのフックとする。
ゲーム画面に表示する文字列の生成と、ホスト側のデバッグログは別の用途として扱う。

### Mesen 2 での実現可能性

Mesen 2 の公式 Lua API 資料には、`emu.addMemoryCallback` と `emu.callbackType.exec` があり、
指定アドレスで CPU が命令を実行し始めた際のコールバックを登録できる。
`emu.getState`、`emu.read`、`emu.log`、CPU アドレスと ROM / RAM アドレスを対応付ける `emu.convertAddress` もある。
このため、命令位置を観測し、値を読んでホスト側でログを作るための基本機能は揃っている。
出典: [Mesen 2 の Lua API 定義](https://github.com/SourMesen/Mesen2/blob/master/UI/Debugger/Documentation/LuaDocumentation.json)
（2026-09-20 閲覧）。ここでは資料による確認のみで、実際のフック動作試験は行っていない。

資料を踏まえると、既存命令への観測だけなら、ログのために NES 側の命令やサイクルを増やさない設計が可能と考えられる。
これはホスト側の処理負荷もゼロという意味ではない。Lua の処理・表示による実時間の負荷は発生する。

### 主案: 命令を出さないログ注釈と、ホスト用メタデータ

```fc
// FC3 の利用イメージ。@log の名称・構文は未決
hp -= damage;
@log("HP: ", hp); // この地点の値をホストで表示。NES 側の関数呼び出しにはしない案
```

将来の構成案:

1. ソースのログ地点を、最適化後の既存の命令位置へ対応付ける。
   必要なラベルはアドレスを表すだけとし、ログのための NOP・JSR・MMIO 書き込みを生成しない。
2. ログ地点と表示する値の所在・型、文字列テンプレートを、ROM 外のメタデータまたは Lua に出力する。
   リンク結果から最終アドレスを解決する。
3. エミュレータはその命令位置にフックを登録し、レジスタ・メモリを読み、Lua 側で表示する。

最初の候補は関数入口などの安定した命令位置と、グローバル変数・定数の観測。
任意のソース行や最適化されたローカル変数へ広げるほど、位置情報・値の復元が難しくなる。
別案として、FC ソースに注釈を書かず、シンボル名を使って Lua / デバッガ側だけでログポイントを設定する方法も比較する。
通常の `printf` のように引数を CPU 上で評価して渡す API とは契約が異なるため、名前と意味を区別する。

### ゼロ追加コストの条件と未決事項

- **値の所在:** ローカル変数が A / X / Y、静的フレーム、定数のどれかを地点ごとに伝える。
  最新値がレジスタにありメモリ側は古い場合もあるので、変数の固定アドレスだけでは十分ではない。
- **最適化:** 消えた値や命令位置を観測するために、変数の寿命延長・退避・最適化の抑制を行えばコストが変わる。
  ゼロ追加コストのモードでは、復元できない値は診断または unavailable とする案を基本にし、暗黙に命令を追加しない。
- **地点の意味:** 命令の前 / 後、分岐の経路、inline 展開された複数の地点、同じアドレスに重なる注釈を整理する。
  ソース上の注釈と、最適化後に実行される地点が常に一対一とは限らない。
- **副作用:** ログ用に FC 関数を実行したり、I/O を通常の CPU アクセスとして読み直したりしない。
  ホスト側で再現可能な純粋な式と観測可能な値に範囲を限定し、副作用を起こさないデバッグ読み取りを使う。
- **バンク:** 同じ CPU アドレスに別の PRG バンクが載る。CPU の PC だけでなく物理 ROM 位置 / バンクを識別する。
  Mesen の memoryType 指定やアドレス変換をどう使うか、対象版で確認する。
- **表示:** 数値の幅・符号・char・文字列の長さと文字コードをホストへ伝える。
  ROM の文字列を読む場合は、その地点のバンク状態も考慮する。
- **成果物:** ROM とログ用情報が同じビルドであることを確認し、リンク後のアドレスを用いる。
  ログ有無で ROM のバイト列と NES 側の実行サイクルが変わらないことを、将来の検証条件にする。

上記は設計上の課題で、現状の FC のデバッグ情報が全てを表現できるという意味ではない。
ログ地点を理由に interrupt の共有作業領域問題（§6）の修正や、NES 側の演算処理を追加しない。

### 比較案: MMIO 通知とホスト側整形

PC フックが使えない場合や、明示的なイベント送信が必要な用途では、
イベント ID と値を所定領域に書き、最後の通知書き込みを Lua 等が検出する案も残す。
ホスト側が ID に対応するテンプレートで文を作るため、NES 側の文字列組み立ては省ける。
ただし値の格納・通知命令のコストは発生し、主案のゼロ追加コストとは区別する。
イベント形式・通知アドレス・対応エミュレータは未決。主案から無断でこの方式へ切り替えない。

### 現行の printf と関連資料

現行 FC の `printf` は C 形式の書式文字列を解釈する関数ではなく、
引数の型に応じて `stdio.print` / `print_int16` を呼ぶ組み込みマクロ。
一般的な出力 API の代替として `@print(...)` やライブラリ関数も比較するが、PC ログポイントとは分けて検討する。
利用者ジェネリクスや文字列補間の導入を前提にはしない。

CLI の emu 用 stdio は既にメモリマップ I/O を経由してホスト側で表示するが、今回の主対象ではない。
その専用アドレスや出力プロトコルを NES エミュレータへそのまま流用する案ではない。
参照: [printf の展開](../internal/sema/builtins.go)、[emu 用 stdio](../fclib/emu/stdio.fc)。
既存の [Mesen 自動プレイ試験](../internal/nes/mesen_test.go) にも、Lua がゲームのメモリを読みログを組み立てる例がある。
これは検討材料であり、上記の PC ログポイント生成が実装済みという意味ではない。
今回の作業は V3 メモの更新のみ。処理系・ROM・エミュレータ・Lua スクリプトは変更しない。

## 10. 一般的な用途で不便な仕様（2026-09-26 調査）

const の表の slice（`{items: [{1, 4}, …]}`）が通らなかった件と、`var p = &TAB[i]` が const を引き継がなかった件の後に、
仕様全般を「普通に書いたら困るもの」の観点で調べた。4 つの分野（型・式、宣言・データ、制御構文・関数・モジュール、
fclib と NES の開発の流れ）で、小さなプログラムを `fcc run`（-O 2 と -O 0）・Mesen で実際に動かして確かめた。
やることの一覧（優先度つき）は [roadmap.md](roadmap.md) の「v3: 一般的な用途で不便な仕様」。ここには再現と直す方向を書く。
優先度は 高 / 中 / 低。

**決定（2026-09-26）:** 配列リテラルの要素がアドレスになる件、ポインタの加減算の単位、コンパイラが落ちる・asm が壊れるもの
（case の文字列、インライン展開した関数の中の const 表、ローカルの `[?]` の配列）は修正する。名前付きの文字列定数の長さは
互換性のため今はこのまま（後で直す候補）。整数の変換・拡張は保留（10.2 に検討の経過）。

### 10.1 コンパイラ・ライブラリのバグ（誤った結果・クラッシュ・壊れた asm）

- **実行時の変数を要素に持つ配列リテラル**（高）: `var a:[2]u8 = [n, m];` が変数の**アドレス**の表になる
  （`g(3, 4)` が 34 でなく 28。-O 0 も同じ。fc 2 の頃から）。要素が式（`[n, n + 1]`）なら「constant value required」、
  代入・引数・struct のフィールドの中（`pts = [a, a]`、`sum([a, 1])`、`{items: [a, 2]}`）では
  `panic: invalid location none of {a}`、グローバル変数・再帰関数の中では ca65 のエラー。const のポインタの表（`[S, T]`）の
  規則で名前がアドレス定数として通っている。直す方向: 要素が整数型なら名前をアドレスにしない。struct リテラルと同じく
  実行時に組み立てる（`[n, n + 1, n * 2]` も書けるようにする）
- **switch の case に文字列**（高）: `case "A":` で `panic: invalid v {$2}`（`fcc check` でも）。C の `case 'A':` の
  つもりで必ず踏む。case の値が整数の定数かを sema で検査する
- **範囲外の整数リテラル**（高）: `var y:i8 = 200; var w:i16 = y;` が -O 2 で -56、-O 0 で 200。型に合わせるときに正規化
  されず、最適化で結果が変わる。範囲外の定数はエラー（下の「暗黙の縮小」と一緒に）
- **スカラーの const の型の注釈が無視される**（中）: `const B:u8 = 300;` が 2 バイト・300、`const F:u8 = -1;` が i8。
  `guessType` の結果（大きいほう・符号付き）を使っている。宣言した型にして、範囲外はエラー
- **struct・配列・ポインタに算術・順序比較**（中。**2026-09-26 決定: struct・配列の `==` / `!=`（中身の比較）は正式な仕様に
  する（リファレンス §2.1 の「`==` はない」を直す）。それ以外はいったんエラー**）: `a + c`（struct）、`a < c`、`x + x`（配列）、`pa * pc`、`!a`、`if (a)` が
  多バイト整数として通る。算術・ビット演算・`<` は整数と bool だけ、ポインタは ± 整数だけにする
- **インライン展開した関数の中のローカル const 表**（高）: `function f(i:u8):u8 { const T = [5, 6, 7]; return T[i]; }` が
  -O 1 / 2 で ca65 の `Symbol 'T' is undefined`（`.proc` のローカルラベルを展開先から参照する）。モジュールで一意な名前で出す
- **`var a:[?]u8 = [1, 2, 3];`（ローカル）の領域が確保されない**（高）: -O 2 でほかのローカルを壊し、-O 0 で ca65 の
  Range error。`@sizeof(a)` は `size is not known`。型を省いた `var a = [1, 2, 3]` は動く。初期値から長さを決める
- **`const X:[4]u8 = [1, 2];` の宣言の長さが無視される**（中）: `@len(X)` が 2 で、`X[2]` は隣のデータを読む。ローカルの
  `var` は 0 で埋め、struct のフィールドはエラーで、3 つとも違う。0 で埋める（またはエラー）にそろえる
- **素のブロック `{ … }` がスコープを作らない**（中）: `{ var x = 2; }` の x が外から見え、`{ var t = 1; } { var t = 2; }` が
  `t already defined`。`if` / `for` の本体は正しい。`sema/hlc.go` の `*syntax.Block` でスコープを積む
- **名前付きの文字列定数を slice にすると終端の 0 が入る**（高）: `const NM = "joe";` の `@len(NM)` と `f(NM)`（`[]const u8`）
  が 4、`f("joe")` は 3。描画ルーチンが 0 まで描く。文字列から作った配列定数には印を持たせ、slice にするとき 0 を除く。
  **互換性のため今はこのまま、後で直す候補（2026-09-26）**
- **ポインタの加減算がバイト単位**（高）: `var p = &w[0]; p += 1;`（`w:[4]u16`）が 1 バイトずれて読み、`o++`（struct の配列）は
  途中のバイトを指す。`p[1]` は要素の大きさを掛けるので `p[1]` と `*(p + 1)` が違う。仕様（language_reference §6「C と同じ」）
  とも食い違う。C と同じく要素の大きさを掛ける（1 バイトの要素は今と同じ）。ポインタ − ポインタは要素数の整数
- **u16 の可変量シフトが -O で通ったり通らなかったり**（中）: `w <<= n` が -O 2 では n の定数伝播で通り、-O 0 では
  `shift of 2-byte value by non-constant count is not supported`。ランタイムのルーチンで対応するか、判定を -O から独立に
- **`use` の検索がソースのディレクトリでなく作業ディレクトリ基準**（中）: `fcc run m1/main.fc` で `use a;` が
  `file a.fc not found`（language_reference §1.4 はソースのディレクトリ）。CLI の `Dir` の既定をソースのディレクトリに
- **NES の `stdio.print_int16` が壊れている**（高）: `_stdio_print_int8` が文字列を `S+0,x` に置いて `jsr _stdio_print` するが、
  `print` は fastcall（`FC_FASTCALL_REG`）。数値でなく前の文字列が出る。16 進の表も `…,66,67,67,69,…`（D が C）。
  NES の `printf` の整数・`exit()`・unittest の出力が全部壊れる。NES の stdio にテストを付ける
- **`mem.zero` / `mem.compare` / `stdio.ppu_put` の長さ 0 が 256**（中）: `iny; cpy; bne` のループ。計算した長さが 0 のとき
  RAM を 256 バイト消す（`mem.set` は正しい）。ループの前で 0 を検査する
- **printf が slice・struct・関数ポインタを黙って捨てる、符号付きを符号なしで出す**（中）: `printf("[", s, "]")` が `[]`、
  `printf(-5)` が 65531、enum は `argument 1 of print_int16` の分かりにくいエラー。扱えない型は printf の名前でエラー、
  slice は長さ分、符号付きは符号付きで（`@log` は正しい）
- **`@(address:)` / fc.toml の `[ram.*]` が fc 自身の領域と重なっても検出しない**（高）: `[ram.oam] start = 0x0200` と
  `FC_FARCALL` が同じ $0200、`@(address: 0x10)` が `reg` と重なる、miku の `@(address: 0x60)` は FC_SZP の中。OAM を $0200 に
  置くのは NES の定番。fc の ZP / SRAM と照合してエラー（§3 の「重ならないかを検査する」は未実装）
- **`@(farcall)` を忘れると切替バンクの関数を普通の `jsr` で呼ぶ**（高。**2026-09-26 決定: fc.toml に切替バンクがあれば far call を
  既定で有効にする。トランポリン・状態変数・起動時の初期化はマッパーのプロファイルから自動で入れ（10.5 のマッパーの定型文と一緒）、
  手動で管理するモジュールは今の `@(near)` で外す。再現（2026-09-26）: MMC3 の bank a / b（どちらも $8000）の `get` を farcall 無しで
  呼ぶと `mb.get(1)` が bank a のコードを実行して 21 でなく 11。castle は `mmc3.fc` の `@(mapper: "MMC3", farcall)` で有効にしている**）: fc.toml の MMC3 で `[bank.a]` / `[bank.b]`（どちらも
  $8000）の関数を main から呼ぶと、両方 `jsr` で警告なしに通る。切替バンクがあれば farcall を既定にするか、別モジュールの
  切替バンクへの直接の呼び出しをエラーに
- **`@(symbol: "_interrupt")` の NMI のフレームが main の呼び出しと重なる**（中）: symbol だけでは interrupt 扱いにならず、
  `F_interrupt` が `F_main_*` と同じ場所。`@(interrupt)` を付けても main と NMI の両方から呼ぶ関数は同じフレームを共有する
  （§6 は演算ルーチンの `reg` だけを記録）。`_interrupt` / `_interrupt_irq` の symbol は interrupt を暗黙に、両方から届く関数を警告
- **値が飛び飛びの enum の表**（中）: `enum E { A = 0, B = 5, C }` で `[@len(E)]` の表を `T[.C]` で引くと範囲外を読み、
  -O で値が変わる。定数の添字の範囲を検査する（下の「定数添字の範囲外」と同じ）

### 10.2 整数と式

- **整数の拡張が無い**（高）: 結果の型はオペランドの型だけで決まり、代入先が広くても 8 ビットで折り返す。警告も無い。
  `var d:u16 = a + b;`（200 + 100）が 44、`score += pts * 10;`（u16 += u8 × 10）、`(x + y) / 2`、`var diff:i16 = x - 5;`。
  `x * 100` は折り返し、`x * 300` は折り返さない（リテラルの大きさで型が変わる）。直す方向: 代入先・相手の型を式の中へ
  伝えて広げる（6502 のコストは 16 ビットが要る所だけ）。無理なら、8 ビットの + − * << の結果が 16 ビットの文脈に入るとき警告。
  今の仕様は「int が 8 ビットの C」と同じ（C も代入先には合わせない。32 ビット int の C で `int64_t d = a + b;` が 32 ビットで
  あふれるのと同じ構図で、MSVC の C26451 や clang-tidy の bugprone-implicit-widening-of-multiplication-result が警告で補う）。
  **保留（2026-09-26）。以下は一度決めかけた案（検討の経過として残す）:**
  - **式全体を「代入先の型」と「式の中で一番広い型」の広いほうで計算する。** 代入先が無く中身が全部 8 ビットなら 8 ビットのまま
    （int = 8 ビットの C と同じ。ゲームの大半の式は速さが変わらない）。`var d:u16 = a + b` は 300、`score += pts * 10`（score:u16）、
    `ppu.put(0x2000 + y * 64, …)`（引数の型と `0x2000`）、`var addr = 0x2000 + y * 64`（式の中の `0x2000`）は 16 ビットで計算する
  - 1 つの式の区切り: 代入・初期化・引数・`return`・struct / 配列の要素の右辺それぞれ。比較は両辺をまとめて 1 つの式。
    呼び出しの中の引数（引数の型で別に決まる）、添字、シフトの右辺には広がらない。`as` も区切り（`(a + b) as u8` は中を 8 ビットで、
    `a as u16 + b` は明示的に広げる）
  - **8 ビットで計算して途中の上の桁を捨てる形は警告**: `var cx:u8 = (x1 + x2) / 2`（200, 100 で 22。C は 150）、`hp * 64 / max_hp`
    （100, 200 で 0。32 のはず）、`(v * 3) >> 2`（120 で 26。90 のはず）、`(a * b) >> 8`、`if (a.x + a.w > b.x)`（250 + 16 が 10 になる）、
    `if (px + dx >= 240)`。値の範囲（定数・`& m`・`% n` など）で収まると分かるものは警告しない。消す書き方は
    `(x1 + x2) as u8 / 2`（8 ビットのつもり）と `(x1 as u16 + x2) / 2`（広げる）。`u8 = u8 + u8` のような `+ - * << & | ^` だけの式は
    下位 8 ビットが同じなので警告しない
  - 注意: 式を分けると結果が変わる（`var t = a + b; var d:u16 = t;` は 44）。C の int の拡張と同じく「1 つの式の中だけ」と文書に書く
  - 効率（2026-09-26 に生成コードで確認）: `m as u16 + n` は 8 ビットの加算に 3 命令（`lda #0 / adc #0 / sta`）足すだけで最適。
    `m as u16 * n` は 16×16 の `__mul_16`（16 回のループ）を呼ぶ（8×8→16 の `__mul_8t16` は「ほぼ未実装」で使われていない）。
    `((m as u16 + n) / 2) as u8` は 10 命令ほど（`clc / lda / adc / ror a` の 4 命令にできる）。どちらも最適化の候補
  実際のコードでの頻度（一時的な検査で数えた）: 8 ビットの + − * << の結果が
  16 ビットの値・演算に入る所は castle 18 か所、miku・darius 0 か所。castle のほとんどは値が小さい（`x * 2`、x < 32）。
  作者が避けている跡（`menu.fc` で `y:u16` と宣言してから `y << 6`、`en7.fc` で `y16` に移してから `* 32`）と、値の範囲に頼る
  所（`text.fc` の `t.addr + 64 * t.cur_y` は cur_y ≥ 4 で折り返す。窓の高さが 2 なので今は無事）がある。ネームテーブルの
  アドレス（`0x2000 + y * 32 + x`）は必ず 16 ビットが絡むので、ここが一番の落とし穴（上の決定で正しくなる）
- **符号の混在**（高）: 同じ大きさなら符号付きが勝つので、`x + -1`（x:u8 = 200）が i8 の -57、`s < 200`（s:i8）が偽。
  u8 の座標に i8 の速度を足すのは定番。混在は 1 段広い型（u8 + i8 → i16）にするか警告。規則をリファレンスに書く
  **保留（2026-09-26）。** 検討の経過: 今の fc は幅については「int が 8 ビットの C」で説明できるが、符号とリテラルは C と違う
  （C は同じ大きさなら符号なしが勝ち、10 進のリテラルは符号付きの int に収まらなければ広い型。fc は符号付きが勝ち、リテラルは
  収まる一番小さい型で `200` は u8）。ほかの言語: C / C++ は int に広げ、int 同士では符号なしが勝つ（`-Wsign-compare` で補う）。
  C# は両方を表せる型に広げる（`byte + sbyte` → int、`int + uint` → long、`long + ulong` はエラー）。Go・Rust・Swift・Kotlin は
  暗黙に混ぜられずエラー（Rust は `wrapping_add_signed` がこの用途用）、リテラルは相手の型に合わせ収まらなければエラー。Zig も
  エラー（両方を表せる i9 に広げる提案 ziglang/zig#15737 がある）。8 ビットの `+ - & | ^ <<` は符号付きでも符号なしでも結果の
  ビットが同じなので、効くのは解釈の場面（比較、`/ % >>`、16 ビットへの拡張、型を省いた変数）だけ。C# 流に i16 へ広げると
  座標 + 速度が毎回 16 ビットになる。案: 計算は 8 ビットのまま、代入先の型があればそれで解釈、無ければ符号の混在を警告し
  `as` を案内、リテラルは相手の型に合わせて収まらなければ広げる（またはエラー）
- **暗黙の縮小が黙って通る**（高）: `var c:u8 = 300;` が 44、引数・戻り値・struct リテラル・配列の要素でも同じ。
  リファレンス §2 の「サイズが合わない代入はエラー」と食い違う（`const T:[3]u8 = [1, 2, 256]` だけはエラー）。
  範囲外の定数はエラー、変数の縮小は警告（`hi = addr >> 8` のために暗黙のままでもよい。その場合は文書を直す）
- **必ず真・偽になる比較**（高。**警告する: 2026-09-26 決定**）: `for (var i = 0; i < 300; i++)`（i は u8）、`for (var i = 0; i < @len(buf); i++)`（256 要素。
  OAM の消去の定番）、`i <= 255`、`i >= 0`（u8）が無限ループ、`hp - dmg < 0`（u8）が常に偽。型の範囲から警告する。
  for の変数の型を上限から推論する案も
- **文字リテラルが無い**（高）: `'A'` は `"A"`（`[2]u8`）。`var c:u8 = 'A'`、`s[i] == 'l'` が型エラー、`case 'A':` は panic
  （10.1）。§8（char 型）で 1 文字のリテラルは未決。fc 3 では `'A'` を u8 の定数にして、migrate で fc 2 の `'…'` を `"…"` に
- **条件式が無い**（中）: `x > 2 ? 10 : 20` が `parse error: unexpected 'Kind(89)'`。`var dir = right ? 1 : -1` が if / else の 4 行
- **`as bool` と bool への代入が下位バイトだけ**（中）: `var b:bool = w;`（w:u16 = 0x100）が false、`5 as bool` が 5。
  `as bool` は `!= 0`、2 バイト以上から bool への暗黙の変換はエラーか `!= 0`。
  **2026-09-26 決定: 正規化はしない（処理が増えるため）。** そのため struct・配列の `==`（バイトの比較）は、正規化されていない bool が
  入っていると真理値としては等しくても偽になる（`a.f = true; b.f = 5 as bool;` で `a == b` も `a.f == b.f` も偽、`if (b.f)` は真。
  2026-09-26 に確認）。これを仕様として文書に書く。
  **ただし bool 同士の `==` / `!=` は真理値で比べるように変える（2026-09-26 決定）。** 今は実行時の値でもバイトの比較
  （`x = 5, y = 3` で `(x as bool) == (y as bool)` と `(x as bool) == true` が偽。-O 2 / -O 0 で確認）。コスト: `f == true` /
  `f == false` は 0 かどうかだけ見る `lda f / bne` で今の `lda / cmp #1 / bne` より短い。変数同士は `lda f / beq / lda g / beq …`
  で分岐が 2 つほど増える。0 / 1 と分かる値（比較の結果・`true` / `false`）同士は今のまま `cmp`。`if (f)` と bool への代入は
  変わらない。struct・配列の `==` はバイトの比較のまま
- **定数添字の範囲外を検出しない**（中）: `var a:[3]u8; a[3] = 1;`、`T[7]`（const）が通る（slice の範囲は定数なら検査している）
- **`if (x = 0)` を警告しない**（低〜中）: `&` と `==` の優先順位の警告と同じ仕組みで、条件の直下の代入を警告
- **enum を回しにくい**（低）: `d++` が `cannot apply + to enum`（`++` なのに `+` と出る）。`++` / `--` だけ許すか、for で回す手段
- **const 表の定数添字が定数にならない**（低）: `const HP1 = MONS[1].hp;`、`const K2 = KINDS[2];` が `must be constant`

### 10.3 宣言とデータ

- **グローバル変数の初期値**（中、既知。**まだやらない: 2026-09-26**）: `var gx:u8 = 5;` が `can't init global variable`（roadmap の既存項目、
  language_feature_candidates.md §6）
- **未知・無効な属性を黙って無視する**（高。**まず警告にする: 2026-09-26 決定。エラーにするかは後で**）: `@(adress: 0x6000)`（綴りの誤り）が普通の RAM 変数になる。`@(volatil)`、
  `@(inlin)`、var の `@(zeropage)`、const 表の `@(segment:)`、ローカルの `@(address:)` も無視。I/O レジスタの宣言の誤りに気づけない。
  宣言の種類ごとに受け付けるキーを持ち、それ以外はエラー（fc.toml の未知のキー・セクションも同じ: 10.5）
- **型名を省いた struct リテラルを引数に書けない**（中）: `add({1, 2}, p)` が `parse error: unexpected '{'`（配列リテラルの要素なら
  書ける。enum の `.B` は引数で推論できる）。`var s = {1, 2};` も構文エラーで「型が要る」と言わない。モジュール修飾の
  `geom.Point{x: 1, y: 1}` は `dot: right side must be identifier`。引数の型を文脈にする
- **名前付きの const を別の const 表の要素にできない**（中）: `const PTS:[?]Point = [ORIGIN, {1, 2}];`（ORIGIN は const の struct）が
  位置なしの `: error: invalid constant for struct t.Point`、`[ROW, [4, 5, 6]]` も同じ。`var arr:[2]Point = [ORIGIN, …]` はエラーの行が
  ずれる。定数の名前を値として展開し、診断に位置を付ける
- **グローバル変数のアドレスを const の表に入れられない**（中）: `const PP:*P = &gp;`、`[&g[0], &gp.y]`、`[h]`（スカラー）が
  通らない（配列の名前 `[g]` だけ通る）。メニュー項目・セーブ対象の表に要る。リンク時に決まるアドレスとして定数にする
- **2 次元配列の行が値の文脈でポインタになる**（中）: `var b = a[1];` が `*u8` で、`a` を書き換えると `b` も変わる。
  `var row = M[1]; @len(row)` がエラー（`@len(M[1])` は 3）。`var f = ANIMS[0].frames;` もポインタ。添字の結果の配列も配列型のままに
- **ZP の変数**（低〜中）: `@(segment: "ZEROPAGE")` はほかのモジュールから `.import`（`.importzp` でない）で絶対番地の
  アクセスになり、ZP のポインタも毎回 `reg` に写して `(reg),y`。var の `@(zeropage)` と直接の `(ptr),y`
- **`@(address:)` に定数式を書けない**（低）: `@(address: BASE + 0x10)` が `must be a literal or identifier`
- **文字列のエスケープと連結**（低）: `\t` / `\0` は `\` が残り、`\"` は 2 バイト、`"abc" "def"` は構文エラー。`\\` が効くことは
  リファレンスに無い
- **soa に `@len` が使えない**（低）
- **型の表示**（低）: `[?]T` が `[]T`（slice と同じ）と出る、`*const u8` が `*u8` と出る、配列のエラーでどの要素が悪いか出ない
  （`const T:[3]u8 = [1, 200, -1]` が `cannot assign [3]i8 to [3]u8`）

### 10.4 制御構文・関数・モジュール

- **do-while が無い**（中〜高、既知）: `do` が識別子として読まれ、エラーが本体の中身で変わる（`unexpected ++`、`unexpected ;`、
  `unexpected while`）。最低 1 回回るループ（256 回回す `i` など）は 6502 で最も自然。fc 3 で `do { } while (c);`、
  少なくとも専用のエラー（loop + break を案内）
- **C の書き方で空の case を並べると何もしない**（中〜高。**2026-09-26 決定: 警告にする。ただし何もしない case は書くので、`:` から
  次の case までにコメントがある、または `break;` などの文があれば警告しない。最後の case も警告しない。コメントは位置つきで
  `syntax.File.Comments` にあり（`fcc fmt` が使う）、`internal/syntax/lint.go`（`&` と `==` の警告と同じ所）で判定できる**）: `case 2: case 3: r = 7;` で x == 2 のとき何もしない（v2 の仕様）。
  fc 3 には `case 2, 3:` と `fallthrough;` があるので、後ろに case が続く空の case を警告（またはエラー）にして案内する
- **return 忘れの検査が狭い**（中）: `while (true) { … return … }`（`isTrueLiteral` が `true` を認めない）、全メンバーの
  enum の switch、`@if (…) { return 1; } else { return 2; }` が `missing return`。`terminates()` に足す
- **初期化していないローカル変数**（中。**2026-09-26 決定: 警告にする。ゼロで初期化はしない**）: 静的フレームがほかの関数と重なるので、前の値が見えて -O で結果が変わる
  （`var y:u8; y += 1;` を 3 回呼んで 111 / 123）。SSA で「書く前に読む」を警告する
- **ローカル変数のアドレス・slice を返しても警告しない**（中）: `function f():[]u8 { var a:[4]u8; …; return a; }` が通り、
  次の呼び出しで上書きされる。警告する
- **C 風の前方宣言**（中）: `function helper(x:u8):u8;` の後に本体を書くと `helper already defined`、本体が無いと ld65 の
  `Unresolved external`（fc のソースの位置が出ない）。「宣言の順は自由」と案内し、fc 3 では本体の無い関数に `@(symbol:)` などを必須に
- **for-each と case の範囲が無い**（中）: `for (x in A)`、`case 0..3:`（`Kind(90)` のエラー）。for-each は上の「必ず真の比較」の
  罠も避けられる。低: for の初期化・step のカンマ、空の switch、for だけ本体の `{}` が必須
- **構文エラーに内部のトークン名**（低、安い）: `Kind(89)`（`?`）、`Kind(90)`（`..`）。`syntax/token.go` の `kindNames` に
  `Question` / `DotDot` / `At*` を足す。`var z = y++;` には「++ は文としてだけ」と案内
- **`@asm` から変数を扱いにくい**（低〜中）: ローカル変数・引数を参照する書き方が無く、asm の誤りは ca65 のエラーが
  `.fc-build\_x.s` の行で出る。グローバルは `@(symbol:)` を案内する
- **モジュール**（低）: サブディレクトリのモジュール（`use sub.util;`）と検索パスの設定が無い。glob で取り込んだ先の private な
  名前が `priv not found (did you mean print?)`（選択的なら `a.priv is private`）
- **エラーの文言**（低）: fc 3 で fc 2 の書き方を案内する（`options(farcall: true)`、`use bitcast` など sema に 12 か所ほど）、
  `elseif` が `unexpected '}'`、デフォルト引数があっても `expects 3 argument(s)`、ラムダの外側のローカル変数が
  `total not found`、`&f`（関数）が `not a variable`、`@(inline)` の再帰のエラーが -O 0 で出ない
- **emu のソフトウェアスタックのあふれ**（低）: 再帰 25 段ほどで Go の panic とスタックトレースがそのまま出る

### 10.5 fclib と NES の開発の流れ

- **最小の NES プログラムに割り込みの定型文が要る**（高。**2026-09-26 決定: 未定義なら空のハンドラを作り、stdio の NMI と
  ぶつからないようにする。割り込みは asm で書く前提（§6: fc の割り込みは `reg` を壊しうる）なので、fc で書きやすくする方向は優先しない**）: `use nes` と `main` だけで ld65 の `Unresolved external '_interrupt'` /
  `'_interrupt_irq'`（share/runtime.asm が import）。`use stdio` して自分の NMI を書くと `Duplicate external identifier`
  （stdio.asm が定義）で、stdio のデバッグ表示と自分の NMI を両立できない。名前の決まりは文書に無い。未定義なら空の
  ハンドラを生成し、stdio の NMI は差し替えられる形に
- **NES の stdio で hello world ができない**（中）: `init()` が NMI を有効にしないので `wait_vsync()` が戻らず、描画は `exit()` まで
  OFF、フォントの CHR が無い。`exit()` が PPU_CTRL1 の bit 6 を立てる。init で NMI と描画を有効に、ASCII フォントを同梱
- **PPU / OAM / vblank の部品が無い**（中）: castle と miku が ppu.fc / ppu.asm（230〜290 行: NMI、書き込みキュー、スプライトの
  バッファ）を自前で持つ。RAM の配置（SRAM $0200-$06FF）で空いているのは $0700 だけで、OAM の置き場所が文書に無い。
  `nes/ppu.fc`（OAM のバッファと DMA、vblank のキュー、パレット・ネームテーブルの転送）
- **マッパー周りの定型文**（中）: fc.toml で mapper を指定しても、`@include("farcall_mmc3.asm")`、
  `var pbank_bak:[2]u8 @(symbol: "_mmc3_pbank_bak")`、バンクの初期化を利用者が全部書く（欠けると ld65 の生のエラー）。
  fclib に mmc3 / mmc1 / uxrom のモジュールが無い。MMC3 で start / runtime_init / interrupt が $C000 台に置かれる
  （電源投入時の状態が不定なので $E000-$FFFF に置き、reset で $8000 を初期化するのが定石）。farcall_mmc1 / mmc3.asm が `cli` を
  無条件に実行する。プロファイルごとにトランポリン・状態変数・reset の初期化を自動で入れる
- **fc.toml の `[target]` のキーが足りない、書き間違いを検出しない**（中）: ミラーリングは iNES ヘッダで常に 1、バッテリーの
  フラグが無い、`chr = "0"`（CHR-RAM）が `not a size`。`[taget]` や未知のキーは黙って無視（`[bank.*]` はエラー）。エラーの
  先頭が `: error:` で位置が無い
- **ターゲットを fc.toml から決めない**（中）: `[target] mapper = "NROM"` があっても既定は emu で、`fcc build main.fc` が
  `file nes.fc not found`（`-t nes` の案内が無い）。`fcc run -t nes` は a.nes を作って黙って終わる。VS Code 拡張の既定の
  ターゲットが 2 つで食い違う（tools/vscode-fc は nes、editors/vscode は emu）
- **fclib の API が slice を受けない**（低〜中）: `print(s)`（`[]const u8`）がエラーで、文言は `cannot assign []u8 to *const u8`
  （const が落ちる）。mem の slice 版が無く、set / zero の長さは u8、copy は u16
- **math**（低）: `sign(i8):u8` が -1 を 255 で返す、`atan(y, x)` は |x|, |y| ≤ 15 だけ正しい（範囲が文書に無い）、i16 の abs が無い、
  `rand` のシードを設定できない、10 進・BCD のスコア表示の部品が無い（castle が手書き）
- **lzw / inflate と ZP の配置の文書**（低〜中）: lzw.fc が ZP の $7C-$7E を固定番地で使う（「$00-$7F 禁止」の規則に反し、
  FC_ZEROPAGE が後ろにずれると衝突しうる）。language_reference §4.5 の ZP の配置（$70-$7F が ZEROPAGE）が実際と違う。
  inflate の `unpack` が public でなく使えないのにリファレンス §8 に載っている
- **nes.fc / pad.fc が最小限**（低）: APU のレジスタが無い、ビットの定数が無い、名前が PPU_CTRL1/2 の古い流儀、pad は
  コントローラ 1 だけ
- **castle / miku の「passes read-only data」の警告**（参考）: castle 102 件、miku 7 件は全部ゲーム側の関数（`add`、
  `put_in_lock`、`put_text_in_lock` など）の引数。fclib の入力は `*const u8` になっている

### 10.6 文書が実装より古い

- language_reference §2.1「struct の比較 `==` はない」→ struct・配列の `==` は中身の比較として動く
- §6「添字は 1 バイト（2 バイトは不可）」→ u16 の添字は動く
- §2「サイズが合わない代入はエラー」→ 暗黙に縮小する（10.2）
- §6 のポインタ演算「C と同じ」→ バイト単位（10.1）
- §4.5 の ZP の配置（10.5）

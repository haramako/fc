# FC V2: 配置指定・Mesen のスタック表示・一時ディレクトリの検討

2026-09-20。ユーザーからの V2 向け検討依頼の記録。**§1 の BSS 指定と §4 の一時ディレクトリ診断は実装済み。§2〜§3 は検討・調査のみ。**
V3 の `@(...)` や型名変更とは分け、例は現行の `options(...)` で書く。未実装の構文例は仮案。

## 1. モジュール・宣言グループの BSS 指定（実装済み）4

`options(bss: "...");` と `block { ... } options(bss: "...");` を実装し、
コミット `0e539d8` で main に取り込んだ。確定仕様は [v2_bss.md](v2_bss.md)、
利用方法は [言語リファレンス §4.1](language_reference.md) を参照。

```fc
options(bss: "BSS_EX");
var a:int;
var b:int;
var small:int options(segment: "BSS"); // 個別指定を優先

block {
    var x:int;
    var y:int;
} options(bss: "irqcmd_bss");
```

検討後に確定した点:

- モジュール・ブロックの既定配置には `bss` を使う。個別宣言自身の配置は従来の `segment` を維持する。
- 優先順位は **個別 segment > 内側のブロック bss > 外側のブロック bss > モジュール bss > BSS**。
- モジュールの指定はファイル全体に効き、他モジュールへ伝播しない。トップレベル宣言の処理後に未指定の BSS 定義へ適用する。
- 配置ブロックは名前空間や寿命を増やさず、`public var` は通常のモジュール変数として公開される。
- ブロック内は `var`・可変 `soa`・入れ子の配置ブロック・空文を許可する。`block` は予約語にしない。
- 関数内ローカル、固定アドレス変数、コード、ROM 定数は対象外。可変 soa は展開した各配列へ継承する。
- ld65.cfg のメモリマップ、起動時ゼロクリア、保存領域の扱いは変更しない。
- 連続配置やページ内配置は保証しない。§2 の配置制約は別機能として検討する。

実例: `C:/Work/castle/src/en.fc`、`bg.fc`、`my.fc` などに `BSS_EX` の繰り返しが多い。
`bg.fc` は通常 BSS と BSS_EX が混在するため、モジュールとブロックの双方の指定に用途がある。

当初の説明の訂正: 現行の**関数自身の** `options(segment:)` はコード配置に反映されるが、
モジュール単独の `options(segment:)` はコードの既定配置を変更しない。
今回の BSS 実装はこの既存挙動を変更していない。

## 2. 要件は「256 バイト境界をまたがない」配置

**ユーザー訂正: 先頭を 256 バイトに align すること自体が目的ではない。関数や変数のメモリブロックが
一つの 256 バイトページに収まり、ページまたぎによる追加クロックを避けることが目的。**

例えば 64 バイトなら `$8080..$80BF` は許容し、`$80E0..$811F` は不可。
現在位置に収まるならそのまま配置し、収まらなければ次ページへ送るのが理想。
開始アドレスを A、サイズを N とすると、非空ブロックの条件は `(A & 255) + N <= 256`。
256 バイトはページ先頭に置く必要があり、257 バイト以上は一つのブロックとしては実現できない。

### ld65 / ca65 でできること

ld65 のセグメント属性 `align = $100` は存在する。ただし保証は**セグメントの開始位置**であり、
中の各関数・変数をページ内に詰める指定ではない。
ca65 の `.align 256` はセグメント内にパディングを入れる。こちらも必要なセグメントの配置条件を cfg 側で満たす必要がある。
公式のセグメント属性には、今回の「収まれば詰め、またぐときだけ次ページへ送る」を直接指定する項目は見当たらない。
参照: [ld65 §5.7](https://cc65.github.io/doc/ld65.html#ss5.7)、
[ca65 .ALIGN / .ASSERT](https://cc65.github.io/doc/ca65.html#ss11.4)。

一方、**最終配置の検査は既存のリンカ機能で可能**。生成 asm に例えば次を出せる。

```asm
object_start:
    .res 64
object_end:
.assert .hibyte(object_start) = .hibyte(object_end-1), lderror, "object crosses page"
```

これは自動再配置ではなく、配置が要件を満たさなければリンクを失敗させるもの。
手元の ca65 / ld65 で上記 64 バイトを `$8080` から置くと成功、`$80E0` から置くと
`object crosses page` で失敗することを確認した。FC への組み込みは行っていない。
空ブロックは `end-1` が不適切なので別扱いが必要。

### V2 の候補

```fc
// 名称は仮。align:256 と異なる要求を表す
var table:[64]int options(segment: "IRQ_DATA", nocross: 256);
function irq_part():void options(segment: "IRQ_CODE", nocross: 256) {
    // ...
}
```

推奨は、まずこの「ページ内に収める要求」と最終リンク検査を定義し、配置方法を分けて検討すること。

| 方法 | 特徴 |
| --- | --- |
| 手書き cfg の配置 + リンク時検査 | 既存の castle に適用しやすい。自動パディングはしない |
| 対象を毎回ページ先頭へ置く + サイズ検査 | 実装は単純だが、小さい対象も最大 255 バイトの隙間を作る |
| サイズに応じ、またぐ場合だけ次ページへ配置 | 要望に最も合う。最終サイズと配置先の下位 8 ビットが必要 |

最後の方法は、変数ならサイズが事前に決まりやすいが、関数では最適化・分岐の長距離化・入口コードまで
含む最終サイズを使う必要がある。ページ先頭に配置した一つの管理セグメント内なら相対オフセットで詰められるが、
別オブジェクトの寄せ集めや外部 asm を含む既存セグメントでは単独の FC モジュールだけでは配置を決められない。
アセンブル後のサイズ情報を使う配置パス等が候補。手書き cfg を前提にした小さな追加とは工数が異なる。
V2 の初期対応を検査だけにするか、自動配置まで含むかは未決。検査だけを自動配置が完成したと説明しない。

castle では `ld65.cfg` に IRQ 用のページ単位 MEMORY 領域と `irqcmd_bss` があり、
`bg.fc` には `_padding_for_align:[64]int` がある。既存の手動管理を壊さず、要求違反の検知を足す価値がある。

### 「追加クロックなし」の保証範囲

メモリブロックがページ内に収まることと、任意の生成命令に追加クロックがないことは完全には同義ではない。

- 配列先頭をベースとする通常の添字読み取りでは、範囲内のバイトが同一ページならページ越えを避けられる。
  ただし範囲外の添字、別のベースポインタ、ベースをずらす最適化、複数バイト要素の展開は生成命令まで確認する。
- 条件分岐は**分岐命令の次の PC**と飛び先のページを比較する。
  命令自体がページ末尾の `$xxFE..$xxFF` に収まっていても、同じページへの後方分岐で追加クロックが生じ得る。
  コードの端点検査に加え、時間制約のある分岐に `page(branch+2) == page(target)` のリンク検査を出す案が必要。
- 分岐が成立すること自体の追加クロックは残る。外部データアクセス、呼び先、DMA 等の時間までこの属性では保証しない。
- 普通の命令フェッチがページを越えただけで一律に追加クロックが生じるわけではない。
  256 バイト超の関数でも、重要な分岐・データアクセスだけを検査する別案は成立する。

時刻依存の処理については、配置検査に加え最終生成命令とエミュレータでのサイクル確認を将来の受け入れ条件にする。
命令タイミングの参照: [Mesen NES CPU 実装](https://github.com/SourMesen/Mesen2/blob/master/Core/NES/NesCpu.cpp)。
ページ内配置は既知の interrupt 共有作業領域問題の対策とは別で、そちらの修正は引き続き行わない。

## 3. Mesen のコールスタックが farcall になる件

現行 FC / castle は `jsr farcall` の後、トランポリンから `jmp (FC_FARCALL)` で本当の関数へ飛ぶ。
バンク切替がある経路では、さらに `jsr @indirect` → 間接 JMP → 復帰処理という構成。
参照: [MMC3 参考実装](../fclib/nes/farcall_mmc3.asm)、`C:/Work/castle/src/mmc3.asm`。

[Mesen 2 の NesDebugger::ProcessCallStackUpdates](https://github.com/SourMesen/Mesen2/blob/master/Core/NES/Debugger/NesDebugger.cpp)
では JSR 等でフレームを記録し、RTS / RTI で戻す。JMP によるフレームの呼び先更新はこの処理にない。
したがって `farcall($DB6A)` になる報告は、このトランポリン構造で説明できる。
ここでは上流 Mesen 2 のコード確認まで。報告環境の実行版・停止位置・表示そのものは未再現。

FC は既に `.dbg` と `.mlb` を出し、[WriteMlb](../internal/driver/dbgfile.go) で物理 PRG ROM 位置のラベルを生成する。
シンボル不足は先に確認すべきだが、共有の farcall アドレスへ全呼び先の別名を付けても実行履歴は復元できない。

対策候補:

1. **Mesen 側のトランポリン認識**: farcall 内の決まった間接 JMP を実行したとき、実際の飛び先と物理バンクで
   表示上の呼び先を更新する。バンク復帰用の内部フレームの隠蔽、再入・割り込み・step out との整合が必要。
   NES 側の命令を変えない点で第一候補だが、Mesen 側の拡張になる。標準設定だけで可能とは確認できていない。
2. **Lua 等による別の論理スタック表示**: ホスト側で追跡する案。標準コールスタック欄を書き換える API は未確認。
   FC_FARCALL の現在値だけでは過去の入れ子を復元できないため、呼び出し・復帰時の履歴が必要。
3. **呼び先別スタブ**: FC 側に識別可能なスタブを生成する案。表示は改善し得るが、固定バンクの ROM 消費、
   バンク復帰、ネスト、追加命令、Mesen がどのフレームを表示するかを検証する必要がある。
   単なるデバッグ情報の改善ではなく ABI / コード生成変更なので、最初の対策には推奨しない。

V2 の課題として残す。Mesen の fork / 使用版による差もあるため、実装前に対象バイナリを確認する。

## 4. `C:\WINDOWS\fc-home-...` 作成失敗の診断（実装済み）

### 分かったこと

[ResolveFCHome](../internal/driver/home.go) は次の順で標準ライブラリの所在を探す。

1. `FC_HOME`
2. fcc 実行ファイル位置から親ディレクトリへ `fclib/` と `share/` を探索
3. カレントディレクトリから同じ探索
4. 見つからなければ `os.MkdirTemp("", "fc-home-")` に埋め込みデータを展開

Windows ディレクトリを FC が明示しているわけではなく、最後の一時ディレクトリ選択に依存する。
Windows の通常プロセスでは `TMP` → `TEMP` → `USERPROFILE` → Windows ディレクトリの順で選ばれる。
参照: [Microsoft GetTempPath2W](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-gettemppath2w)。
手元の Go ソースも GetTempPath2W / GetTempPathW を使用している。

この環境で Win32 GetTempPathW の返す文字列だけを調べた結果:

| 子プロセス内での条件 | 選ばれたディレクトリ |
| --- | --- |
| 通常 | ユーザーの AppData/Local/Temp |
| TMP だけを削除 | 同上（TEMP が有効） |
| TMP と TEMP を削除 | ユーザープロファイル直下 |
| TMP・TEMP・USERPROFILE を削除 | C:\WINDOWS |

Windows 配下へのファイル作成は試していない。環境変数の変更は調査プロセス内だけで、最後に復元した。
最初の PowerShell 経由の試行は null が空文字列として渡ったため除外し、C# 内でネイティブ API に null を渡す削除で確認した。
**TMP が渡らないだけで必ず Windows になる、という説明は不正確。** 他の候補も未設定か、
いずれかの値自体が Windows を指しているなどの追加条件が必要。元の Bash ツール環境は未再現。

### 評価と実装した対応

分類は **環境依存の起動失敗**。fcc に原因・失敗パス・対処を案内する診断を追加した。コンパイル対象のソースやコード生成のバグとは別。
PowerShell / make なら常に安全とは言えず、子プロセスへ渡る環境と FC_HOME の解決結果で決まる。

**ユーザー方針: AI の Bash ツール経由の問題として、AI が原因と対処を判断できるエラーメッセージを出せば十分。
根本的な対策・展開先の自動フォールバックは不要。現在の探索順序と展開方法を維持する。**

- 当面は呼び出し環境で書き込み可能な TMP / TEMP を渡すか、実在する FC_HOME（例: `C:/Work/fc`）を明示する。
- fcc のエラーに「同梱ライブラリ展開用ディレクトリの作成失敗」、選ばれた親ディレクトリ、
  OS のエラー、FC_HOME または一時ディレクトリ用の環境変数を指定する対処を追加した。Windows では TMP と TEMP、その他では TMPDIR を案内する。全環境変数は出力しない。
- エラーに Bash が原因と断定して書かない。観測できた失敗パスと対処を示せば、AI が起動環境を修正できる。
- テストで作成失敗時のメッセージと CLI の終了コード・標準エラーを確認した。元の OS エラーはラップして保持する。
- 正常時の展開・後片付け、および FC_HOME / カレントディレクトリの親から既存ライブラリが見つかる場合の動作もテストする。探索順序・自動フォールバックは変更していない。

Windows でのメッセージ例:

```text
failed to create a temporary directory for bundled FC libraries
  parent: C:\WINDOWS
  cause: <original OS error>
Set TMP and TEMP to a writable directory, or set FC_HOME to a directory containing fclib/ and share/.
When running through an agent/shell tool, pass these variables to the fcc process.
```

## 残る検討

BSS 指定と一時ディレクトリ失敗時の診断は実装済み。一時ディレクトリの自動回復は追加しない。
ページ内配置は、最終配置の検査と自動パディングを分けて設計する。
farcall の標準スタック表示は FC のラベルだけで直るとは期待せず、対象 Mesen での再現と拡張箇所の確認から始める。

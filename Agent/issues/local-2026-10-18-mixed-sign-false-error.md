# F6 の符号の混ざりのエラーが 8 ビットの式に対して誤検出する

- 出典: ローカル（2026-10-18 のバグ調査。他のエージェントのレビューで再現をもらった）
- 状態: **修正済み**（2026-10-19。回帰テスト `TestBugMixedSignNarrowExpr`、bugzoo の `mixed-sign-narrow-expr`）

## 再現

```fc
#fc 4
use console;
var a:i16 = 100; var b:u8 = 200; var c:u8 = 3;
function main():void
{
	@printf("{}\n", a - b);          // -100 …通る
	@printf("{}\n", a - (b as u8));  // -100 …通る
	@printf("{}\n", a - (b >> 2));   // error: `a - (b >> 2)` mixes i16 and u16, so it is i16 …
	@printf("{}\n", a - (b + 0));    // error: 同じ
	@printf("{}\n", a - (b | 0));    // error: 同じ
	@printf("{}\n", a - (b + c));    // error: 同じ
}
```

`i16` と `u8` の組み合わせで、**右辺がただの変数だと通り、8 ビットの式だとエラー**になる。仕様
（`docs/reference/language.md` の「同じ大きさで符号が違う」ものの規則と、`docs/reference/language.md` の
「シフトの結果は左辺の型」）では `b >> 2` は `u8` で、`i16` と `u8` は大きさ違いなので規則の対象外。
値も曖昧さがない（`u8` 由来の値は 32768 以上にならないので、`i16` として読んでも読み替えが起きない）。
実際に計算させた値は正しく（50）、**エラーの方が間違い**。

### 狭い側が符号付き・広い側が 32768 以上を持つときも同じ（2026-10-18 に `fcc run` で確かめた）

「広い側の符号なしが 32768 以上を持ちうるならエラーは妥当」ではない。広い側を同じにして、狭い側（i8）を変数・式・`as` に
書き換えると、**エラーになるかは狭い側が変数か式かだけで決まる**（`gu:u16 = 40000`、`gi80:i8 = -128`、`gi83:i8 = -1`、
`gi84:i8 = 0`、`gi87:i8 = 127`。`@printf` の引数に書いた）:

| 式 | 結果 |
|---|---|
| `gu + gi84` | 通る（40000） |
| `gu + (gi84 ^ gi84)` | エラー |
| `(284 * gi87) + gi84` | 通る（36068） |
| `(284 * gi87) + (gi84 ^ gi84)` | エラー |
| `(gi80 & 288) * gi83` | 通る |
| `(gi80 & 288) * ((-122) + gi83)` | エラー |
| `gi80 * id_u16(293)` | 通る |
| `(gi80 << 3) * id_u16(293)` | エラー |
| `gu + (gi84 as i16)`、`(gi80 as i16) * id_u16(293)` | エラー（本当に同じ大きさで符号違い。正しいエラー） |

`gi84` と `(gi84 ^ gi84)` は同じ `i8` なので、どちらかの結果が間違い。仕様は大きさが違えば規則の対象外なので、エラーの方が誤り。
`TestRandomArithV4` が大きな種で踏んだ 3 本（下の「生成器の回避」）はこの形。

**文言も矛盾している**: 誤検出の経路では「mixes u16 and i16, so it is **u16** (the signed type wins at the same size)」と、
符号付きが勝つと言いながら符号なしの型を名乗る。本当の混ざり（`gu + (gi84 as i16)`）は正しく「so it is i16」。
直すときに、誤検出が消えた後もこの文言の型の選び方が正しいかを見る。

## 原因（`internal/sema/mixedarith.go` の `mixedOf`）

`Add / Sub / Mul` の印は、**A1 で広げた後の IR のオペランドの型**を見て付ける
（`lt.Size == rt.Size && lt.Signed != rt.Signed && tmp.Type.Size == lt.Size`）。

- 変数 `b` はオペランドとして狭い型（`u8`）のまま渡るので `1 != 2` で印が付かない
- 一方 `b >> 2` のような式は、式そのものが 16 ビットの命令に広げられ、自分の符号を保つので `u16` になる
  → `i16` と `u16` で「同じ大きさで符号違い」に見えて印が付き、`@printf` や比較に届いてエラーになる

## 直したこと（2026-10-19）

`mixedOf` の `+ - *` の起点の判定で、両辺の型を IR のオペランドでなく式の型（`exprType`。広げる前の型）で見る
（`mixedOperandType`。複合代入など式の型が取れない所は IR の型のまま）。大きさの違う項（i16 と u8 の式、u16 と i8 の式）は
通り、本当に同じ大きさで符号が違う項（`gu + (gi84 as i16)`、`b + gi84`）は今までどおりエラー。誤検出の経路の文言の矛盾
（「so it is u16 (the signed type wins…)」）も消えた。migrate のテスト（書き換えも同じ判定を使う）は変わらず通る。

生成器の回避（`randarith_test.go` の `arMarkTy`）は、`TestKnownBugF6FalseError` が「直った」と落ちたので外し、テストは
`bugs_test.go` の `TestBugMixedSignNarrowExpr`（通ることと値、本当の混ざりはエラー）に移した。`TestRandomArithV4` を種
0・1000000・20261018000・20261019000 の各 1000 本で 0 件。

## 影響

コードの受け入れ（コンパイル可否）の話で、生成コードの誤りではない。fc 4 の既存コードが通らなくなる方向なので、
移行の体験にも関わる。`+%` や `as` で回避できる。

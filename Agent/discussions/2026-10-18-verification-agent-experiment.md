# 2026-10-18 「作業後に別エージェントで検証する」は効くのか（レビュー前の状態で検証役を走らせた実験）

## 質問

バグ調査の 10 コミットで私が作った誤り（[2026-10-18-bug-hunt-review.md](2026-10-18-bug-hunt-review.md)）を、
**別のエージェントの検証を後から挟むだけで止められたのか**。ハーネスに「完了後に別エージェントで検証」を入れられるか。

## 実験の形

`git worktree add --detach /tmp/fcreview/{a,b,c} 37943f2`（レビュー前の状態。答えになる
`2026-10-18-bug-hunt-review.md` はこのコミットに存在しない）。検証役は 3 本、**すべて私と同じ `yuri-strata/qwen3.8-flash-next`**、
ファイル編集・コミット禁止。

| 子 | エージェント | プロンプト | 予算 |
|---|---|---|---|
| A | `reviewer` | カテゴリ列挙＋「『見つけた』『効いた』と書く前に対照と比べろ」＋ビルド/テストの呼び出し方 | 30 分 |
| B | `evidence-auditor` | 「`Agent/` に記録した計測を裏取りして、合っている/間違っているを判定して」 | 30 分 |
| C | `reviewer` | 「10 コミットの作業が終わったという報告を信用できるか検証して。何を見るかは任せる。20 分で結論と merge 判定を」 | 20 分 |

## 結果

**3 本とも実行ツールを持っていなかった**（実際に呼ばれたのは A・C が `ls` / `find` / `read` / `grep`、B が `read` と `web_search` / `fetch_content`。シェルは無く、`go build` も `go test` も 1 回も実行できない）。
B は途中でそれを申告してきたので、静的監査に切り替えてもらった。つまりこれは全部**静的読解だけ**の実測。

レビューで出た 4 件のうち、静的に辿り着けたのは:

| 見逃した件 | B（静的・誘導あり） | C（静的・最小プロンプト） | A（静的・誘導あり） |
|---|---|---|---|

| F6 の誤検出を「生成器の穴」と分類 | 見逃し | 見逃し | 〃 |

**新規に、私が気づいていなかった不整合も出た**（3 件とも `37943f2` で私が実測して裏を取った）:

- **受け入れ条件の未達** — 条件は「型の網羅表の golden」＋「4 patch のうち 3 つ以上を newly」だが、
  `arAllTy = {u8,i8,u16,i16}` で enum/bool を生成せず golden 比較も無く、newly は 2（うち 1 つは誤検出で実質 1）
- **文書間の矛盾** — `interp-array-eq` を plans は「文字列生成器が見つける」、discussions は「検出できない（全項目 0）」と書く（同じ zoo 実行の記録）
- **patch 数の誤り** — 記録は 34 だが `git ls-tree 37943f2 testdata/bugzoo` は **35**
- その他: コミット数 9（10 でない）、`randarith_test.go` のコメント「シフト量は 0〜7」と実コード（2 バイトは 8〜15）の不一致、
  「測った zoo がどのコミットで測られたか」の記録が無い

C の判定は **Merge: BLOCK**、「承認者に実行してほしいコマンド」3 本を添えて終了（これが一番安くて一番効く出力の形だった）。

## 分かったこと

- **自己矛盾は、文脈を持たない読者にだけ見える。** 同じツリーの中の「記録 vs 記録」「模型のコード vs Issue」「定義 vs 呼び出し箇所」
  を突き合わせるだけで 4 件中 3 件が取れた。私は 10 コミットを書いている最中に自分の正当化を信じてしまった
- **誘導しすぎると沈む。** A は「実装・道具・記録を全部確かめる」という広いスコープで、30 分で read 19 / grep 21 / ls 7 / find 3 を呼んだが報告に至らなかった。
  呼び出し回数は少なく、読みすぎより 1 ターンごとの思考が長くて時間切れになった形。
  C は「20 分で結論と merge 判定」と言われて出し切った。**検証役にはスコープと出力形式の指定が要る**
- **worktree 分離は汚染を防げない。** C は `/home/harada/fc/.git/logs/HEAD` を読み、後続コミット
  （`e438ae3`「TestRandomArithV4 を HEAD で緑に戻し」）を「裏付け」として引用した（自己申告あり）。
  A も開始直後に同じ `/home/harada/fc/.git/logs/HEAD` を読んでいる（申告なし。報告を出していないので結論への影響は無い）。
  → **自発性を測る目的では A・C の結果は無効**。ハーネスとして組むなら、検証役には single-commit のスナップショット
  （`git archive` か、後続コミットが見えない clone）を渡す
- **実行ツールは必須。** 3 本とも持たずに 3/4 なので、実行できれば残り 1 件と確認まで行ける。
  ただし検証役のエージェント選びが素朴な穴で、`evidence-auditor` にはシェルが生えていない
- **LLM より先に機械ゲート**（今回の 4 件のうち 3 件は決定的に安い検査で取れる）:
  大きな種の乱数テスト 1000 本 = 約 7 秒 / 未参照の生成器関数 = grep / 実行ファイルのコミット = `git status` とサイズ上限

## 訂正（私がこのセッションで誤って報告した話）

「`reviewer` には bash があり、イベントログを見る限り `go build` / `go test -randseed` / `fuzzmeasure` を実行している」と書いたが**誤り**。
イベントログの文字列一致（`"bash"` の出現）をツール呼び出しと誤読していて、実際は 3 本ともコマンド実行は 0 回だった。
（root `AGENTS.md` の「生成物・判定を足したら、わざと壊して落ちることを見る」を、自分の測定に対してやっていない）

**追記（別セッションで子のセッションログと照合）**: 初版の「A は read 111 / grep 119」も同じ誤りだった。
これはイベントログ中の文字列 `"read"` / `"grep"` の出現数で、子のセッション（`run-0/session.jsonl` の `toolCall`）を数えると
A は read 19 / grep 21 / ls 7 / find 3。あわせて「汚染は C だけ」も誤りで、A も本体の `.git/logs/HEAD` を読んでいた。
上の本文は修正済み。訂正を書いた同じ文書で同じ数え方をしていたので、ツール使用の集計は `toolCall` を数える。

## ハーネスに入れるなら（提案）

1. 検証役に **実行できるシェル + 単一コミットの作業コピー**を与える（worktree ではなくスナップショット）
2. 出力を **「信用できる / 一部信用できない / 判断できない」＋ merge 判定 + 承認者が実行すべきコマンド**に固定する
3. スコープは「この差分が更新した記録とコードの整合」に絞る（実装の正しさの再設計は頼まない）
4. その前に機械ゲート（上記 3 つ、合計 10 秒）を置く
5. 検証役が本体リポジトリを読めないようにする（読んだら申告させる）

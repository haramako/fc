# fclib の NES のモジュールの asm 化（2026-10-05）

ユーザーの指示「NES のモジュールの asm 化」（roadmap「fclib の NES のモジュールを縮める」の残り: vram.put_dir、frame の NMI、
pal.shade）で試したことと決めたこと。数は examples/miku4 の `--size-report`（ROM 15569 → 15490 バイト）。

## asm にしたもの

- **pal.shade**（`fclib/nes/pal.asm`）: 123 → 78 バイト。fade のたびに 32 回呼ぶ。fc の版を `shade_ref` として pal.fc の
  `@(test)` に残し、全部の入力（c は 0〜63、d は -8〜8）で比べる（わざと壊すと落ちることも確かめた）
- **vram の描画を止めて書く所**（`fclib/nes/vram.asm` の write_raw / fill_raw。write_now / write_v_now / fill_now と、描画を
  止めているときの put / fill）: 大きさはほぼ同じ（write_dir 97 → write_raw 69、fill_now の分が別の関数 50 に）。速さが目的:
  1 KB のネームテーブルを書くと 1 バイト約 31 → 14〜16 サイクル（ポインタを 16 ビットで進めて終わりと比べていたのを、Y を
  一回りさせてページを数える mem.asm の形に）。statusbar は描画を始めるまでが速くなり、最初の 1 フレームの画面だけ変わる

## asm にしなかったもの

- **キューに積む put_dir / fill**: 空きと手間の残りを見て frame.flush を呼ぶところまで asm（queue_raw / fill_queue）にしたが、
  vram は 771 → 801 バイトと**大きくなった**（queue_raw 174 + fc の包み 72 > 今の put_dir 256。frame の変数は絶対番地の
  3 バイトの命令で、slice を frame の規約の引数に写す包みも要る）。速さも 1 バイト 20 → 18 サイクル程度なのでやめた。
  今のコンパイラの生成コードはこの形ではほぼ手書きと同じ大きさになっている
- **frame の NMI（`_interrupt` 304 バイト）**: もとから asm。写す・埋めるループを 8 バイトずつ展開しているのは vblank の
  手間（frame.BUDGET）のためなので縮めない

## コンパイラ側（一般に効くもの）

- ピープホールの A の追跡: A が既にその値の `lda` を、N/Z を読む前に立て直すなら（ラベルの合流を越えて先を見る）消す。
  `@min` や `if (k > 128) { k = 128; }` の `lda #k; cmp x; bcs @l; lda #k; sta x` の 2 つ目の lda（前の fork が見つけた
  「@min の後に残る写し」はこれ）。bench の fib −2.1%・oam −0.6%
- struct を指すポインタのフィールドの読み直しを前の値に（opt の `fwdmem`。Agent/wiki/design/ssa.md §11）: pad.update の 2 回目の
  `p.held`。書いた値が書く所だけで使う一時変数なら置き換えない（A に置けなくなって大きくなるのを測って確かめた）。対象を struct に
  限り、`*u8` で I/O のレジスタを読む書き方は残す（docs/reference/language.md の「ポインタ」に書いた）

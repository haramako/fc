# struct のメソッドと interface の相談

## 背景

ユーザーが interface と struct の埋め込みを入れたいと提案した。castle の敵の task のように、型ごとに処理の違う要素を効率よく回すためで、
u8 の ID で interface を管理し、メソッドは ID で引き、soa に対応する（それが主な使い方）。相談の段階で、計画だけ作る。

## 相談したことと決定

- **メソッドを先に**（ユーザー）: interface は「同じ名前のメソッドを ID で引く」ものなので、メソッドの書き方・`self` の渡し方が先
- **値の受け取り手も要る**: Point のような小さい struct は値で渡すほうが 6502 で速く、値を返すメソッド・変数でない値や const に
  呼べる。受け取り手の型をふつうの引数として書く（Zig と同じ: `self:Point` / `self:*Point` / `self:*const T`）
- **一般の struct の埋め込みはやらない**（ユーザー、候補に残す）:
  - Zig が埋め込みを持たないのは、フィールドがどこから来たか読んで分かること・名前のぶつかりを優先しているからと思われる
    （`usingnamespace` を外した理由と同じ方向。公式の説明を確かめてはいない）
  - 今回欲しい「どの実装でも共通のフィールドを `self.x` と書ける」は、interface に共通のフィールドを書けば満たせる
- **interface はタグ付きの共用体 + メソッドの表**:
  - Pascal・Ada の可変レコードに、メソッドの表を足した形
  - 「1 段だけの閉じた継承」に近い。何段もの継承・フィールドの上書き・`super` は持たない
- **soa の interface と普通の interface は共存できる**:
  - 1 つの interface はどちらか一方の形（`soa interface` か `interface`）
  - `*Slime` は soa なら 1 バイトの添字、普通ならアドレス
  - ソースの書き方は同じ
- **メソッドは struct の外に書く**（ユーザー）: 実装を別のモジュールに置ける
- **構文は `interface` / `soa interface`、実装は `struct Slime: Task = 1`**（ユーザー）
- **ID は手動と自動の両方**（ユーザー）:
  - 自動はモジュールのパスと宣言の順で決める。実装を足すと番号がずれるので、外のデータに書く番号は手動
  - ゲームのデータの番号から作る `@set_id`（ID を書くだけ）と、init を interface のメソッドにする形（ユーザーが原始的な機能でよいと）
- **バンク**（相談の後、ユーザー）:
  - near / far を interface の宣言で決める（`fn` / `farfn` と同じ関係。`@(far)`）
  - far は呼ぶたびに切り替えて戻す形で今回は十分
  - near はバンクを呼ぶ側の責任にし、`@bank_of_id` で手書きの速い形も書けるようにする（エージェントの案）
- **未決だった点**（ユーザー）: ほかのモジュールの型にメソッドは足せない（まずは）。ID の 0 は「無し」。要素を値として写すのは
  今は禁止（後の段で）。一般の埋め込みはやらない。0 = 無しを `null` と合わせる案（要素の `null` は ID が 0、ハンドル・ポインタの
  `null` は今のまま）を出し、ユーザーが一度採用したが、ポインタの `null` と紛らわしいので撤回。
  ID の enum の `.none`・予約語 `none` も出したうえで、「とりあえず」専用の言葉を作らず `@set_id(e, 0)` / `@id_of(e) == 0` に決めたが、さらに撤回して
  **ID を interface ごとの enum `Task.Id`（`none = 0` と実装の名前）にし、`.none` と書く**ことにした（型で ID の取り違えを防げ、
  `switch` も使える。`@id(Slime)` は `Task.Id.Slime` で要らなくなる）
- **候補のメモ**（ユーザー、実装しない）: far call でバンクを戻さない呼び出しの記法。far の interface にも普通の `farfn` にも。
  その後のバンクは自己責任

# コンパイラのバグ調査の計画（2026-10-18）

## 背景

ユーザーから「fc のコンパイラにバグがないかを詳しく調査してほしい。まずは計画を立てて」という相談。差分 fuzz・bugzoo・IR 検証器・asm のレジスタ検査という既存の基盤がすでに強い（[2026-09-19 の fuzz の発見ログ](2026-09-19-fuzz-findings-log.md)）ので、「何を今さら調べるのか」を先に決める必要があった。

## 相談したことと検討

- **本数を増やすだけでは足りない**。差分 fuzz の 3 判定（-O 0 / -O 2 / 最適化前の IR のインタプリタ）は同じ IR を共有するので sema の誤りが見えず、6502 も内蔵の 1 実装だけ。実行系が 1 系統という穴は本数では埋まらない
- **fc 4 の整数規則に Go の模型が無い**のが一番の空白。2026-09-28 以降に書き換えたばかりで、模型を持つ生成器（methods / format / grid / str / bank）の対象外。型規則は「通る / エラー」の表だけ
- **Mesen と QuickNES が Linux で必ず Skip になる**（MesenCE と libretro の DLL が Windows のみ）。実機の描画と scanline IRQ の見張りが、この開発機では完全に効いていない
- **テストが黙って空になる危険**は既に実績がある（2026-09-30 に bugzoo 22 中 16 が空振り、TestRandomConstFold が 0 本で通っていた）。fc 4 の作り直しで bugzoo がまたずれている可能性があり、まず測るべき
- 選択肢として「まず 2 万本回す」が安いが、出るのは既存の判定の範囲内のバグだけ。**判定を足してから回す**順に変えることにした

## 決定事項

- 調査の計画は [../wiki/plans/bug-hunt.md](../wiki/plans/bug-hunt.md) に置く（Phase 0 計測 → 1 既存 fuzz を長く → 2 穴を塞ぐ生成器 → 3 第 2 の実行系 → 4 不変条件の検査器 → 5 実プロジェクトとゲーム → 6 トリアージと記録）
- **主役は「オークルの穴を塞ぐ」**。本数を増やすだけの変更は Phase 1 で打ち切る
- 優先順位 1 は `TestRandomArithV4`（fc 4 の式の型と値を Go で計算し、型の全組合せはランダムでなく網羅の表を golden 化する）
- 実行系は「`m6502` の表と `r6502` の突き合わせ」→「表を引かない独立実装の 6502 を 4 つ目の判定に」の 2 段で足す
- **フラグ生存の検査（比較の N/Z/C を読む命令の前に壊す命令が挟まらないか）を asm レベルで入れる**。過去の同系統のバグ（梯子バグ、踏むスイッチ、`TestIfCallResultFlags`、`TestResidentCondRestore`）は bugzoo に 1 つも patch が無い
- 未定義動作の自動検出（範囲外添字の trap など）は作らない。仕様決定が必要なので Issue にして「診断を出す」側に寄せる
- 直すものは bugzoo の patch と生成器の形をセットで足す（無い修正は同じ穴に戻る）

## 2026-10-18 にこの開発機で確かめた事実（計画の前提）

- `go test ./...` は全緑（Linux、go1.27.1、ca65/ld65 は `~/.local/bin`）
- 非テストの Go 51,716 行（sema 13,936 が最大）、panic 箇所 494（sema 404）
- bugzoo 33 patch、`rpFeatures` の機能 42、`rand*_test.go` 15 本、コミット済みの fuzz の種 25 件
- CI は ubuntu + windows の `go test ./...`（`-race` は無い）+ 毎晩の fuzz + 日曜の bugzoo
- emu も内蔵 NES ランナーも同じ `internal/r6502`（`internal/m6502` は命令の性質の表でエミュレータではない）
- メモリは空き 34GB。fuzz はメモリ上限つきで回す（過去に OOM でセッションが落ちている）

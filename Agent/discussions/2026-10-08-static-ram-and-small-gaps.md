# 静的フレームの RAM の予約と、ゲームで見つかった小さな不足への対応（2026-10-08）

[デバッグ用のゲームで見つかったこと](2026-10-08-debug-games-findings.md) の相談の続き。

## 静的フレームの RAM の予約

- **決定**: `static_ram` を書かなければ、base.s の `FC_SRAM` は静的フレームが実際に使う分（`plan.RamUsed`）だけ取る（計画の上限は
  今までの 512）。書けばその大きさで固定する。ユーザー: golden の ROM が変わってよい
- 使う分だけにすると、関数の変数の量が変わるたびにグローバル変数の番地がずれて ROM 全体が変わる（ユーザーの指摘）。golden で ROM を
  比べるソース（test/ の 7 本・examples/miku）には `static_ram: 512` を書いて固定した（castle はもとから 256 で固定）。golden の
  ROM はそのまま（IR のダンプに option の行が増えただけ）
- ユーザーから「普段は最適の大きさで、golden 比較のときだけコマンドラインで指定する」案も出た。今は足さない: テストは Go の中で
  ビルドするので CLI のオプションはテストに効かず、ソースに書く固定は migrate のように中身を書き換える経路でも残る。ソースを変えずに
  別の版のコンパイラと ROM を比べたい場面が出たら足す
- games の 11 本は `@(static_ram: N)` を外しても RAM に収まる（使う量は 0〜72 バイト）

## 小さな不足 3 つ（fc 側で対応。ユーザー: 対応を入れる）

- **soa の `@len`**: 要素の数の定数（soa interface の置き場所も、宣言より前の const からも。宣言をその場で解決する）
- **slice を返す interface のメソッドの「何もしない」関数**: 長さ 0 の slice を返す（RAM の隠した変数（起動時に 0）を返す: ROM の
  定数だと書き換えられる slice に渡したときに読み取り専用の警告が出る）。配列はすべて 0 の定数。これで既定の本体が無くてよい
- **長さの決まった窓**: `a[x..x + K]` / `a[x..=x + K]`（x は同じ変数、K は定数。`K + x` も）は、長さが u16 の配列・広い slice から
  切っても長さ K の普通の slice。形は式の木で見る（同じ変数の値と、足す定数）。`a[x..y]` のように長さが式から決まらない切り方は
  今までどおり広い slice
- 検討して見送ったもの: 広い slice から普通の slice への暗黙の変換（長さを実行時に調べるか切り詰めるかが要る。明示の `@slice` で
  足りる）、`a[x..][..K]` の形（今の窓の形で足りる）

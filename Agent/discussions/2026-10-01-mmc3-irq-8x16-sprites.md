# MMC3 の走査線 IRQ と 8×16 のスプライト

## 背景

castle（8×16 のスプライト、MMC3 の走査線 IRQ）を Mesen で動かすと、スプライトの有無で IRQ の位置が横に数ドットずれる。原因と対策を相談した（まだ直していない）。

## 分かったこと（NESdev の MMC3 のページと PPU の仕組みから。Mesen で測ってはいない）

- MMC3 は PPU の A12 の立ち上がりを数える（A12 が M2 の 3 回の立ち下がりの間 Low だった後の立ち上がりだけ）。背景 $0000・スプライト $1000 なら、スプライトの読み出し（ドット 257〜320）の頭で 1 ラインに 1 回、ドット 260 付近で減る
- 8×16 ではタイル番号の bit 0 でパターン表が決まる（偶数 $0000、奇数 $1000）。空の枠はタイル $FF（$1000）を読む
- その走査線の最初の枠が $0000 のスプライトだと、A12 の最初の立ち上がりが後の枠まで遅れ、IRQ が 8 ドット単位で右にずれる。$0000 と $1000 が交互に並ぶと、余分に数えることもある
- 背景とスプライトを逆（背景 $1000・スプライト $0000）にしても直らない。空の枠のタイル $FF が $1000 を読むので、スプライトの枚数で立ち上がりの位置が変わる

## 対策の候補

1. スプライトを全部 $1000 側に置く（OAM のタイル番号を全部奇数にする）。背景は $0000。確実に直る。スプライトの CHR が $1000〜$1FFF の 4KB に限られるが、MMC3 の CHR のモード 0 なら $1000〜$1FFF が 1KB × 4（R2〜R5）なので、バンクを切り替えれば足りることが多い
2. IRQ が起きる走査線の次のラインにスプライトが掛からないようにする（HUD の境目にスプライトを入れない）。ずれるのは、その走査線でどのスプライトを読むかで決まるから
3. IRQ の中の書き込みを、数ドットずれても見えない所（画面外や、同じ色が続く所）で済ませる

## castle を見直した（同じ日）

castle はもう対策 1 の形だった。OAM に書くのは `ppu.sprite` / `ppu.sprite_idx` だけで、どちらもタイル番号を `pat | 1` にしている。PPUCTRL は 8×16・背景 $0000。なので A12 の立ち上がりの位置は、スプライトの有無では変わらないはず。ずれの原因の候補を CPU の側に移した（どれも未確認）:

- IRQ を受け付けるまでの遅れ: 実行中の命令が終わるまで待つので 0〜6 サイクル（0〜18 ドット）ばらつく。castle の IRQ の処理はサイクルを数えて hblank に書き込む作りなので、このばらつきがそのまま見える。スプライトが多いと主の側の処理が重くなり、IRQ の時に待ちのループ（短い命令）ではなく長い命令を実行している、という形で有無に連動しうる
- DMC の DMA（DPCM を鳴らしていれば、1 回 3〜4 サイクル盗む）
- NMI が長引いて IRQ の時刻に重なると、NMI が終わるまで待たされる（その場合はドットでなくラインの単位でずれる）

確かめ方: Mesen の Lua で、IRQ の入口の走査線とドット、割り込まれた PC を、スプライトありとなしで記録して比べる。

ユーザーの見立て: 初期化していない固定の枠（`sprite_idx` で使う OAM の先頭と末尾）だけが問題だったのでは。ありうる。fc のランタイムは RAM を消さず、`clear_out_sprite` は Y だけを 255 にするので、タイル番号のバイトは電源投入時の値（0 なら偶数 = $0000）のまま残る。その枠が `sprite_idx` を通らずに画面の中に出ると、A12 がずれる。対策は、消すときにタイル番号も奇数（$FF など）にすること。

## MMC3 で 8×16 を使うときの選択肢（まとめ）

- 基本は、スプライトを全部 $1000 側・背景を $0000 にする。$1000〜$1FFF は MMC3 の CHR の 1KB × 4 で切り替えられる
- $0000 のスプライトを混ぜると、次の 2 つのどちらかになる
  - $1000 の枠 → $0000 の枠 → $1000 の枠と並ぶと、A12 が長く Low になって、そのラインで 2 回数える（ライン数がずれる）
  - $0000 のスプライトがそのラインの枠の先頭に並ぶ場合（OAM で先に置く）は、数えるのは 1 回で、IRQ が 8 ドット単位で遅れるだけ。分割の書き込みがずれても見えない所なら使える。ただし、ちらつきを減らすために OAM の順を回す方式とは相性が悪い
- 背景 $1000・スプライト $0000 も、空の枠が $1000 を読むので、枚数で位置が変わる
- 走査線の数え方が A12 によらないマッパー（MMC5 など）や、スプライト 0 の当たりで分割する方法なら、この制約はない

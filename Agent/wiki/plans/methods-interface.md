# struct のメソッドと interface（ID で引くメソッドと soa）

2026-10-06 の相談（[経緯](../../discussions/2026-10-06-methods-interface.md)）。**計画の段階で、実装は始めていない。**
構文は決めた形の案で、細部は各段の実装の前に詰める。

## 目的

ゲームの敵・弾・エフェクトのような「型ごとに処理の違う要素を、決まった数のスロットで回す」形を、言語の機能で書けるようにする。
今は手で書いている（castle の敵: 型の番号の列、フィールドごとの列、型ごとに意味の変わる共有の列 `p1`〜`p8`、型の番号で引く
関数の表とバンクの表。6502 のゲームでは定番の形）。表・番号・共有の列の意味の対応をコンパイラが型で確かめ、表を作る。

効率の目標: 手で書いた形より遅くしない。

- 要素は soa の 1 バイトの添字
- メソッドの `self` はレジスタで渡す
- 呼び出しは ID で引く下位・上位の表
- フィールドは `lda 列,x`

## 決めたこと（2026-10-06、ユーザー）

- **段の順**: ① struct のメソッド → ② interface（共通のフィールド・ID・表）と soa → ③ far の interface
- **メソッドは struct の外に書く**: `function Point.add(self:Point, o:Point):Point`。実装を別のモジュール・ファイルに置ける
- **受け取り手の型はふつうの引数として書く**（Zig と同じ）: 値 `self:Point`・書き換え `self:*Point`・読むだけ `self:*const Big`・
  soa のハンドル `self:*Enemies`。名前 `self` は慣習（予約語にしない）
- **interface の構文は `interface` / `soa interface`**。実装は `struct Slime: Task = 1 { ... }`
- **一般の struct の埋め込みはやらない**（2026-10-06 に再確認）。共通のフィールドは interface に書く
- **1 つの interface は soa か普通の struct かのどちらか**。1 つの関数はどちらか 1 つの形だけを対象にする
- **ID は手動・自動の両方**（混ぜてよい）。ID は interface ごとの enum `Task.Id`（0 は「無し」で `.none`）。ゲームのデータの番号から要素を作る原始的な機能（`@set_id`）を入れる
- **メソッドを足せるのは型を宣言したモジュールだけ**。**要素を値として写すのは後の段まで禁止**
- **near / far は interface の宣言で決める**（`fn` / `farfn` と同じ関係）。far は呼ぶたびに切り替えて戻す（下の「段 3」）

## 段 1: struct のメソッド

```fc
struct Point { x:u8; y:u8; }

function Point.add(self:Point, o:Point):Point { return {self.x + o.x, self.y + o.y}; }
function Point.move(self:*Point, dx:u8):void { self.x += dx; }

soa Enemies:[8]Enemy;
function Enemies.update(self:*Enemies):void { self.x += 1; }   // soa のハンドル (1 バイト)

var p:Point;
p.move(1);                  // 変数なら &p を渡す
var q = p.add({1, 2});      // 値は写す
Enemies[i].update();
```

- `p.m(args)` は `T.m(p, args)` と同じ。呼ぶ側が受け取り手の形に合わせる:
  - 変数 → `&`
  - ポインタ → 中身を写す（値の受け取り手）
  - 書き換えるメソッドを変数でない値・const に呼べばエラー
- 呼び先は決まっているので直接呼び出し（インライン展開・静的フレームがそのまま効く）
- 名前: メソッドは型の名前の空間に入る。フィールドと同じ名前はエラー
- `public function Point.add` で公開。メソッドを足せるのは型を宣言したモジュールだけ（ほかのモジュールの型には足せない。2026-10-06 ユーザー）
- soa のハンドルの受け取り手は A/X で渡す（レジスタ渡しの規約を使う）。フィールドは `lda 列,x`
- fmt・doc（`fcc doc` にメソッドを型の下に並べる）・VS Code の色付けも合わせる

## 段 2: interface と soa

```fc
soa interface Task:u8 {               // ID の型
    x:u8; y:u8; slot:u8;              // 共通のフィールド (全部の実装が持つ)
    function init(self:*Task, p:u8):void;
    function process(self:*Task):void;
}
struct Slime: Task = 1 { dir:u8; speed:u8; }   // 手動の ID
struct Bubble: Task { life:u8; }               // 自動の ID
function Slime.process(self:*Slime):void { self.x += self.dir; }

soa Tasks:[16]Task;

Tasks[i].process();                   // ID で表を引く
Tasks[i] = Slime{x: 8, y: 16, dir: 1}; // ID と全フィールドを書く

// ゲームのデータの番号から作る
@set_id(&Tasks[k], map_data[j] as Task.Id);  // ID を書くだけ (範囲は調べない)
Tasks[k].init(param);                 // 書いた ID の実装の init が走る
if (@id_of(&Tasks[k]) == .Slime) { ... }
@set_id(&Tasks[k], .none);            // 空にする (0 は「無し」)
```

置き方

- **soa の interface**:
  - 列は ID の列・共通のフィールドの列・重ねて置く列（v0, v1, ...）の 3 種類
  - 実装のフィールドは重ねる列に先頭から割り当てる（Slime の `dir` も Bubble の `life` も v0）。u16 は下位・上位で 2 列
  - 列の数は全実装の最大。`@(variant: 8)` で上限を書けば超えたらエラー
  - 置き場所は soa 1 つだけ（1 つの interface につき 1 つ）。`*Task` / `*Slime` は `Tasks` の 1 バイトの添字
  - できないこと: `&self.x`、`*u8` への変換、要素を値として写すこと（後の段まで禁止。2026-10-06 ユーザー）
- **普通の interface**:
  - 要素は `[id][共通][重ねた中身]` の 1 つの塊で、大きさは一番大きい実装に合わせる
  - グローバル・ローカル・配列・struct のフィールドに置ける
  - `*Task` / `*Slime` は 2 バイトのアドレス。呼び出しは `(p),y` で ID を読んで表を引く
- 実装（`Slime`）を単独の変数にはしない（初めは）。「Task の入れ物を Slime として見たもの」

型の規則

- 実装のメソッドの中の `self.f`: 実装のフィールドを見て、無ければ interface の共通のフィールドを見る（探す所は 2 か所だけ）
  - 共通のフィールドと同じ名前を実装に書いたら、宣言の時点でエラー
- interface の型のまま読めるのは共通のフィールドと ID。実装のフィールドを外から読む変換（`as? Slime`）は後で
- 1 段だけ（実装の下に実装を作らない）。フィールドの上書き・`super` は無い。interface に既定のメソッドを書ける
- 実装は interface のメソッドを全部書く（既定のあるものは省ける）。書かなければエラー

ID

- 手動: `= N`。同じ番号はエラー
- 自動: 手動の番号を除いた空きを 1 から割り当てる。モジュールのパスと宣言の順で並べる（読む順に左右されない）
  - 実装を足すと後ろの自動の番号がずれる → **外のデータ（ツールで作ったマップ・セーブ・asm）に番号を書くなら手動**
- **ID は interface ごとの enum `Task.Id`**（2026-10-06 ユーザー）:
  - 基になる型は interface の ID の型（`:u8`）。メンバーは `none = 0` と実装の名前（`Task.Id.Slime`）。値は上の手動・自動の番号
  - 今の enum の規則がそのまま使える: 型の分かる所では `.Slime` / `.none`、`switch`、`@len`、整数との変換は明示（`as`）
  - ほかの interface の番号や、ただの整数を取り違えて入れるのを型で防ぐ
  - 実装の名前がメンバーの名前になるので、同じ interface の実装に同じ名前（別のモジュールの同名の struct）や `none` はエラー
- `@id_of(e):Task.Id` は実行時に読む、`@set_id(e, id:Task.Id)` は書く。`@id(Slime)` は要らない（`Task.Id.Slime` と書く）
  - `@set_id` が書くのは ID だけ（ほかのフィールドは 0 にしない。`init` が書く）
  - ゲームのデータの番号（u8）は `map_data[j] as Task.Id` で渡す（範囲は調べない）
- **0 は「無し」**（2026-10-06 ユーザー）。`@set_id(e, .none)` で空にし、`@id_of(e) == .none` で調べる。実装に `= 0` はエラー、
  自動は 1 から。`.none` の要素のメソッドは表の 0 番（interface の既定のメソッド。本体が空なら何もしない。既定が無ければ止める関数）
- 「無し」の書き方は、要素の `null` → 専用の言葉なし（`@set_id(e, 0)`）→ enum の `.none` と 2 回変えた（経緯は discussions）。
  見送った案:
  - 要素の `null`: ポインタの `null` と並ぶと紛らわしい（`e == null` と `*e == null`）
  - 予約語 `none`: 短いが、言語全体の予約語が増え、将来の optional などと名前がぶつかる
  - 整数の 0（`@set_id(e, 0)`）: 0 の意味が読んで分かりにくい
- `fcc build -d` に ID の割り当ての一覧を出す

呼び出しの作り方

- メソッドごとに ID で引く下位・上位の表（大きさは最大の ID + 1）
  - 実装の無い番号は既定のメソッド（無ければ止める関数）を指す
  - 表より大きい番号は調べない（配列の範囲外と同じ）。emu のテスト・debug のビルドで調べる印は後で
- 実装の組は閉じている（プログラム全体で分かる）ので:
  - 実装のメソッドは interface ごとの共通の規約（`self` を A/X、引数はレジスタか決まった置き場所）にできる。
    今の「アドレスを取られた関数」の entry（共通のバッファから写す）は要らない
  - 静的フレームの飛び先が正確（その interface のそのメソッドの実装だけ）
  - ID が定数なら直接呼び出しに。実装が少なければ分岐に展開（今の const の表の直接化と同じ）
- 表と列の数は、sema が全モジュールを読んだ後に決める（driver が作るモジュールに置く）。ハンドルは添字なので、ほかのモジュールの
  コンパイルの結果は列の数に左右されない

## 段 3: far の interface

```fc
soa interface Task:u8 @(far) { ... }   // ID ごとのバンクの表で切り替えて呼び、元へ戻す
soa interface Bullet:u8 { ... }        // 既定は near: fn と同じく、バンクは呼ぶ側の責任
```

| | near（既定） | `@(far)` |
|---|---|---|
| 関数ポインタで言えば | `fn` | `farfn` |
| 呼び出し | ID で下位・上位の表を引く | 下位・上位・バンクの表を引いて far call のトランポリン（`farcall_ay`。`self` を A で渡す） |
| バンク | 切り替えない（呼ぶ側の責任。切り替わるバンクにあっても何も言わない） | 呼ぶたびに切り替えて戻す |

- 1 つの実装のメソッドは同じバンクに置く（実装のモジュール）。バンクの表は interface に 1 本（ID ごとに 1 バイト）
- `@bank_of_id(id)`（`id:Task.Id`）でバンクの表を引ける。near の interface と合わせれば、手書きと同じ「ループの中で切り替え、戻すのは
  ループの後に 1 回」が書ける。バンクの表は `@(far)` か `@bank_of_id` を使ったときだけ作る
- 呼ぶたびに戻す費用の見積もり（概算、測っていない）: 戻す分で 1 回 20 サイクル前後、16 体で 1 フレームの 1 % ほど。
  今回はこれで十分（2026-10-06 ユーザー）
- `fcc build -d` に interface ごとの実装・ID・バンクの一覧を出す
- 割り込みから far の interface を呼んだときの警告は、今の far call の規則のまま

## 候補（実装しない。ほしくなったら）

- **far call でバンクを戻さない呼び出しの記法**（2026-10-06 ユーザー）: far の interface のメソッドも、普通の `farfn` も、
  呼び先のバンクへ切り替えて呼ぶだけで、戻さない。その後のバンクがどうなっているかは自己責任。続けて同じ窓の別の関数を呼ぶ
  ループで、戻す手間を省く（手書きの「戻すのはループの後に 1 回」を、near + `@bank_of_id` より短く書く）。
  自動でする形の検討メモが roadmap.md の「far call のバンク復帰を関数の出口まで遅らせる」にある（戻さない版のトランポリン）
- 続けて far call するとき、戻すのを後に回す最適化（呼ぶ側が固定バンクにあり、間で切り替わる窓を使わないと分かるとき）。
  呼ぶたびに戻す形を測って、遅さが問題になったら考える

## 前例（調べ直していない、知識による）

- 宣言の形: Pascal・Modula-2・Ada の可変レコード（共通のフィールド + タグ + 重ねて置くフィールド）。メソッドの表は無い
- 閉じた組をタグで呼ぶ: Rust の `enum_dispatch`、C++ の `std::variant` + `std::visit`、Zig の `union(enum)` と `inline else`
- SoA: Odin の `#soa`、Zig の `MultiArrayList`（タグ付きの共用体ならタグの列と中身の列）
- 置き方: 6502 のゲームの手書きの形（スーパーマリオブラザーズの敵の ID の配列・フィールドごとの配列と `JumpEngine`）
- Zig は埋め込みを持たない（`s.base.x`、`@fieldParentPtr`）。フィールドがどこから来たか読んで分かることを優先していると思われる

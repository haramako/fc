# 外部コマンドの定数マクロ（計画）

2026-09-30。組み込み（`@lz4`・`@rle`・`textmap` など）は今は `internal/sema` の `registerBuiltins` で登録していて、足すには fcc の
ソースに手を入れるしかない。プロジェクトの中の Go（ほかの言語でもよい）のコードで、**定数を作るマクロ**（表の生成・アセットの変換・
圧縮など）を後から足せるようにする。

## 決めたこと（2026-09-30 ユーザー）

- **対象は定数を作るマクロだけ**: 引数（定数）を受け取って定数のデータを返す。コードを出すマクロ（`@printf`・`@format`・`@copy`）は
  sema の中身（cexpr・IR・型）に深くつながっているので外に開かない（開くなら、マクロが fc のソースの断片を返してその場で構文解析して
  展開する形を後の段で考える）
- **外部コマンドを fcc の生存中は常駐させ、改行区切りの JSON（1 行に 1 つ）で要求と応答をやり取りする**
- textmap をこの仕組みに乗せるかは後で検討する（下の「textmap」）

## 宣言

```toml
# fc.toml
[macro_server.tools]
command = ["go", "run", "./tools/fcmacros"]
```

```fc
const SIN = @sin_table(256, 64);   // 結果は [256]i8 などの定数の配列
```

- 1 つのコマンドが複数のマクロを提供する（起動時のあいさつで名前を返す）。マクロの名前は `@` で始まる組み込みと同じ綴りで呼ぶ
  （組み込みと同じ名前はエラー）
- 作業ディレクトリは fc.toml のあるディレクトリ

## プロトコル

- 起動したら、まず 1 行: `{"macros": ["sin_table", "font_map"]}`
- 要求: `{"id": 1, "macro": "sin_table", "args": [256, 64]}`。引数は整数・文字列・バイト列（`{"bytes": "<base64>"}`）・整数の配列
- 応答: `{"id": 1, "result": {"type": "i8", "data": [0, 1, …]}, "deps": ["font.txt"]}`
  - `id` を付けるので、要求を並べて送れる（今の sema は 1 本で回るが、並列にしても困らない）
  - エラーは `{"id": 1, "error": "…"}`。fcc はマクロを呼んだ位置のエラーとして出す
  - `deps` はマクロが読んだファイル（キャッシュを捨てる判断に使う）
- マクロ側のログは stderr（fcc がそのまま流す）
- 結果の型（最初の版）: 整数 1 つ、整数の配列（要素の型つき。そのまま const の配列になる）、バイト列（base64）、文字列

## 寿命とキャッシュ

- 最初に使ったときに起動し、fcc の終了時に止める（使わないビルドでは起動しない）。落ちたら、そのビルドの間はエラー
- 起動には毎回時間がかかる（`go run` で 0.3〜1 秒）ので、ディスクのキャッシュも持つ: 「コマンド・マクロ名・引数・deps の内容のハッシュ」
  → 結果を `.fc-build` に置く。全部キャッシュに当たればプロセスを起動しない
- 将来、長く生きる fcc（`fcc watch`、言語サーバー）では常駐の効き目がさらに大きい

## textmap（後で検討）

textmap は「変換器を作る」マクロで、後から `_T("あいう")` が何度も呼ばれる。呼ぶたびにプロセスに問い合わせると往復が増えるので、
結果の型に「変換表」（文字 → コードの列）を足し、マクロは表を 1 回返すだけにして、`_T(...)` の変換は fcc の中でその表を引く案。
今の `textmap` も中身は表を作っているだけなので素直に乗る。組み込みの textmap を外に出すか、外部の変換表マクロと並べるかは後で決める。

## 進め方

1. 整数・整数の配列・バイト列・文字列の結果と、常駐のプロセス、fc.toml の宣言、ディスクのキャッシュ
2. 変換表の結果の型と textmap（上の検討の後）
